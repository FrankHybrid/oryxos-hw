# OryxOS 多实例扩展 AI 编程指南

> 本文档定义 OryxOS **阶段二（底座分布式 / 多实例扩展）** 的 AI 编程实施思路。主体思路仍然是 **Spec-Kit 做主体实现 + 手动提示词做单点改造** 的混合模式，但两段的分工与阶段一相反：阶段二是 brownfield 改造，先用**手动提示词**完成抽象层与档位隔离的清理（宪法增补第 1 条：单机档零回归），再用 **Spec-Kit** 把集群档的 7 个 user story 逐个做出来。前置阅读：[IndustryResearch.md](IndustryResearch.md)（业界做法与取舍）、[DemandAnalysis.md](DemandAnalysis.md)（需求与验收）、[TechnicalSolution.md](TechnicalSolution.md)（设计与决断）、[README.md](README.md)（范围 / 术语 / 决断 D1–D14 / 状态表 / 量级目标 / M0–M5 / Demo A–E），以及阶段一文档 `docs/oryxos-docs/AiProgrammingGuide.md`（实施方法基线）与项目根目录 `CLAUDE.md`（宪章八原则 + 042 工作区存储约束）。本文档讲**思路、拆解方法与红线**，不绑定具体时间安排，也不展开提示词全文。

> **本文档写的是本周期的实施方法，不是已完成实现的记录**。引用阶段一已落地的能力（五大核心能力、14 个模块、审计表 day one 落库、渠道适配器、知识库、人格库、Tool Policy、定时任务、主密钥加密、Docker 部署）只作为基线；集群档的一切都是待建目标。所有术语、决断编号、表名、里程碑、Demo 编号一律以 [README.md](README.md) 第 3~7 章为准。

## 1. 实施总览

### 1.1 主体思路：仍是混合模式，但分工与阶段一不同

阶段一的成功公式是"**Spec-Kit 做主体（按 5 个 user story 拆）+ 增量阶段切手动提示词**"。阶段二沿用这个公式，但把顺序**倒过来**：

| 维度 | 阶段一 | 阶段二 |
|------|--------|--------|
| 代码性质 | greenfield，从零建 14 个模块 | **brownfield**，在既有代码路径上加档位判断 |
| 主体工具 | Spec-Kit（specify → plan → tasks → implement） | **先手动提示词清理抽象层，再 Spec-Kit 做集群功能** |
| 手动提示词用在 | 主体完成**之后**的增量 | 主体开始**之前**的准备与隔离 |
| 硬约束 | 五大能力跑通 | **同一 jar 同一镜像下，单机档零回归**（D1、宪法增补第 1 条） |
| 正确性难点 | 功能能否跑通 | **并发与共享卷上的恰好一次语义**，编译期看不出来 |
| 验证方式 | 单机 CI + Demo 一~五 | 单机 CI 只是下界，必须多进程 / 多副本 / 存储矩阵 |

为什么必须先手动提示词、后 Spec-Kit？三个原因：

1. **brownfield 的"改造"部分没有新需求可写**。把 `oryxos-core` 里的裸文件访问收敛到 `WorkspaceStorage`、把 `ChannelAdminService` 的停机链路加上属主释放、把进程内去重 Map 抽成接口——这些都是**接口形状的调整**，没有新的用户可见行为，写 spec 只会产出"重构 spec"这种空转产物。
2. **Spec-Kit 的 specify 阶段会重新描述整个特性**。如果一上手就跑 Spec-Kit，AI agent 会在"集群档"这个 spec 下顺手改 core 主链路（把协调判断渗进 ReAct 循环），而这一步恰恰是最不该由 spec 驱动的——它需要人盯着 `git diff` 逐个确认单机档路径没变。
3. **清理完成后才有稳定的契约可写 spec**。`WorkspaceStorage`、认领原语、档位判定入口这些契约定下来之后，集群档的 7 个 user story 才有明确的"接入点"，Spec-Kit 的 tasks 才能拆成"一个 task 一个可验证行为"。

> **一句话**：阶段二的前置清理是**把单机档保护起来**（红线是"不许动"），集群档建设是**在新档位上叠加功能**（红线是"恰好一次"）。前者用手动提示词 + 人 review，后者用 Spec-Kit + Demo 验收。

### 1.2 跟需求文档 + 技术方案的关系

实施指引不重写需求和技术方案，而是把已有文档喂给 Spec-Kit。对应关系：

| Spec-Kit 输入 | 来源文档 | 作用 |
|--------------|---------|------|
| `/speckit.constitution` 增补 | `CLAUDE.md` 宪章八原则 + 042 工作区存储约束 + [TechnicalSolution.md](TechnicalSolution.md) 第 1 章（方案概述）决断表 | 阶段二的非协商条款（见 3.2） |
| `/speckit.specify` 输入 | [DemandAnalysis.md](DemandAnalysis.md)（功能需求 / 非功能需求 / 数据模型 / 验收章） | 转成 7 个 user story 的 spec |
| `/speckit.plan` 输入 | [TechnicalSolution.md](TechnicalSolution.md)（第 4 章共享状态层与 CAS 认领原语、第 5 ~ 7 章恰好一次三件套、第 8 章渠道属主、第 10、11 章共享工作区与版本号总线、第 12 章知识库在集群档、第 16 章容器交付） | 转成模块与契约级实施 plan |
| `/speckit.tasks` 输入 | `spec.md` + `plan.md` + `constitution.md` | 按 user story 组织 task，并可被阶段一的 `tasks.md` 风格复用 |
| acceptance criteria | [README.md](README.md) 第 7 章 Demo A–E + [DemandAnalysis.md](DemandAnalysis.md) 验收章 | 直接复用，不另立口径 |
| 量级目标 | [README.md](README.md) 第 6 章 | 压测与验收数字的唯一口径（含 mock provider 固定时延的测量前提） |

> **关键注意**：技术方案是 `/speckit.plan` 的输入，plan 里的模块结构必须与阶段一 `docs/oryxos-docs/TechnicalSolution.md` 第 10 章的 **14 个模块**一致，只在必要时新增模块（例如把集群协调放进既有模块还是新开一个），新增必须在 plan 里写明理由并同步更新模块表与 `CLAUDE.md`。喂文档时确保用的是本套最新版，否则生成的 plan 会按错误的模块边界拆分。

D1–D14 不是"建议"，而是 spec 的输入约束。`/speckit.plan` 出来之后要能逐条回答"这条决断落在哪个模块、哪张表、哪个契约上"，答不上来的决断就是设计漏项。

### 1.3 拆解策略：按 user story 拆，不按时间拆

阶段二按 **7 个 user story** 组织，每个对应一段集群能力，与里程碑 M0–M5 一一对应或一对多。

| User Story | 内容 | 里程碑 | 依赖 | 可并行 |
|-----------|------|--------|------|--------|
| **US-1** | 共享状态基座：集群档开关、实例标识、误配拒启动、实例心跳、PostgreSQL 档 | M0 | 无（但依赖准备阶段的档位隔离清理） | — |
| **US-2** | 会话轮次跨副本恰好一次（`session_turn_leases`） | M1a | US-1 | 与 US-3 串行（同为 M1，共享认领原语的首个落地） |
| **US-3** | 定时到点认领 + 入站事件回执去重（`schedule_claims` / `event_receipts`） | M1b | US-1、US-2（复用认领原语） | 与 US-4 并行 |
| **US-4** | 渠道属主与停机链路（`channel_ownerships`） | M2 | US-1 | 与 US-3 并行 |
| **US-5** | 共享工作区与版本号总线（`workspace_versions`、存储插件、本机执行视图、管理写预约、逃生舱） | M3 | US-1 | — |
| **US-6** | 知识库代次化（`knowledge_build_claims` / `knowledge_generations`） | M4 | US-5 | — |
| **US-7** | 容器交付与验证（Helm Chart、探针、滚动升级、OTel、HA 演练、压测） | M5 | US-1 ~ US-6 全部 | — |

**推进顺序**：US-1 → US-2 → US-3 ∥ US-4 → US-5 → US-6 → US-7

- US-1 是唯一的"零依赖"user story，也是唯一一个**必须先做完才能写任何协调逻辑**的：档位判定入口、实例标识、共享 PostgreSQL 连接的建立方式，决定了后面 6 个 US 的代码长什么样。
- US-2 排在 US-3 前面，不是因为更重要，而是因为**会话轮次租约是认领原语最完整的形态**（有续约、有排队、有崩溃接管、有续约失败的语义）。原语先在 US-2 上做扎实（含契约测试），US-3 的定时认领和事件回执就是"换个幂等键复用同一套语句"，task 数量和安全风险都下降。
- US-3 与 US-4 互不依赖，可并行：前者是数据库面协调，后者是长连接属主与停机链路，改的模块不重叠。
- US-5 排在 US-6 前面，因为知识代次化建立在工作区存储抽象与版本号总线之上（重建认领要 bump `knowledge` 域，索引段落盘要走原子改名）。
- US-7 依赖全部：Helm Chart 的探针要检查数据库与工作区，滚动升级要验证前面所有"恰好一次"在 Pod 重启下依然成立。

> **不用 P1/P2/P3 优先级标记**。理由与阶段一一致：优先级标记会被误读成"靠后的可以不做"，而 US-5 ~ US-7 恰恰是"能上线"的门槛（共享工作区不做，多副本就是数据分裂；Helm 不做，企业装不进去）。本文档只讲依赖顺序，不讲重要性排序。

每个 user story 完成后跑一次 `/speckit.analyze`，并留下该 US 对应的里程碑可演示成果（M0–M5 的口径见 [README.md](README.md) 第 7 章）。

### 1.4 与阶段一最大的不同：这是 brownfield 改造

阶段一是"在空仓库里按 spec 长出代码"，阶段二是"在长好的代码里加一个档位，并且不许碰坏原来的档位"。四条差异决定了本文档后面所有的方法选择：

| # | 差异 | 具体表现 | 对应的方法调整 |
|---|------|---------|--------------|
| 1 | 要在既有代码路径上加**档位判断** | ReAct 循环、`AgentScheduler`、`InboundMessageService`、渠道适配器的启动/停机、`ContextLoader` 的 agent 扫描、知识的索引与检索，都要在集群档下换一套存储面行为（D1） | 先用手动提示词把档位判定**收敛到少数几个入口**，禁止在 core 主链路里判断"我是不是集群档"（见 3.5 review checklist 第 1、2 条） |
| 2 | 正确性问题在**并发与共享卷**上，不在编译期 | 先查后写的认领竞态、用应用时钟判断过期、用墙钟做幂等键、`WatchService` 事件丢失、软连接用逻辑路径校验——全都编译通过、单线程测试全绿 | 认领原语先写契约测试再写实现；多进程集成测试（3 副本并发同会话）；存储矩阵冒烟（见 5、6.3） |
| 3 | 无法只靠单机 CI 验证 | 单机 CI 只能证明"单机档没坏"，证明不了"3 副本下恰好一次" | 单机 CI 是**下界不是上界**：集群档功能必须在 kind/多进程环境跑 Demo A–E；真实 NFS / 云盘 RWX 做少量回归 |
| 4 | 任何一步都不能让单机档回归 | 阶段一已有渠道、知识、定时、人格、治理等能力在用，默认档就是单机档（`oryxos.cluster.enabled=false`） | 每个 task 的验收条件里都带"单机档回归测试通过"；批次化改造，每批结束仓库处于可发布状态 |

> **brownfield 的最大风险不是"写不出集群档"，而是"为了写集群档把单机档改坏了"**。单机档回归在阶段二里不是"顺手跑一下"，而是每个 user story 的硬性验收条件之一。

### 1.5 本章小结

混合模式不变，**顺序与分工变了**：先手动提示词做档位隔离与抽象层清理，再 Spec-Kit 做 7 个 user story 的集群档功能；拆解按 user story + 里程碑（US-1 → US-2 → US-3 ∥ US-4 → US-5 → US-6 → US-7），不按时间；验收口径来自需求文档与 Demo A–E，设计口径来自 D1–D14，本文档不新造口径。

> **注意**：本文档的"准备阶段"包含一段阶段一没有的工作——**先做一批手动提示词的清理提交**。跳过它直接跑 Spec-Kit，AI agent 几乎必然把协调逻辑写进 core 主链路，事后返工代价远大于前置清理。

## 2. Spec-Kit 匹配度评估

写实施计划之前先回答一个根本问题：**Spec-Kit 在阶段二还合适吗？** 结论是"合适，但适用范围比阶段一窄，必须配一套不依赖 Spec-Kit 的验证手段"。

### 2.1 Spec-Kit 适合什么场景

Spec-Kit 把 AI 辅助编码结构化成可重复的 specify → plan → tasks → implement 流程，让 spec 成为代码行为的契约与单一事实来源。阶段一已论证过它的适用面（greenfield、medium 以上规模、需求清晰、AI agent 协作、方法论场景）与不适用面（小 feature、上下文超出单次窗口的 brownfield、探索性研究）；阶段一"五条全中"，阶段二需逐条重估。**阶段二多出来的那条不适用面是"正确性主要由运行时并发行为决定的改动"——spec 描述不了竞态。**

### 2.2 阶段二的匹配度逐维评估

| 评估维度 | 阶段二情况 | 匹配度 |
|---------|-----------|--------|
| greenfield | **不是**。在阶段一 14 个模块、既有渠道/知识/定时/人格/治理实现之上改造 | ❌ 不匹配（阶段一的核心优势消失） |
| 规模 | 7 个 user story、6 个里程碑、9 张新表 + 审计表增量 + Helm Chart，典型 large | ✅ 匹配 |
| 需求清晰 | 需求文档给了功能/非功能/数据模型/验收四层，D1–D14 已定，边界（不做阶段三/多活/多主/新中间件）已划 | ✅ 匹配 |
| AI agent 协作 | 本周期仍然用 Claude Code 做主体实现 | ✅ 匹配 |
| 方法论价值 | 阶段二新增的"档位隔离 + 恰好一次 + 误配拒启动"需要被固化成可复用模式 | ✅ 匹配 |
| **并发正确性可验证性** | spec 能描述"同一会话恰好一次"，但**描述不了** CAS 语句形状、续约线程时序、崩溃接管顺序；AI 一次写对的概率低 | ⚠️ 部分匹配（需额外验证手段） |
| **共享存储行为可测性** | NFS/CIFS/云盘 RWX 的 rename 原子性、可见性延迟、watcher 可靠性，单机 CI 里无法复现 | ⚠️ 部分匹配（需存储矩阵环境） |

**结论**：Spec-Kit 仍然适合做**集群档的功能实现**（US-1 ~ US-7 的"加什么"），不适合做**档位隔离的改造**（"怎么加而不破坏"）。所以阶段二把改造段交给手动提示词，把功能段交给 Spec-Kit。

### 2.3 局限与应对

| 局限 | 阶段二的具体表现 | 应对 |
|------|----------------|------|
| spec 不会自动跟实现同步 | 集群档的"实现漂移"（比如把租约续约偷偷改成异步）在单机档测试里完全看不出来 | 每个 user story 结束跑 `/speckit.analyze`；改动回写 `tasks.md`（见 6.4） |
| AI 在并发正确性上一次写对的概率低 | 认领原语是最容易写歪的一段：写成先查后写、用应用时钟判过期、续约放异步线程 | **先写契约测试再写实现**；补 3 副本并发集成测试 |
| 共享卷行为无法在单机 CI 复现 | rename 原子性、跨节点可见性延迟、`WatchService` 事件丢失，本地盘上表现良好 | **存储矩阵冒烟**；真实 NFS/云盘少量关键回归；集群档不装 watcher（D8） |
| brownfield 上下文超出单次窗口 | 整个仓库 + 阶段二设计 + 阶段一历史决策，放不进一次 AI 会话 | **按档位隔离分批改**，每批只碰一个关注点，每批结束单机档可编译可测 |
| Spec-Kit 本身在迭代 | 命令名、artifacts 格式、集成方式都在变 | 不锁定版本细节；实施前锁一个版本，期间不升级；只用官方核心命令 |

> **注意**：第 1 ~ 3 条在第 7.1 节会按"表现 / 应对"再展开一次（那里是**实施阶段的风险视角**，这里是**工具匹配视角**），口径一致，不重复论证。

### 2.4 本章小结

- 阶段二的匹配度是"**规模、需求、协作、方法论 ✅；greenfield ❌；并发正确性、共享存储 ⚠️**"。
- 因此工具分工明确：**Spec-Kit 管功能增量，手动提示词管档位隔离与单点修补**。
- Spec-Kit 的产出（spec/plan/tasks）在阶段二的作用是**防止功能漏项与契约漂移**，它不是并发正确性的保证；正确性由契约测试 + 多副本演练保证。

> **注意**：不要因为"并发正确性 spec 描述不了"就放弃 spec。恰恰相反——正因为 AI 容易写错，才更需要把"同一会话恰好一次""每个 `fire_time` 恰好一行 `task_executions`""误配启动即拒"这些**可判定的验收条件**写进 spec，让每个 task 都能被验证，而不是靠感觉。

## 3. 准备阶段

准备阶段是正式实施前的脚手架工作，产出四样东西：**一份干净的档位隔离基线**（手动提示词产出）、**constitution 增补**、**spec**、**plan**。与阶段一相比，阶段二的准备阶段多出第一样，而且它必须排在最前面。

### 3.1 工具与工作区

沿用阶段一的约定，不引入新工具链：

| 环节 | 工具 | 约定 |
|------|------|------|
| 主体实现 | Spec-Kit（Specify CLI + Claude Code） | 工作区沿用阶段一的 `.specify/`（`memory/`、`templates/`、`scripts/`、`workflows/`、`integrations/`）；spec 目录沿用 `specs/<三位序号>-<短横线特性名>/`（阶段一为 `specs/001-llm-provider-abstraction/`），阶段二每个 user story 或每组相关 user story 一个目录，artifacts 命名保持 `spec.md` / `plan.md` / `tasks.md` / `data-model.md` / `research.md` / `quickstart.md` / `contracts/` / `checklists/` |
| 手动提示词 | Claude Code（直接对话，不走 Spec-Kit） | 用于准备阶段的档位隔离清理，以及上线后的单点修补（第 6 章） |
| 运行环境 | 本地目录 + NFS + 云盘 RWX + kind | 本地目录与单机档测试跑每条提交；kind 跑集群档 Demo A–E 与滚动升级；真实 NFS/云盘做少量关键回归 |

### 3.2 `/speckit.constitution`：宪章增补

阶段一宪章八原则（见 `CLAUDE.md`）在集群档下**全部继续有效**，但不足以约束集群档引入的新风险。阶段二在此基础上**增补 5 条同级非协商条款**，写进 `.specify/memory/constitution.md`（作为增补章节），并同步在 `CLAUDE.md` 的"不可违背的原则"一节登记。

> 与阶段一相同的纪律：`constitution.md` 增补写一次定下来，实施期间不改；发现某条不对就停下来重新讨论，**不允许 AI agent 自己修改 constitution**。

#### 增补一：单机档零回归，同一 jar 同一镜像

`oryxos.cluster.enabled=false`（默认档）的代码路径**不得新增任何协调调用**——不查 `instances`、不取租约、不 bump `workspace_versions`、不轮询共享状态；单机档与集群档必须是**同一个 jar、同一个镜像、同一份配置结构**，唯一区别是这个开关及其要求的存储面；每个 task 的验收条件都必须包含"单机档回归测试通过"。

> **为什么**：企业绝大多数部署仍是单实例（阶段一的默认形态），为非目标场景付复杂度是净损失；两套产物会立刻产生"哪个版本修了哪个 bug"的维护地狱（D1）。**违反后果**：单机档凭空多出数据库往返与后台线程，启动变慢、故障面扩大；一旦分叉产物，回归与发布流程失效，既有渠道/知识/定时/人格/治理能力在默认档上出现难以定位的行为变化。

#### 增补二：跨副本互斥只允许 CAS 单语句 + TTL 租约

一切跨副本互斥（会话轮次、定时触发、事件回执、渠道属主、知识重建、管理写预约）只能用**一条带条件的写语句**完成认领，凭据带 TTL，持有方周期性续约；**禁止**应用层"先查后写"（read-modify-write）、禁止悲观长事务、禁止用应用时钟判断过期。

> **为什么**：先查后写有竞态窗口，两个副本会同时认为自己持有；长事务会拖垮连接池（D4）；TTL 是崩溃后唯一可靠的接管依据（D4 靠租约过期而非心跳丢失判定）；崩溃轮次按 D6 标失败、不重放。**违反后果**：同会话双回复、定时重复执行、渠道互踢、索引重复重建——**不可审计的静默正确性故障**，只在并发下偶发，事后极难复现。

#### 增补三：禁止为集群能力引入异步编程模型

不引入 Reactor / WebFlux / `CompletableFuture` 等异步模型（阶段一原则七在集群档下继续成立）；租约续约、版本号轮询、回执清理、断线重试**全部在调度线程上同步阻塞**，并发靠 Java 21 Virtual Thread 承载，不靠回调链。

> **为什么**：续约/轮询天然是"固定节奏的小任务"，同步写法可读、可测、可断点；异步化会让"续约到底有没有在跑""失败了几次"变成不可直接观察的状态，而这两件事恰好是恰好一次语义的命门。**违反后果**：续约异常被吞导致租约静默过期、接管风暴；调试只能靠日志拼时间线；同步执行模型被撕裂。

#### 增补四：集群档误配必须拒启动，禁止静默降级

启动时的档位校验是 **fail-closed**：集群档下有 **7 类**不支持的组合——SQLite 档、markdown 记忆后端、内存（memory）知识后端、`oryxos.workspace.storage=local`、工作区标识缺失或不匹配、主密钥缺失或跨副本不一致、实例标识重复——必须**直接启动失败**并打印恢复指引，**不得**回退本地存储、不得跳过协调原语继续跑。**另有 1 类运行期 fail-closed**（不占启动校验名额）：协调基质（数据库）不可用时集群档拒服务，不降级为单机。

> **为什么**：错的存储组合会让多实例静默读写各自的数据副本，故障在几天后以数据分裂的形式暴露且不可审计（D11），启动失败是唯一低成本的暴露时机。**违反后果**：多副本各自一套数据，用户看到"消息一会儿有一会儿没有"，事后无法通过审计还原哪条消息落在哪个副本。

#### 增补五：工作区访问只走存储抽象 + 本机执行视图

业务代码访问工作区**只能**通过 `WorkspaceStorage.root()/resolve()` 取得 NIO Path；**禁止**把逻辑路径转成字符串后用 `Path.of` 绕回默认存储；插件以 `WorkspaceStorageProvider.id()` 显式选择；**本机执行（文件 Tool、Shell Tool）必须调用 `nativePath`**；共享模式启动先校验管理员预置的 `.workspace-id`，不匹配即拒；`.workspace-*` 与 `.staging` 为内部保留路径（042）。

> **为什么**：共享工作区里"逻辑路径"与"本机可执行路径"不是一回事（D9）；裸文件 API 会绕过存储插件与原子落盘，静默写坏共享卷（D7 只依赖读写可见 + rename 原子）。**违反后果**：多副本数据分裂、写到本机而非共享卷、软连接越界漏检、原子改名约定被绕过导致读到半成品文件。

| 原则 | 集群档下的具体要求 |
|------|------------------|
| 一（自实现 ReAct）、二（Spring AI 只用两件事、禁用自动 tool 执行） | 多副本不改变 ReAct 的归属与 tool 调度权；协调逻辑不得挤进循环体 |
| 三（Provider 显式映射） | 每副本各自持有显式映射，不跨副本共享 Provider 状态 |
| 四（一个目录 = 一个 Agent；Skill 以相对软连接绑定 + 渐进披露） | 共享卷上 Skill 绑定视图与公共实体库的路径关系不变；软连接与真实路径校验必须取 `nativePath` 的真实路径（与增补五一致） |
| 五（审计 day one 落库） | 每条审计行带 `instance_id`，与既有 `trace_id` 一起构成跨副本链路（D13） |
| 六（软连接真实路径校验） | 共享卷下更严：必须用**本机执行视图**取真实路径，用逻辑路径校验会漏检越界 |
| 七（同步执行模型） | 续约、轮询、重试全部在调度线程同步阻塞（增补三把它抬成独立条款） |
| 八（Tool 模块三合一） | 不因集群化拆模块；协调原语与存储抽象在 core 出契约、下游模块实现（与 3.4 的"模块与契约清单"一致） |
| 042（工作区存储约束） | 只走存储抽象；保留路径不可占用；管理写互斥预约不自动过期 |

### 3.5 plan 生成后的人工 review checklist

**Plan 生成后人工 review 是必要环节，不可省。** 阶段二的 review 比阶段一更重，因为 AI agent 在 brownfield 上会本能地"顺手把逻辑放到它觉得最自然的地方"，而最自然的地方通常是 core 主链路。逐条检查：

| # | 检查项 | 为什么 AI 会做错 | 正确做法 |
|---|--------|----------------|---------|
| 1 | 有没有把协调逻辑渗进 core 主链路 | 在 `ReActLoop` / `PromptBuilder` 里加一行"如果是集群档就取租约"是最省事的写法 | 协调逻辑放在触发源外层（会话入口、调度器、渠道适配器），core 循环体保持不认识"集群"这个概念 |
| 2 | 有没有在单机档路径里新增协调调用 | "统一走一套逻辑"看起来更整洁 | 单机档路径零协调调用；档位差异在装配层体现（宪法增补一） |
| 3 | 有没有用 `SELECT` 再 `UPDATE` 实现认领 | 先查后写是最直观的写法，AI 默认这么写 | 单条 CAS：`UPDATE ... WHERE owner IS NULL OR expires_at < now()`（受影响行数=1 才算认领成功），或 `INSERT ... ON CONFLICT DO NOTHING` |
| 4 | 有没有用应用时钟判断过期 | JVM 里的 `Instant.now()` 最方便 | 过期判定用数据库时钟或单调时钟；多副本的墙钟不可信（宪法增补二） |
| 5 | 有没有用墙钟做定时幂等键 | `new Date()` 顺手 | 幂等键取 `CronTrigger` 的**理论触发时刻**，落 `(schedule_id, fire_time)` 唯一约束（D5） |
| 6 | 有没有把 `WatchService` 留在集群档 | 阶段一已有 watcher，留着"也没坏处" | 集群档不装 watcher（D8）；变更感知只走 `workspace_versions` 轮询 + 逃生舱 |
| 7 | 有没有裸 `Path.of` 绕开存储抽象 | 既有代码里可能本来就有，AI 会照着抄 | 一律 `WorkspaceStorage.root()/resolve()`（042、宪法增补五） |
| 8 | 有没有忘记 `nativePath` | 逻辑路径能通过编译、也能在本地测试跑通 | 本机执行视图（文件 Tool、Shell Tool）必须取 `nativePath` |
| 9 | 有没有引入异步模型 | `CompletableFuture` 写并发"更现代" | 同步阻塞 + 调度线程（宪法增补三、阶段一原则七） |
| 10 | 有没有漏掉审计的 `instance_id` | 既有的 `tool_invocations` / `llm_calls` 写入点容易只加协调逻辑不加列 | `tool_invocations`、`llm_calls` 增 `instance_id`；`task_executions` 增 `instance_id` 与 `fire_time`（D13） |
| 11 | 有没有忘记误配拒启动 | 校验是最容易被认为"可以后面补"的部分 | 启动误配 **7 类**（SQLite 档、markdown 记忆后端、内存（memory）知识后端、`oryxos.workspace.storage=local`、工作区标识缺失或不匹配、主密钥缺失或跨副本不一致、实例标识重复）全部拒启动并给恢复指引；另加**运行期 fail-closed 1 类**（数据库不可用拒服务、不降级为单机）（D11、宪法增补四） |
| 12 | 有没有把阶段三的 A2A 混进来 | "跨副本协作"听起来就是 Agent 互相调用 | 阶段二只有"共享状态"，没有跨节点 Agent 协作；A2A 属阶段三（D14、[README.md](README.md) 第 2 章线外第 1 条） |
| 13 | 迁移脚本有没有做到双轨同版本号只增不改 | AI 常常只给 PostgreSQL 轨写 SQL | 两 vendor 各一份、同版本号、只增不改；`hibernate.ddl-auto` 保持 `none`（[README.md](README.md) 第 5 章） |
| 14 | 有没有默认参数自己发明数值 | TTL / 间隔这类数字 AI 会随手填 | 一律用 [README.md](README.md) 第 6 章统一默认参数表的配置项名与数值 |

Review 通过后 `plan.md` 锁定。**任何一条不过，退回重写而不是"记在 issue 里"**——这 14 条里每一条的违反后果都不在编译期暴露。

> **artifact 约定沿用阶段一**：`specs/<三位递增序号>-<短横线特性名>/` 下就是 `spec.md`、`plan.md`、`tasks.md`、`research.md`、`data-model.md`、`quickstart.md`、`contracts/`、`checklists/` 这八件（阶段一样例见 `specs/001-llm-provider-abstraction/`），**不发明新结构**。其中 `contracts/` 的纪律是**一份契约一个 md 文件**（阶段一是 `provider-service.md`、`llm-calls-schema.md` 等），阶段二的认领原语、存储抽象、属主租约、知识代次各自独立成文，便于第 6.4 节的 artifacts 回写与漂移检查定位到具体文件。

> **准备阶段的完成判据**：`constitution.md` 增补 5 条落定 + `spec.md` 7 个 user story 全部可判定 + `plan.md` 五块必备内容齐全 + 14 条 review 全过 + 单机档全量测试绿。五条全中才算准备完成。

## 4. 基于 Spec-Kit 的实施拆解

准备阶段把 spec 与 plan 备齐，下面按 7 个 user story 拆解。每个 user story 的拆解结构一致：**核心目标 / 涉及模块 / Spec-Kit 任务拆分思路 / 关键 task 颗粒度 / 验收 Demo / 提示词要点与红线**。

task 颗粒度的统一判据：**一个 task = 一个可验证行为**。可验证的含义是"能写出一个断言或一个可演示步骤来证明它做到了"，而不是"写完了一个类"。`tasks.md` 的组织方式沿用阶段一：按 user story 分组、组内按依赖排序、可并行任务显式标注 `[P]`、每个 task 末尾标注它对应的验收条目。

> **每个 task 的通用完成判据**（不逐条重复）：单机档回归测试通过 + 本 task 的断言通过 + 该 US 完成后跑 `/speckit.analyze`。

### 4.1 US-1：共享状态基座（M0）

**核心目标**：让 OryxOS 能"以集群档的身份"起来并自证身份，同时保证任何不支持的配置组合都在启动那一刻被拒绝。

**涉及模块**：`oryxos-core`（档位配置模型、启动校验契约、实例标识与心跳契约）；`oryxos-storage`（共享状态表迁移脚本、`instances` 仓储、数据库时钟读取）；`oryxos-web`（`GET /api/v1/instances`）；`oryxos-boot`（配置装配与档位隔离入口，唯一的档位判定收敛点）；`oryxos-cli`（`ConfigLoader` 校验与报错文案）。

**Spec-Kit 任务拆分思路**：US-1 是后面 6 个 US 的地基，拆解上要"先把地基的形状定死再填内容"。预期 task 类别：档位与配置类（`oryxos.cluster.*` 配置项与默认值、`instance-id` 缺省生成规则）；启动校验类（启动误配 **7 类** → 启动失败 + 恢复指引；另加运行期 fail-closed 1 类 → 数据库不可用拒服务）；状态表类（`instances` 迁移脚本 + 仓储 + 状态枚举 `starting` / `ready` / `draining` / `stale`）；心跳类（注册、周期心跳 10s / 失效判定 30s、关停置 `draining`）；实例视图类（`GET /api/v1/instances` + 响应契约）；档位隔离类（档位判定收敛到装配层，确认 core 主链路不认识"集群"）。

**关键 task 颗粒度**（一个 task 一个可验证行为）：
1. 定义 `oryxos.cluster.*` 配置项与默认值，并让 `ConfigLoader` 在缺省时按单机档启动（断言：默认配置下 `cluster.enabled=false`，不连数据库）
2. 生成并暴露本副本 `instance-id`（断言：两个副本各自非空且互不相同；显式配置时以显式值为准）
3. 实现启动校验与拒绝路径（断言：7 类启动误配各有一条失败用例，另加 1 条运行期 fail-closed 用例，报错含恢复指引；正确组合正常启动）
4. 写 `instances` 表迁移脚本（断言：双轨目录同版本号各一份；集群档下 `flyway_schema_history` 恰好一次应用）
5. 实现注册与心跳续约（断言：启动后 30s 内 `instances` 出现本实例且 `last_heartbeat_at` 单调前进；心跳线程是同步阻塞循环）
6. 实现关停置 `draining`（断言：SIGTERM 后状态可观察为 `draining`，进程按 `spring.lifecycle.timeout-per-shutdown-phase` 退出）
7. 实现 `GET /api/v1/instances`（断言：2 副本环境下返回 2 条记录，含 `status` 与心跳时间）
8. 单机档回归（断言：阶段一全量测试绿；单机档进程不出现任何 `instances` 查询）

**验收 Demo**：M0 可演示成果——拉起 2 副本，`GET /api/v1/instances` 看到两个实例与心跳；误配组合启动即拒并给出恢复指引。

**提示词要点与红线**：明确"这是唯一允许出现档位判定的地方"（装配层 + 启动校验），并给出误配清单的完整枚举，避免 AI 自行增删。
> **红线**：① 不得在 `oryxos.cluster.enabled=false` 时建立数据库连接或启动心跳线程（宪法增补一）；② 误配必须**拒启动**而不是打印 WARN 继续跑（宪法增补四、D11）；③ 心跳/校验不得用异步模型（宪法增补三）；④ 不得把 `instances` 表只写进 PostgreSQL 轨（双轨同版本号，[README.md](README.md) 第 5 章）。

### 4.2 US-2：会话轮次跨副本恰好一次（M1a）

**核心目标**：同一会话的轮次在任意副本上都串行执行、跨副本排队等待、崩溃的轮次**标失败不重放**。这是认领原语最完整的落地，也是后面 US-3 复用的模板。

**涉及模块**：`oryxos-core`（租约认领契约、会话入口的协调层）；`oryxos-storage`（`session_turn_leases` 迁移脚本 + 仓储 + CAS 语句）；`oryxos-boot`（续约调度线程装配）；`oryxos-web` / 渠道模块（排队与超时的对外语义，不改既有端点的形状）。

**Spec-Kit 任务拆分思路**：US-2 拆解的关键是**先契约、后实现、再并发验证**。预期 task 类别：契约类（认领 / 续约 / 释放 / 接管，`contracts/` 一份独立 md）；实现类（`session_turn_leases` 表 + 插入式认领 + 抢占式认领）；续约类（TTL 60s / 续约 20s，同步阻塞）；排队类（跨副本等待与超时上限 120s，含到点后的用户可见行为）；崩溃语义类（接管"先标失败"顺序）；审计类（`instance_id`）；测试类（3 副本并发同会话 + 单机档回归）。

**关键 task 颗粒度**：
1. 定义租约认领契约与 `contracts/` 契约文档（断言：契约测试可针对接口跑，实现未写时测试红）
2. 写 `session_turn_leases` 迁移脚本（断言：`session_id` 为持有者维度、列名与枚举对齐 [README.md](README.md) 第 5 章）
3. 实现插入式认领（断言：并发 N 次认领仅 1 次成功；N-1 次返回明确的"他人持有"结果）
4. 实现抢占式认领（断言：`expires_at` 已过的租约可被接管，且接管只发生一次）
5. 实现轮询续约线程（断言：持有期间 `expires_at` 持续前移；续约失败立即停止本轮并落 `failed`）
6. 实现跨副本排队等待与超时（断言：第二副本排队至第一副本完成；超过 120s 返回明确超时语义，不静默丢消息）
7. 实现崩溃接管"先标失败"顺序（断言：接管方先把旧轮次置 `failed` 再开始新轮次；被标失败的轮次**不被重放**）
8. 审计落 `instance_id`（断言：`llm_calls` / `tool_invocations` 每行都有 `instance_id`，与本轮租约持有者一致）
9. 多进程集成测试：3 副本并发打同一会话（断言：回复不重不乱，会话消息顺序单调）
10. 单机档回归（断言：单机档不产生租约语句，既有会话行为逐条不变）

**验收 Demo**：Demo A（升级期间消息有且仅有一次回复）与 Demo B（崩溃轮次标失败不重放、租约过期后 ≤ 60s 接管）的核心判据都由本 US 承担。

**提示词要点与红线**：要求 AI **先写契约测试再写实现**，并明确"认领必须是单条带条件写语句"。
> **红线**：① 禁止 `SELECT` 后再 `UPDATE`（宪法增补二）；② 禁止用应用时钟 / 墙钟判断过期；③ 续约禁止用 `CompletableFuture` / 定时线程池异步回调（宪法增补三）；④ 接管顺序必须是"先标失败、再开新轮次"（D6）；⑤ 禁止把租约逻辑写进 `ReActLoop`（协调在会话入口，不在循环体）。

### 4.3 US-3：定时与入站回执恰好一次（M1b）

**核心目标**：定时任务到点跨副本恰好执行一次（幂等键取理论触发时刻）；入站渠道事件回执去重从进程内 Map 换成共享状态层，同一条事件只处理一次。

**涉及模块**：`oryxos-core`（`AgentScheduler` 的认领锚点、`InboundMessageService` 的去重抽象）；`oryxos-storage`（`schedule_claims`、`event_receipts` 迁移脚本 + CAS）；渠道模块（飞书 / 企微 / 钉钉，替换进程内去重 Map 的接入点）；`oryxos-web`（`task_executions` 增 `instance_id` 与 `fire_time` 后的可查口径）。

**Spec-Kit 任务拆分思路**：US-3 是"同一套认领原语换两个幂等键"，拆解重点是**幂等键的取值来源**与**两个场景的边界差异**（定时是"到点必须有一次"，事件是"重复到达必须只处理一次"）。预期 task 类别：
认领原语复用类（把 US-2 的 CAS 语句抽为可复用形式）；定时幂等类（`(schedule_id, fire_time)` 唯一、`fire_time` 取 `CronTrigger` 理论触发时刻、`state` ∈ {`claimed`, `running`, `succeeded`, `failed`, `skipped`}，其中 `skipped` 只由认领成功方按 misfire 策略写入）；定时认领类（TTL 120s、**抢不到即放弃且不写任何行**，不重试、不等待）；回执去重类（`(channel, event_id)` 唯一、保留窗口 24h、过期清理在调度线程同步执行）；审计类（`task_executions` 增 `instance_id`、`fire_time`）；测试类（3 副本触发计数、同事件重复投递、单机档回归）。

**关键 task 颗粒度**：
1. 抽取可复用的认领语句构造（断言：US-2 与 US-3 共用同一实现，语句形状一致）
2. 写 `schedule_claims`、`event_receipts` 迁移脚本（断言：唯一约束与列名对齐 [README.md](README.md) 第 5 章）
3. 实现定时认领与理论触发时刻取值（断言：3 副本算出的 `fire_time` 完全相同；注入时区/夏令时用例不漂移）
4. 实现"抢不到即放弃"（断言：每个 `fire_time` 恰好 1 行 `task_executions`；落败副本**不写** `schedule_claims`、**不写** `task_executions`、不执行任务体）
5. 实现事件回执去重（断言：同一 `(channel, event_id)` 重复投递只处理一次；替换进程内 Map 后行为不变）
6. 实现回执过期清理（断言：24h 前的回执被清理，清理不影响新事件去重）
7. 审计补列并核对（断言：`task_executions` 每行带 `instance_id` 与 `fire_time`，可反查是哪个副本执行）
8. 3 副本触发计数测试（断言：人为阻塞一个副本，`fire_time` 仍恰好 1 行）
9. 单机档回归（断言：单机档仍用原有进程内去重，不查 `event_receipts`）

**验收 Demo**：Demo A（升级期间定时任务每个 `fire_time` 恰好一次）与 Demo C（跨副本恰好一次）。

**提示词要点与红线**：明确"幂等键**不是墙钟**"，并点名 `CronTrigger` 的理论触发时刻；明确"**抢不到就放弃，不是等待也不是重试**"；`skipped` **只由认领成功方**按 M1 定稿的 misfire 策略写入。
> **红线**：① 禁止用 `Instant.now()` / `new Date()` 作为 `fire_time`（D5）；② 禁止在去重失败时"顺手重试"——回执去重的语义是丢弃重复；③ 禁止为清理任务引入异步调度（宪法增补三）；④ 禁止改动既有渠道适配器的事件解析行为，只替换去重存储。

### 4.4 US-4：渠道属主与停机链路（M2）

**核心目标**：渠道长连接在全局只有一个属主，**永不互踢**；属主故障后在租约 TTL 内被接管；停机时先释放属主（接管秒级完成，不等 TTL 走完）。

**涉及模块**：`oryxos-core`（渠道属主租约契约、`ChannelAdminService` 的启动/停机编排、`InboundMessageService` 与属主的关系）；`oryxos-storage`（`channel_ownerships` 迁移脚本 + CAS）；`oryxos-channel-feishu` / `oryxos-channel-wecom` / `oryxos-channel-dingtalk`（连接生命周期与限时关闭的既有实现保持不变，只在属主判定后启动）；`oryxos-boot`（装配层决定哪个副本尝试成为属主）。

**Spec-Kit 任务拆分思路**：US-4 的关键不在"抢"而在"不互踢"的时序，以及停机链路的顺序。预期 task 类别：
属主契约类（获取 / 续约 / 释放 / 只允许过期后接管）；状态表类（`channel_ownerships`：`channel_name` 主键、`owner_instance_id`、`lease_id`、`acquired_at`、`expires_at`、`last_renew_at`）；获取类（未抢到则本副本该渠道不建连接、静默待命）；续约类（10s / TTL 30s，同步阻塞）；接管类（仅在 `expires_at` 已过后接管，接管前让旧连接走完停机链路）；停机类（`stopAll` 先释放属主再限时关闭长连接）；治理类（能查到当前属主与租约到期时间）；测试类（多副本同渠道启动、kill 属主接管、停机不超时、单机档回归）。

**关键 task 颗粒度**：
1. 定义属主租约契约与 `contracts/` 契约文档（断言：契约测试针对接口可跑）
2. 写 `channel_ownerships` 迁移脚本（断言：`channel_name` 维度唯一、列名对齐 [README.md](README.md) 第 5 章）
3. 实现启动获取属主（断言：3 副本同时启动时仅 1 个成为属主，另 2 个不建立渠道连接）
4. 实现属主续约（断言：`last_renew_at` 与 `expires_at` 持续前移；续约失败的副本主动停止本渠道服务而不是继续持有僵尸连接）
5. 实现"仅过期后接管"（断言：未过期时接管尝试失败且**不触碰**现有连接；过期后接管成功且旧属主未产生重复回复）
6. 实现停机先释放属主（断言：SIGTERM 后租约被显式释放，接管方**不等 TTL** 即可接管）
7. 核对 `stopAll` 的限时关闭不退化（断言：整条停机链路在 `spring.lifecycle.timeout-per-shutdown-phase`（10s）内完成，Pod `terminationGracePeriodSeconds`（40s）内退出）
8. kill 属主接管测试（断言：`kill -9` 后 TTL（30s）内接管，渠道不互踢、无重复回复）
9. 单机档回归（断言：单机档不查 `channel_ownerships`，启动即建连接，停机行为与阶段一一致）

**验收 Demo**：Demo B（渠道属主在 TTL 内被接管、不互踢、不双回复）。

**提示词要点与红线**：把"**永不互踢**"写成显式约束并解释 IM 平台侧行为（同渠道多连接可能互相踢到全部掉线，D10），让 AI 理解为什么不能"重连探活"。
> **红线**：① 禁止在接管前重启或新建连接（接管的前提是旧连接已走完停机链路）；② 禁止把属主判定塞进渠道适配器内部，判定必须在编排层（宪法增补一）；③ 禁止在 `stopAll` 里**阻塞等待**长连接优雅关闭——既有实现是限时 join（守护线程 + 超时放弃等待），这个纪律必须保持；④ 禁止新增"属主选举"式的新机制（只有 CAS 租约，宪法增补二）。

### 4.5 US-5：共享工作区与版本号总线（M3）

**核心目标**：`.oryxos/` 工作区放共享卷，多副本共享同一份工作区数据；变更按版本号总线轮询传播（P99 ≤ 3s）；一切写入原子落盘；本机执行视图正确；管理写互斥预约与逃生舱可用。

**涉及模块**：`oryxos-core`（`WorkspaceStorage` / `WorkspaceStorageProvider` 契约、`nativePath` 语义、域枚举 agents/skills/personas/knowledge/channels/bootstrap）；`oryxos-storage` / 存储插件模块（本地实现 + 共享实现；`AtomicFiles` 原子改名落盘）；`oryxos-tool`（`FileTools`、`ShellTools` 改用存储抽象与本机执行视图）；`oryxos-knowledge`、`oryxos-persona`（落盘路径改走原子写入）；`oryxos-web`（`POST /api/v1/workspace/refresh` 逃生舱、管理写预约端点）；`oryxos-boot`（启动校验 `.workspace-id`、集群档不装 watcher）。

**Spec-Kit 任务拆分思路**：US-5 是 7 个 US 里范围最宽的一个，涉及"存储抽象 + 原子落盘 + 变更感知 + 执行视图 + 两个运维闸门"五件事。拆解上按**先抽象、再落盘、再感知、最后闸门**的顺序。预期 task 类别：
存储抽象类（`WorkspaceStorage` 契约、`WorkspaceStorageProvider.id()` 显式选择、启动校验 `.workspace-id`）；原子落盘类（`AtomicFiles`：临时文件 + rename；多文件发布只承诺可恢复）；保留路径类（`.workspace-*` 与 `.staging` 内部保留、运行输出按 Agent/run 隔离）；变更感知类（`workspace_versions` + 各副本 1s 轮询 + 落后即重载域）；执行视图类（文件 / Shell Tool 走 `nativePath`，软连接校验用真实路径）；闸门类（`admin_write_reservations` 管理写预约 + 逃生舱端点）；隔离类（集群档不装 `WatchService`，单机档 watcher 零回归）；测试类（传播延迟 P99 ≤ 3s、直接改盘 + 逃生舱、存储矩阵、单机档回归）。

**关键 task 颗粒度**：
1. 定义 `WorkspaceStorage` / `WorkspaceStorageProvider` 契约（断言：契约测试可用本地实现通过；plugin 以 id 显式选择）
2. 实现共享模式启动校验（断言：`.workspace-id` 缺失或不匹配时拒绝启动并给恢复指引；**不初始化、不回退本地**）
3. 实现 `AtomicFiles` 原子改名落盘（断言：并发读不会读到半成品文件；rename 前后内容一致）
4. 写 `workspace_versions` 迁移脚本 + bump 逻辑（断言：agents / skills / personas / knowledge / channels / bootstrap **六个域**各域落盘后对应 `version` 单调递增）
5. 实现轮询重载（断言：一个副本改 `AGENT.md` / 绑 Skill，其余副本按 1s 轮询在 P99 ≤ 3s 内生效）
6. 改造文件 / Shell Tool 用 `nativePath`（断言：共享卷下读写落在共享卷；本机执行视图指向真实可执行路径）
7. 收紧软连接校验为真实路径（断言：越界软连接被拒；用逻辑路径校验的旧实现有反例测试覆盖）
8. 实现管理写互斥预约（断言：预约期间其他副本的管理写被拒；预约不自动过期；释放后恢复可写）
9. 实现逃生舱 `POST /api/v1/workspace/refresh`（断言：直接改盘后调用即强制重载，不依赖版本号变化）
10. 核对保留路径与运行输出隔离（断言：`.workspace-*`、`.staging` 被拒绝写入；运行输出按 Agent/run 隔离）
11. 存储矩阵冒烟 + 单机档回归（断言：本地目录/NFS/云盘 RWX 三格冒烟通过；单机档 watcher 行为不变）

**验收 Demo**：Demo D（变更 P99 ≤ 3s 生效、知识重建只执行一次）与 Demo E（逃生舱生效、实例视图与审计口径一致）的工作区部分。

**提示词要点与红线**：把 042 的四条硬约束原文喂给 AI（存储抽象 / `nativePath` / `.workspace-id` / 保留路径），并要求它**逐条**在 plan 里落位。
> **红线**：① 禁止裸文件 API 与 `Path.of`（宪法增补五）；② 禁止集群档装配 `WatchService`（D8）；③ 禁止把 `.workspace-*`、`.staging` 当业务目录；④ 禁止声称"多文件发布是目录原子快照"（只能写"可恢复"）；⑤ 禁止让共享模式在校验失败后回退本地（D9）。

### 4.6 US-6：知识库代次化（M4）

**核心目标**：知识索引重建在多副本下只执行一次（冲突方排队不丢），检索**恒读已提交代次**，重建期间旧代次继续服务不断服。

**涉及模块**：`oryxos-core`（知识后端契约与代次契约，沿用阶段一依赖倒置的放置方式）；`oryxos-knowledge`（索引构建流水线、代次切换、检索读取路径）；`oryxos-storage`（`knowledge_build_claims`、`knowledge_generations` 迁移脚本 + CAS；`ChunkStore` 的代次列）；`oryxos-web`（重建端点的 409 / 排队语义）。

**Spec-Kit 任务拆分思路**：US-6 是把 US-2 的认领原语用在"长耗时任务"上，额外引入**代次**概念。拆解重点是"构建与检索的解耦"与"导入与重建的互斥"。预期 task 类别：
认领类（`knowledge_build_claims`：`(backend, scope)` 认领、TTL 30min / 续约 5min、冲突方 409 + 排队）；代次类（`knowledge_generations`：`state` ∈ {`building`, `committed`, `retired`}、`chunk_count`、保留代次 2）；检索类（恒读 `committed` 代次，`building` 对检索不可见）；提交类（先提交新代次、再退役旧代次，切换瞬间不断服）；互斥类（导入索引段与重建同认领互斥、排队不丢）；崩溃类（TTL 到期可接管，半成品代次标废弃而非续跑）；测试类（多副本同时触发、检索全程可用、单机档回归）。

**关键 task 颗粒度**：
1. 写两张表迁移脚本（断言：`(backend, scope)` 唯一、代次枚举与列名对齐 [README.md](README.md) 第 5 章）
2. 实现重建认领（断言：多副本同时触发只有一个进入 `building`，其余返回 409 并排队）
3. 实现认领续约与崩溃接管（断言：TTL 30min 到期后可接管；半成品代次被标记废弃而非继续写入）
4. 实现代次写入与提交（断言：`building` → `committed` 单向；提交后代次对检索可见）
5. 改造检索读取路径（断言：检索只读 `committed` 代次；构建期间检索返回旧代次结果且不报错）
6. 实现代次保留与退役（断言：保留 2 个代次，更早的 `retired` 并被清理）
7. 实现导入与重建互斥（断言：并发导入 + 重建只有一方执行，另一方排队，**不丢**）
8. 多副本重建 + 检索连续性测试（断言：重建全程检索成功率 100%，结果来自已提交代次）
9. 单机档回归（断言：单机档仍走阶段一的索引路径，不查代次表）

**验收 Demo**：Demo D（多副本同时触发重建只有一个执行、冲突方排队不丢、检索全程读已提交代次不断服）。

**提示词要点与红线**：明确"**检索与构建解耦**"是硬要求（重建期间不许停服、不许降级为关键词兜底），并给出代次状态机的单向性。
> **红线**：① 禁止让检索读到 `building` 代次；② 禁止用文件锁 / watcher 感知重建（D7、D8）；③ 禁止把"排队"实现成"静默跳过"（冲突方要么 409、要么排队，不能丢请求）；④ 禁止把索引段写入与重建拆成两个互不互斥的路径。

### 4.7 US-7：容器交付与验证（M5）

**核心目标**：把前面 6 个 US 的成果装进企业现有的 K8s 治理流程——官方 Helm Chart 装机即用、探针正确、滚动升级零丢失、量级目标可复现、HA 演练有记录。

**涉及模块**：`charts/oryxos/`（官方 Helm Chart：values、模板、README）；`oryxos-boot`（探针端点、优雅停机配置、OTel 可选导出装配）；`oryxos-core` / `oryxos-web`（`SpanRecorder` 契约与探针语义的既有面，原则上只接线不改形状）；CI / `Makefile`（Helm 门禁与 kind 冒烟 job）。

**Spec-Kit 任务拆分思路**：US-7 的"代码量"最小但门禁最密，拆解上按**chart 结构 → 密文与探针 → 停机与滚动 → 观测 → 验证**推进。预期 task 类别：
Chart 基础类（`charts/oryxos/` 结构、`values.yaml`、lint / template / kubeconform 门禁）；密文与配置类（必填仅两项密文引用、集群档默认开）；工作区类（RWX PVC 挂载、管理员预置 `.workspace-id`、非 root uid 1000 权限一致）；探针类（liveness / readiness，readiness 含数据库）；停机类（`preStop` + grace 40s + phase 10s）；滚动类（`maxUnavailable: 0` / `maxSurge: 1`）；观测类（OTel 可选导出、不配零开销、审计与日志 `instance_id` 口径一致）；验证类（kind 安装冒烟、固定时延 mock provider 压测、HA 演练、Demo A–E 复现说明）。

**关键 task 颗粒度**：
1. 建 Chart 骨架并通过门禁（断言：`helm lint` + `helm template` + kubeconform 无错）
2. 接通两项密文引用（断言：charts 里没有明文密钥；缺密文时 Pod 启动失败而非静默使用默认值）
3. 配置共享工作区挂载与非 root 权限（断言：Pod 以 uid 1000 运行并能读写 RWX PVC；`.workspace-id` 校验通过）
4. 配置探针（断言：数据库不可用时 readiness 不通过；进程僵死时 liveness 触发重启）
5. 配置停机链路（断言：SIGTERM 后先释放渠道属主、在途请求排空、Pod 在 40s 内退出）
6. 配置滚动策略（断言：`maxUnavailable: 0` / `maxSurge: 1` 下升级期间可用副本数不下降）
7. 接通 OTel 可选导出（断言：不配 endpoint 时零开销且不报错；配置后 turn/llm/tool 三 span 与审计同 traceId、同计时区间）
8. kind 安装冒烟 job（断言：3 副本起来、`GET /api/v1/instances` 看到 3 条、误配镜像启动失败）
9. 压测（断言：单副本 ≥ 50 消息/秒、2→4 副本加速比 ≥ 0.8、变更传播 P99 ≤ 3s、属主接管 ≤ 30s、轮次接管 ≤ 60s，全部标注 mock provider 口径）
10. HA 演练 + Demo A–E 复现说明（断言：随机 kill 副本期间消息不丢不重；五个 Demo 有可复现步骤）

**验收 Demo**：Demo A（滚动升级零中断）、Demo D、Demo E 全量，以及压测报告（加速比、传播延迟、接管时间）。

**提示词要点与红线**：明确"**chart 的必填项只有两项密文**"，其余全部有默认值；明确"readiness 必须含数据库"。
> **红线**：① 禁止把明文密钥写进 `values.yaml` 或模板（022 的原生面是环境变量）；② 禁止把镜像内路径当成本机执行视图（工作区在 RWX PVC 上，宪法增补五仍成立）；③ 禁止用 `maxUnavailable > 0` 换取升级速度；④ 禁止在 chart 里替用户做数据迁移动作（迁移由 Flyway 在启动时完成）；⑤ 禁止把阶段三的 A2A 或跨组织联邦写进交付范围。

### 4.8 跨 user story 的协作要点

7 个 US 的实施过程中有几个跨 US 的纪律，与阶段一的"每 US 跑 analyze"一脉相承但更重：

| 要点 | 做法 |
|------|------|
| 认领原语只在 US-2 做一次 | US-3 / US-4 / US-6 复用同一实现，**不允许各自实现一套 CAS**；发现第二套立刻回退 |
| 每个 US 结束跑 `/speckit.analyze` | 检查 constitution（含增补 5 条）+ spec + plan + tasks + 代码一致性，**不能省** |
| 每个 US 结束跑单机档全量回归 | brownfield 的硬约束；回归红则本 US 不算完成，不许"下一个 US 一起修" |
| 每个 US 结束做一次 git commit 打标 | 便于随时回到"单机档可用 + 已完成的集群能力"这个稳定点 |
| 跨 US 上下文断裂时回到 spec | 开新 US 前让 AI 重读 `spec.md` + `plan.md` + constitution 增补 + 最近代码 |
| 表名 / 列名 / 枚举只在 README 第 5 章定义 | 任何新表都要对齐该章；发现不一致以 README 为准并回写代码 |
| 默认参数只在 README 第 6 章定义 | TTL / 间隔 / 等待上限一律取统一默认参数表的配置项名与数值，不在代码里发明第二套 |

> **注意**：4.2 ~ 4.7 的 task 样例是**拆解颗粒度的示范**，不是 task 全量清单。`/speckit.tasks` 生成的 `tasks.md` 通常比这里更细；review 时用这里的颗粒度做**下界检查**——如果某个 task 描述的是"实现 XX 模块"而不是"某行为可被断言"，说明拆得不够细。

## 6. 增量阶段：手动提示词模式

### 6.1 为什么需要它

集群档上线之后，工作性质会变。主体阶段是"把能力建出来"，上线后是"把参数和边界调准"：

| 工作类型 | 典型例子 | 为什么不适合 Spec-Kit |
|---------|---------|---------------------|
| **TTL / 间隔调优** | 会话轮次租约 60s/20s 在某企业网络下太紧导致接管频繁；渠道属主 30s/10s 需要调整 | 改动是配置默认值与一处判定，跑一次完整 specify → plan → tasks 开销大于改动本身几十倍 |
| **存储矩阵适配** | 某企业用 CIFS 而非 NFS，rename 语义或可见性延迟与预期不同，需要调轮询或落盘实现 | 问题只在真实环境暴露，spec 里描述不清；需要"改一处 + 在真实卷上验一次"的循环 |
| **真实环境竞态排查** | 只在客户现场偶发的重复回复、接管风暴、版本号不动 | 上下文极强（日志 + 审计行 + 卷行为），必须人机来回对话定位，不是规格驱动 |
| **单点修补** | 审计漏 `instance_id`、误配校验漏了一种组合、逃生舱没生效 | 小颗粒度、已有代码上下文清晰，改完双档测试即可 |

> **判据**：改动如果**需要新的用户可见行为**，走 Spec-Kit；如果只是**让既有行为在更多环境/参数下正确**，走手动提示词。两者都不允许跳过 6.3 的不变量清单。

---

### 6.2 Brownfield 单点改造的工作流

手动提示词不等于"随手改"。brownfield 单点改造走固定五步，每步都有"不能省"的理由：

1. **读契约与档位判断**。先读本次要碰的契约文件（`contracts/` 下对应那份）、该模块的档位判定位置、以及 constitution 增补 5 条。
   *不能省*：AI 在有上下文时会自己发明一致但错误的用法（例如直接 `Path.of`）；先把契约摆在对话里，等于先给它划边界。
2. **改一处**。一次提示词只改一个关注点，不允许"顺手把这个也优化了"。
   *不能省*：brownfield 的返工成本主要来自"改了三处，不知道哪处导致的回归"；单点改动才能把回归定位到行。
3. **双档测试**。单机档（`oryxos.cluster.enabled=false`）全量回归 + 集群档（≥ 2 副本）针对性验证，两档都跑才允许提交。
   *不能省*：单机档零回归是阶段二的硬约束（宪法增补一）；只跑集群档等于把回归风险留给默认部署。
4. **审计与 traceId 核对**。确认本次改动涉及的调用仍落审计行、带 `instance_id`、`trace_id` 与前后的 span 不断链（D13）。
   *不能省*：审计是 OryxOS 的核心差异化能力（阶段一原则五）；接错一行会静默丢链路，只有主动核对才能发现。
5. **更新文档**。改动回写 `tasks.md` / `spec.md`（一致性检查用，见 6.4）；涉及默认参数、表结构、存储矩阵的改动同时更新对应文档。
   *不能省*：这些文档是下一个改动的上下文来源；不回写，下一个人（或下一轮 AI）就会基于过期信息做决定。

> **注意**：第 3 步是五步里最容易被压缩的。真实环境竞态排查往往在客户现场，压力下容易"先改了验证一下"。**任何一次改动，双档测试记录都要留痕**（至少写清两档各自跑了什么、结果如何），否则不能合并。

### 6.3 每次改动必须验证的不变量清单

以下 16 条是**每次改动都要过一遍**的检查项，与 3.5 的 review checklist 互补：3.5 检查 plan（设计层），本清单检查改动（代码层）。

| # | 不变量 | 怎么验 |
|---|--------|-------|
| 1 | 单机档零回归：`oryxos.cluster.enabled=false` 路径不新增协调调用 | 单机档全量回归绿；`git diff` 里单机档执行路径无新增查询/线程 |
| 2 | 未引入异步模型 | 不出现 `CompletableFuture` / Reactor / WebFlux / 异步重试框架（宪法增补三） |
| 3 | 无裸文件 API | 不出现 `Path.of`、`FileInputStream`、`Files.*` 直接作用于工作区路径（宪法增补五、042） |
| 4 | 工作区访问走存储抽象 + 本机执行视图 | 只用 `WorkspaceStorage.root()/resolve()`；本机执行取 `nativePath` |
| 5 | 审计不漏且带 `instance_id` | 本次涉及的 `tool_invocations` / `llm_calls` / `task_executions` 行都有 `instance_id`（D13、原则五） |
| 6 | traceId 不断链 | 一次消息处理的审计行、日志、span 同 `traceId`；跨副本可拼回同一条链路 |
| 7 | 误配仍拒启动 | 新增配置组合后重跑误配矩阵：启动误配 **7 类**（SQLite 档 / markdown 记忆后端 / 内存知识后端 / `oryxos.workspace.storage=local` / 工作区标识缺失或不匹配 / 主密钥缺失或跨副本不一致 / 实例标识重复）仍 fail-closed，另加**运行期 fail-closed 1 类**（数据库不可用拒服务、不降级为单机）（宪法增补四、D11） |
| 8 | 留痕不泄露密钥 | 日志、审计、报错文案里不出现明文 key / 主密钥；敏感项走 `enc:v1:` 加密面（022） |
| 9 | TTL 不写死、参数来自统一默认参数表 | 改动涉及的 TTL / 间隔 / 等待上限与 [README.md](README.md) 第 6 章配置项名与数值一致；**改默认值必须同步 README 统一默认参数表与 TechnicalSolution 第 3 章（集群开关与配置面）**，不得只改代码默认值 |
| 10 | 无新增中间件 | 不引入 Redis / ZooKeeper / etcd / 消息队列；协调基质仍只有 PostgreSQL + 共享卷（D2、D14） |
| 11 | 无阶段三内容渗入 | 不出现跨节点 Agent 协作 / A2A / 多活 / 多主 / 冲突合并（D14） |
| 12 | 迁移脚本只增不改 | 新变更用新版本号；两 vendor 同版本号各一份；既有版本号文件未被修改 |
| 13 | 表名 / 列名 / 状态枚举与 README 第 5 章一致 | 新增或改动的列名、枚举值逐字比对 README 第 5 章；有偏差以 README 为准并回写代码 |
| 14 | `.workspace-*` 与 `.staging` 未被占用 | 新增路径不落入保留前缀；运行输出按 Agent/run 隔离（042） |
| 15 | 认领仍是 CAS 单语句 + TTL 租约 | 改动涉及的互斥不看"先查后写"；过期判定不用应用时钟（宪法增补二、D4） |
| 16 | "恰好一次"的承诺未被扩大 | 只在五个粒度上承诺（会话轮次 / 定时触发 / 入站事件 / 渠道属主 / 知识重建）；审计落库与通知推送仍表述为"至少一次 + 幂等键"（D3） |

> **注意**：第 9 与第 13 条是**同步义务**，不是"最好也做"。只改代码不改 README / 技术方案，会让四篇文档与实现各说一套，下一个改动就会以过期口径为前提。

### 6.4 跟主体阶段 Spec-Kit artifacts 的对接

手动提示词的改动**必须回写 artifacts**，否则 Spec-Kit 的 artifacts 会在几周内变成历史遗迹，下一次跑 `/speckit.analyze` 会报出大量"实现漂移"却无法区分哪些是合理演进。

| 改动类型 | 回写位置 | 检查方式 |
|---------|---------|---------|
| 行为语义变化（例如排队超时后的用户可见行为） | `spec.md` 对应 user story 的行为陈述 | `/speckit.analyze` 看 spec 与代码是否一致 |
| 契约变化（认领原语的语义、存储抽象的方法） | `contracts/` 下对应那份契约 md + `plan.md` 契约清单 | `/speckit.analyze` |
| 新增/调整的默认参数 | [README.md](README.md) 统一默认参数表 + TechnicalSolution 第 3 章（集群开关与配置面）与第 13 章（数据持久化增量） + `plan.md` | 人工逐项比对；参数表是唯一口径 |
| 表结构变化（列、枚举、索引） | `data-model.md` + [README.md](README.md) 第 5 章 | 人工逐项比对 |
| 尚未落地但已确认要做的工作 | `tasks.md` 追加条目 | `/speckit.converge` |

两个命令的用法思路：

- **`/speckit.analyze`**：非破坏性的一致性检查，看 spec / plan / tasks 与当前代码之间的偏差。用途是**定位漂移点**（例如：constitution 增补一要求单机档零协调调用，但代码里有一段只在集群档分支里……），发现后人工判断是"实现错了"还是"spec 过期了"，再决定改哪边。**不要用 analyze 的输出去直接改代码**。
- **`/speckit.converge`**：把当前代码与 spec/plan/tasks 的差距**追加成新 task**，让后续 `/speckit.implement` 能把剩下的工作做完。用途是**把手动提示词阶段确认的剩余工作重新纳入 Spec-Kit 流程**——适合某一批修补累计到一定规模、值得回到规格驱动的时候。

> **切换判据**：手动提示词改动的**累计规模**到达"需要新契约或影响两个以上 user story"时，不要继续用提示词堆，回到 `/speckit.specify` 或 `/speckit.converge` 重新进入主体流程。手动提示词是给单点用的，堆多了就失去了它的成本优势。

## 7. 风险和注意事项

### 7.1 Spec-Kit 在阶段二暴露的局限

| # | 局限 | 表现 | 应对 |
|---|------|------|------|
| 1 | **并发正确性无法由 spec 保证** | spec 写"同一会话恰好一次"，AI 实现成先查后写也能宣称"符合 spec"；单机档测试全绿，3 副本并发下偶发双回复 | 认领原语**先写契约测试再写实现**（断言"并发 N 次仅 1 次成功"）；强制多进程集成测试（3 副本并发同会话）；把"语句形状（单条 CAS）"写进 `contracts/` 契约文，让实现层有可比的对照物 |
| 2 | **共享存储行为无法在单机 CI 复现** | 本地目录上 rename 原子、watcher 可靠；到 NFS / 云盘 RWX 上出现半成品读取、变更不传播 | 建**存储矩阵冒烟**（本地 / NFS / 云盘 RWX）；真实卷做少量关键回归；集群档不装 watcher（D8）；一切写盘走 `AtomicFiles` 原子改名 |
| 3 | **跨模块契约漂移** | 四个 US 各自实现一套认领语句；表名/列名/枚举在代码与 README 第 5 章之间分叉；默认参数各写一套 | 认领原语只在 US-2 落地、其余复用；表名/列名/枚举以 [README.md](README.md) 第 5 章为唯一真相源；TTL 等数值以第 6 章统一默认参数表为唯一真相源；每 US 结束跑 `/speckit.analyze` |

三条局限的共同点是：**都在编译期和单机 CI 里看不见**。所以阶段二把"多副本演练 + 存储矩阵 + 契约比对"当作与单元测试同级甚至更重的验证手段。

### 7.2 AI 最容易写错的点

下面 15 条是阶段二最可能被 AI 写错的地方。每一条都在阶段一有过"对称"的坑（例如阶段一的"审计表没落库"），在阶段二换了个形态再次出现。

| # | 症状 | 后果 | 正确做法 | 决断 |
|---|------|------|---------|------|
| 1 | 租约续约写成异步（`CompletableFuture` / 异步定时器 / 回调链） | 异常被吞导致租约静默过期、接管风暴；无法直接观察"续约到底在不在跑" | 续约在调度线程上**同步阻塞**循环，失败立即停止本轮并落 `failed` | 增补三 / 原则七 |
| 2 | 把"我是不是集群档"的判断渗进 core 主链路（`ReActLoop` / `PromptBuilder`） | 单机档凭空多出分支与依赖，主链路被协调语义污染，回归面不可控 | 档位判定收敛在装配层与启动校验；core 循环体不认识"集群" | D1 / 增补一 |
| 3 | 认领用"先 `SELECT` 再 `UPDATE`" | 竞态窗口内两个副本同时认为自己持有：双回复、定时重复执行、渠道互踢 | 单条带条件写语句（CAS）或以受影响行数判定成功 | D4 / 增补二 |
| 4 | 用应用时钟（`Instant.now()`）判断租约过期 | 多副本墙钟漂移时误判：过早抢占造成双写，或永不过期造成永久卡死 | 过期判定用数据库时钟 / 单调时钟 | D4 |
| 5 | 用墙钟做定时幂等键 | 各副本算出不同的键，唯一约束失效，定时任务重复执行 | 幂等键取 `CronTrigger` 的**理论触发时刻**，落 `(schedule_id, fire_time)` 唯一 | D5 |
| 6 | TTL 到期直接重跑，而不先标失败 | 重放已产生外部副作用（发过消息、调过工单）的轮次，造成重复副作用 | 接管时**先标 `failed` 再开新轮次**；崩溃轮次不重放，由用户重发恢复 | D6 |
| 7 | 集群档还装配 `WatchService` watcher | 共享卷上事件丢失或跨节点不可见，变更不传播且难以察觉 | 集群档不装 watcher，变更感知只走 `workspace_versions` 轮询 + 逃生舱 | D8 |
| 8 | 裸 `Path.of` 绕回默认存储 | 写入本机磁盘而非共享卷，多副本数据分裂 | 一律 `WorkspaceStorage.root()/resolve()`；插件以 `id` 显式选择 | D9 / 042 / 增补五 |
| 9 | 忘记 `nativePath`（把逻辑路径当文件路径用） | 本机执行失败或落到错误位置；共享模式下逻辑路径不可直接执行 | 本机执行视图（文件 Tool、Shell Tool）必须取 `nativePath` | D9 / 042 |
| 10 | 误配校验漏了"内存知识后端"或"markdown 记忆后端" | 集群档静默用各副本本地存储，故障几天后以数据分裂暴露 | 启动校验矩阵覆盖 **7 类**（SQLite 档、markdown 记忆后端、内存知识后端、`oryxos.workspace.storage=local`、工作区标识缺失或不匹配、主密钥缺失或跨副本不一致、实例标识重复），另有运行期 fail-closed 1 类（数据库不可用拒服务） | D11 / 增补四 |
| 11 | 审计漏 `instance_id` | 跨副本链路无法拼回一条，审计失去定位能力 | `tool_invocations`、`llm_calls` 加 `instance_id`；`task_executions` 加 `instance_id` 与 `fire_time` | D13 / 原则五 |
| 12 | 软连接校验用逻辑路径 | 越界链接漏检，Agent 可读到白名单之外的内容 | 存在目标用 `toRealPath()` 校验真实路径仍位于白名单根；新建路径校验最近存在父目录的真实路径 | 原则六 |
| 13 | 依赖 `hibernate.ddl-auto=update` 改表 | SQLite 侧 ALTER TABLE 报错、双轨迁移序列断裂、history 表失去恰好一次保证 | 写 Flyway 迁移脚本（`db/migration/{vendor}/` 双轨各一份、同版本号、只增不改），`ddl-auto` 保持 `none` | 阶段一迁移纪律 / README 第 5 章 |
| 14 | `channel stopAll` 里**阻塞**关闭长连接 | 停机拖满 grace period，滚动升级期间副本不可用窗口被拉长甚至超时被 kill | 长连接限时关闭（守护线程 + 超时放弃等待），先释放渠道属主租约再关闭；停机链路由 `spring.lifecycle.timeout-per-shutdown-phase`（10s）兜底 | D10 / D12 |
| 15 | 共享卷上多副本首启并发生成主密钥，导致密钥不一致 | 各副本用不同主密钥加密同一批数据，落库凭证互相解不开，故障在重启后才暴露 | 集群档**必须**由环境变量提供主密钥（K8s Secret → 环境变量）；缺失即拒启动；首启自动生成仅适用于单机档 | D11 / 022 |

> **注意第 15 条**：这是最隐蔽的一条——单机档"首启自动生成 `.oryxos/master.key`"是很自然的行为，AI 会原样保留到集群档。集群档下必须把"主密钥来源"变成**必填校验项**，否则密钥不一致的后果（加密字段解不开、启动即拒且无恢复路径）要到很久以后才暴露。

### 7.3 实施过程中的常见挑战

| 挑战 | 表现 | 对策 |
|------|------|------|
| **多副本本地调试难** | 本地起 3 个进程要各自的 `instance-id`、端口、工作区目录，手工起容易串味 | 用 compose / kind 一次性起齐；本地多进程用脚本固定端口与工作区变量；调试单个副本时显式指定 `instance-id` |
| **NFS 环境准备** | 本地没有 NFS/云盘 RWX，存储矩阵的另外两格长期空着 | 用 kind + 集群内 NFS provisioner（或企业已有存储类）跑冒烟；真实云盘做少量关键回归；**不允许因为"环境难搞"就把矩阵缩成一格** |
| **压测环境成本** | 4 副本 + PostgreSQL 高可用的环境占用大，不可能天天压 | 压测只在里程碑（M5 与每个 US 收尾）跑；日常用固定时延 mock provider 做小规模吞吐与传播延迟抽查；报告口径统一到 [README.md](README.md) 第 6 章 |
| **评审者对"恰好一次"的口径误解** | 有人把审计落库、通知推送也当成"恰好一次"，于是对每一条链路都要求去重 | 回到 D3：恰好一次只承诺五个粒度；其余链路明确写"至少一次 + 幂等键"；文档与评审材料统一这个口径 |
| **单机档回归被当成"顺手跑一下"** | 补丁在集群档验完就合并，单机档在下一个版本才炸 | 把单机档全量回归写进每次改动的合并前置条件（6.2 第 3 步、6.3 第 1 条）；CI 上做到默认档必跑 |

## 8. 总结

OryxOS 阶段二的 AI 编程实施分两段，两段的工具分工与阶段一相反：

### 主体阶段（Spec-Kit，7 个 user story）

准备阶段先做一批**手动提示词的档位隔离清理**（把单机档保护起来），再产出 constitution 增补 5 条 + 7 个 user story 的 spec + 含五块必备内容的 plan，然后按依赖关系顺序实施：

```
US-1 → US-2 → ┌─ US-3 ─┐ → US-5 → US-6 → US-7
               └─ US-4 ─┘
（M0）  （M1a）  （M1b）（M2）  （M3）  （M4）  （M5）
```

每个 user story 完成后跑 `/speckit.analyze` 并跑单机档全量回归；每个里程碑结束有可演示成果（M0–M5）。

### 增量阶段（手动提示词 + 不变量清单）

集群档上线后的 TTL 调优、存储矩阵适配、真实环境竞态排查，颗粒度小、上下文强，走"读契约 → 改一处 → 双档测试 → 审计与 traceId 核对 → 更新文档"五步工作流，**每次改动过一遍 16 条不变量清单**，并回写 Spec-Kit artifacts；累计规模变大时用 `/speckit.converge` 重新纳入主体流程。

### 验收口径

阶段二的验收**不是"集群档能起来"**，而是两件事：

1. **Demo A–E 全部可复现**：滚动升级零中断、副本猝死接管、定时跨副本恰好一次、工作区变更传播 + 知识重建认领、运维逃生舱与实例视图（判据见 [README.md](README.md) 第 7 章）。
2. **随机 kill 副本仍然正确**：任意时刻 kill 任意副本（包括渠道属主），消息不丢、不重、不乱；崩溃轮次被标失败而不重放；属主与轮次在 TTL 内被接管。

> **阶段三属于另一层，不在本套文档范围**。跨节点 Agent 协作（A2A、Agent 之间跨实例发现与委托）是在"一组同构实例共享状态"之上再叠一层"Agent 通信底座"，它的前提（共享状态、恰好一次、实例标识与心跳、跨副本可观测）正是阶段二交付的东西。本套四篇文档只覆盖阶段二，不写阶段三的设计，也不把阶段三的需求掺进阶段二的 spec。

### ② 集群档回归清单

**第一层：单机档回归（每次改动必跑）**

- [ ] 阶段一全量测试绿（`oryxos.cluster.enabled=false`，不连 PostgreSQL）
- [ ] 单机档进程不发起任何协调查询（无 `instances` / 租约 / 版本号访问）
- [ ] 单机档不装 watcher 之外的新后台线程；既有 watcher 行为不变
- [ ] 单机档启动不要求工作区标识、不要求主密钥环境变量（沿用首启自动生成）
- [ ] 单机档渠道启动即建连接（不查属主），停机行为与阶段一一致

**第二层：集群档功能回归（每个 US 收尾必跑）**

- [ ] 误配矩阵：启动误配 **7 类**（SQLite 档 / markdown 记忆后端 / 内存知识后端 / `oryxos.workspace.storage=local` / 工作区标识缺失或不匹配 / 主密钥缺失或跨副本不一致 / 实例标识重复）→ 全部拒启动并给恢复指引；运行期 fail-closed **1 类**（数据库不可用）→ 集群档拒服务，不降级为单机
- [ ] 实例视图：`GET /api/v1/instances` 与心跳状态枚举（`starting` / `ready` / `draining` / `stale`）正确
- [ ] 会话轮次：3 副本并发同会话不重不乱；`kill -9` 后 ≤ 60s 接管且崩溃轮次被标 `failed`
- [ ] 定时触发：3 副本下每个 `fire_time` 恰好 1 行 `task_executions`；阻塞一个副本不重复
- [ ] 事件回执：同一 `(channel, event_id)` 重复投递只处理一次
- [ ] 渠道属主：多副本同渠道仅 1 属主；`kill -9` 后 ≤ 30s 接管；停机先释放属主
- [ ] 工作区变更：一个副本改 `AGENT.md` / 绑 Skill，其余副本 P99 ≤ 3s 生效
- [ ] 知识代次：并发重建只执行一次，冲突方 409 排队不丢，检索不断服
- [ ] 审计：`instance_id` 全落；同一次处理跨副本 `traceId` 可拼回
- [ ] 逃生舱：直接改盘后 `POST /api/v1/workspace/refresh` 强制重载生效
- [ ] 交付：滚动升级零消息丢失；Pod 在 grace 内退出

**第三层：存储矩阵（里程碑 + 关键回归时跑）**

| 档位 \ 存储 | 本地目录 | NFS | 云盘 RWX（CIFS 类同） |
|------------|---------|-----|---------------------|
| 单机档 | 必跑（每条提交） | 冒烟 | 冒烟 |
| 集群档 | 必跑（本地多进程 / kind） | 冒烟 + 变更传播 | 冒烟 + 变更传播 |

- [ ] 三格冒烟均通过：启动、写入、变更传播、逃生舱
- [ ] 真实 NFS / 云盘 RWX 各做一次关键回归（变更传播延迟 + 原子落盘 + 知识重建）
- [ ] 矩阵缩格必须有书面理由，不允许默认只跑本地

### ③ 常用校验命令

> 以下命令的**口径以仓库实际存在者为准**（`Makefile` 目标、CI job 名、参数名）；仓库里没有的，先加门禁再引用，**不要凭印象编造命令或参数**。

| 用途 | 命令 / 参数 | 说明 |
|------|------------|------|
| Chart 静态检查 | `helm lint charts/oryxos/`、`helm template charts/oryxos/` | 模板渲染与 lint；具体路径以 chart 落地位置为准 |
| Chart 清单校验 | `kubeconform`（对 `helm template` 的输出） | 校验渲染出的 K8s 清单符合 API schema |
| 安装冒烟 | kind 集群上安装 chart，起 3 副本 | 断言 `GET /api/v1/instances` 返回 3 条；误配镜像启动失败 |
| 滚动升级 | 改镜像 tag 触发 RollingUpdate | 断言升级期间消息零丢失、可用副本数不下降（`maxUnavailable: 0` / `maxSurge: 1`） |
| 压测 | 固定时延 mock provider：`-Doryxos.mock.latency-ms=<毫秒>` | 把 LLM 侧不确定性排除在外，测单副本吞吐与 2→4 副本加速比；报告必须标注该口径 |
| 迁移核对 | 检查 `db/migration/sqlite/` 与 `db/migration/postgresql/` 版本号成对 | 同版本号、只增不改；`hibernate.ddl-auto` 为 `none` |
| 一致性检查 | `/speckit.analyze`、`/speckit.converge` | 每个 US 收尾跑一次；手动提示词改动累计后用 converge 回流 |
| 停机验证 | SIGTERM / `kill`（含 `kill -9` 属主副本） | 断言先释放渠道属主、在途请求排空、Pod 在 `terminationGracePeriodSeconds`（40s）内退出 |

> **注意**：本附录只给"验什么 + 用什么口径"，不给完整命令清单——chart 路径、Makefile 目标名、CI job 名在实施时确定。任何校验命令一旦确定，就应写进 `quickstart.md` 与 CI，而不是留在文档里当参考。
