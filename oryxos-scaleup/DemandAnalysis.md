## 1. 项目概述

### 1.1 阶段二是什么

阶段一交付的是**单机运行时内核**：一个 OryxOS 实例，装在企业自己的一台服务器或一个容器里，跑起一组 Agent，服务一个部门或一个场景。用一句话概括阶段一的成果——**它让"一个实例跑好一群 Agent"这件事成立**。

阶段二要解决的是阶段一刻意没有解决的问题——**让"一组实例共同跑好一群 Agent"，对外表现成同一个 OryxOS**。用户的接入方式不变、Agent 目录的写法不变、REST API 的语义不变；变的是这些请求不再注定落在同一个进程里。

单实例在"从部门试点走向全公司"的路上会同时撞上三件事：

| 撞上的事 | 具体表现 | 阶段一为什么没解决 |
|---------|---------|------------------|
| **扛不住量** | 全公司的 IM 消息、多个部门的定时任务、上百个 Agent 挤在一个进程的线程池与连接池里；一个实例的吞吐决定全公司的上限 | 阶段一的目标是跑通最短链路，没有容量模型，也没有"加机器就加容量"的路径 |
| **扛不住故障** | 进程崩溃 = 全部会话中断、全部渠道长连接掉线、正在跑的轮次半途而废；升级一次就是一次计划内停机 | 单进程即单点，状态（会话、定时状态、知识索引）与进程同生共死 |
| **扛不住规模化治理** | 多个部门共用同一份工作区与知识库，配置变更、定时任务、索引重建、运维直接改盘这些动作在单实例上靠"只有一个进程"侥幸成立，一旦多进程就变成重复执行、互相覆盖、双属主 | 阶段一的互斥手段是进程内的（进程内 Map、单进程内存状态、文件 watcher），跨进程不成立 |

阶段二的做法不是给 OryxOS 加一套新的架构，而是**把阶段一刻意留在进程内的那部分状态搬出去**，搬到一组实例共读写的存储面上，再用最小的一组协调原语（认领、租约、版本号）保证多实例下的语义与单实例一致。判断标准始终是一条：**同一个请求落到任意一个副本上，结果都必须正确**。

> **阶段二不是把单机版改造成分布式版，而是让同一个 jar 在两种档位下都正确。** 单机档是默认值，走阶段一的全部代码路径；集群档由 `oryxos.cluster.enabled=true` 打开，多出的是协调原语与它所要求的存储面（决断 D1）。

### 1.2 阶段二能干什么

阶段二交付六组能力。每组能力下面写两类内容：**是什么**（要做什么）与**基于这个能力可以做的事**（业务上换来什么）。

#### 能力组一：共享状态与实例治理

一组实例共读写同一份状态，每个实例有全局唯一标识，实例之间完全对等、没有主从；实例的心跳、上下线、当前档位可查。

**基于这个能力可以做的事：**
- 用 `GET /api/v1/instances` 回答"现在到底有几个副本在跑、版本分别是什么、谁的最后一个心跳在什么时候"，不必登录每台机器
- 容量按副本线性加：从试点期的 1 副本加到服务全公司的 3~8 副本，不需要改 Agent 配置
- 灰度与回滚有落点：新版本先起一个副本观察，异常时把它下线，流量自然回到旧副本
- 运维误配（集群档配了 SQLite、配了只支持单机的记忆后端）在启动那一刻就暴露，而不是几天后数据分裂了才发现

#### 能力组二：跨副本恰好一次

五类必须"只做一次"的动作在集群档下跨副本成立：会话轮次、定时触发、入站事件、渠道属主、知识重建。幂等键分别取（会话 + 轮次）、（任务 + 理论触发时刻）、（渠道 + 事件 id）、渠道名、（后端 + 作用域）。

**基于这个能力可以做的事：**
- 同一个用户在 IM 里连发两条消息、两条恰好被两个副本收到，Agent 不会同时开两个轮次来回抢同一份对话历史
- 运维把服务从 2 副本扩到 4 副本，定时任务不会因为副本变多而多跑几遍、多发几遍消息
- IM 平台重推同一条事件（网络抖动、平台重试）不会让 Agent 把同一件事做两次
- 可以放心地把请求分发给任意副本，不需要在网关做会话粘性路由

#### 能力组三：渠道属主

每一个 IM 渠道的长连接在任意时刻只有一个实例持有（属主），属主通过租约维持，**永不互踢**；属主停机时先主动释放，崩溃时由其他副本在租约过期后接管。

**基于这个能力可以做的事：**
- 多副本部署下仍能接飞书/企微/钉钉长连接，不因为"平台侧多连接会互踢"而被迫把渠道钉死在单副本上
- 渠道所在副本滚动升级时，渠道在租约过期后自动漂到另一个副本，用户侧表现为几十秒内机器人又能回话
- 容量扩展与渠道接入解耦：加副本只加处理能力，不改变渠道拓扑

#### 能力组四：共享工作区与变更感知

`.oryxos/` 工作区放共享卷，各副本用版本号总线感知变更并重载；工作区访问统一走存储抽象与本机执行视图；落盘原子、管理写互斥、运维改盘有逃生舱。

**基于这个能力可以做的事：**
- 改一份 `AGENT.md`、绑一个 Skill、加一个人格预设，所有副本在秒级内一起生效，不用逐个重启
- 运维直接在共享盘上改文件（应急修 prompt、塞一个脚本）之后，用逃生舱强制全集群重载
- 多部门共用一个工作区时，Agent 的产出物按 Agent/run 隔离，两次并发运行互不覆盖
- 排障时能确认"每个副本看到的确实是同一份工作区"，而不是各自读到本地残留副本

#### 能力组五：知识代次

知识索引在集群档下代次化：**检索恒读已提交代次**，重建走认领保证跨副本恰好一次，导入索引段与重建互斥，重建期间旧代次继续服务。

**基于这个能力可以做的事：**
- 知识库从几百份文档涨到几万份文档、重建从几分钟涨到几十分钟的过程中，用户照常提问，检索不断服
- 多个副本同时到点触发重建（定时 + 手工 + 变更触发撞在一起），只有一个真正执行，其余排队或直接返回冲突，不产生两套互相覆盖的索引
- 重建失败或副本在重建中崩溃时，旧代次仍然可用，重新发起重建即可，不需要人工清理半成品

#### 能力组六：容器交付与可观测

官方 Helm Chart 交付（探针、滚动升级、优雅停机、RWX 卷、密文引用），跨副本可观测与审计同源（同 traceId、审计带 `instance_id`、OTel 可选导出）。

**基于这个能力可以做的事：**
- 用企业现有的 K8s 发布流程接管 OryxOS：`helm upgrade` 就是一次滚动升级，不需要写自定义脚本
- 一次消息处理跨了多个副本（入站副本、执行副本、恢复副本）时，仍能用同一个 `traceId` 把日志、审计行、trace span 拼回一条链路
- 按实例维度看指标：哪个副本在抗量、哪个副本在空转、滚动升级期间吞吐掉了多少
- 出故障时用审计与实例视图回答"这件事是哪个副本做的、什么时候做的"，满足事后追溯的要求

> 六组能力合起来才是阶段二的完整交付。只做前五组不做交付组，企业仍然要手搓部署；只做交付组不做前五组，多副本跑起来语义就是错的。

## 2. 术语和概念

阶段一已有术语（Agent、Profile、Provider、ReAct 循环、Tool、Memory、Channel、Web Service、Session、Sandbox、Tool Policy、Skill、Bootstrap、Workspace）沿用 `docs/oryxos-docs/DemandAnalysis.md` 第 2 章的定义，本文档不重复。以下为阶段二术语，含义以本表为准；本文档与同套另外三篇文档共用这一套口径。

下表为 README 第 3 章统一术语表的**补充项**（本文档需要的需求侧概念），不改变 README 已有条目的定义。

| 术语 | 定义 |
|------|------|
| **实例 / 副本（instance / replica）** | 一个 OryxOS 进程。集群档下每个实例有全局唯一的 `instance-id`，实例之间完全对等，没有主从之分 |
| **单机档 / 集群档** | 由 `oryxos.cluster.enabled` 决定的两个运行档位。单机档是默认值，走阶段一的全部代码路径；集群档打开协调原语。同一个 jar、同一个镜像、同一份配置结构，唯一区别是这个开关和它所要求的存储面 |
| **共享状态层** | 集群档下多实例共读写的状态载体，本方案里是 PostgreSQL（关系型状态 + 协调原语）与共享卷（文件面状态）两部分 |
| **认领（claim）** | 用一条带条件的写语句（CAS）把某件事在某一时刻唯一归属到某个实例的动作。认领失败即代表别人持有 |
| **租约（lease）** | 认领的凭据加过期时间。持有方必须周期性续约；持有方崩溃后，租约自然过期，由其他实例接管 |
| **属主（owner）** | 某个渠道长连接或某项在跑工作的当前唯一持有实例 |
| **理论触发时刻（theoretical fire time）** | cron 表达式算出来的应触发时刻，由调度器（`CronTrigger`）给出，**不是墙钟时间**。它是定时任务跨副本去重的幂等键 |
| **幂等键（idempotency key）** | 用来判定"这件事是不是同一件"的键。会话轮次用（会话 + 轮次序号），定时任务用（任务 + 理论触发时刻），入站事件用（渠道 + 事件 id），渠道属主用渠道名，知识重建用（后端 + 作用域） |
| **事件回执去重** | 入站渠道对同一条消息事件只处理一次。阶段一用进程内 Map，集群档必须落到共享状态层 |
| **版本号总线（version bus）** | `workspace_versions` 表按域维护单调递增的版本号。管理面写路径落盘后 bump 对应域，各副本轮询比对自身已加载版本，落后即重载 |
| **域（domain）** | 版本号总线上的一类可独立重载的工作区数据：agents、skills、personas、knowledge、channels、bootstrap |
| **代次（generation）** | 知识索引的一次已提交快照版本。检索**恒读已提交代次**，重建期间旧代次继续服务 |
| **本机执行视图（native path）** | 共享工作区里的一个路径在本实例上真实可执行的本地路径。Tool（文件、Shell）执行必须用本机执行视图，不能把逻辑路径直接当文件路径用 |
| **管理写互斥预约** | 管理面对某类工作区数据的写操作前提。它是人工介入的闸门，**不自动过期**；恢复前必须先停掉全部写者 |
| **读写者停机预约** | 停机流程里的写者退场确认，保证"最后一个写者关灯"之后才允许做离线恢复动作 |
| **保留路径** | `.workspace-*` 与 `.staging`。工作区里以它们开头的路径由底座内部占用，业务 Agent 不得使用 |
| **逃生舱（escape hatch）** | `POST /api/v1/workspace/refresh`。运维绕过版本号总线直接改盘后，用它强制各副本重载 |
| **崩溃轮次** | 实例在跑某个会话轮次或某个定时触发时崩溃留下的半成品记录。**标失败、不重放**，由用户重发恢复 |
| **误配拒启动** | 集群档下遇到本方案不支持的状态组合（如 SQLite、markdown 记忆后端、内存知识后端）时，启动直接失败并给出恢复指引，不静默降级 |
| **工作区标识（`.workspace-id`）** | 管理员在共享卷上预置的标识文件。集群档启动时校验它与配置中的标识一致，不一致即拒启动，**绝不回退到本地工作区**（否则数据分裂） |
| **实例视图** | `GET /api/v1/instances` 返回的实例清单：实例标识、地址、版本、状态、最近心跳时间 |
| **心跳（heartbeat）** | 实例周期性写入的时间戳。超过心跳超时未更新的实例被视为失联，从实例视图中标记为不可用 |
| **轮询间隔（poll interval）** | 集群档下各副本比对工作区版本号的周期，默认 1s。变更传播延迟的上限由它决定 |
| **轮询放大** | 副本数 × 轮询频率带来的数据库读压力。轮询是刻意选定的方案，放大是它的已知代价，需要被容量评估覆盖 |
| **双属主窗口** | 旧属主尚未停机完成、新属主已因租约过期而接管的短暂重叠期。设计上用"接管前先让旧连接走完停机链路"把它的影响压到最小 |
| **单写者** | 本方案的一致性取向：对任一共享状态，集群在任意时刻只认一个写者（CP 取向），不做多主冲突合并 |
| **集群档迁移** | 从单机档切到集群档的动作：备份 SQLite、切 PostgreSQL 数据源、工作区迁到共享卷、补配置项、按顺序逐副本切换。它是运维流程，不是数据自动同步 |
| **只读降级拒服务** | 当协调基质（PostgreSQL）不可用时，实例不再接受新的轮次与定时触发，已在进行的工作按停机链路收尾；宁可拒服务，也不错服务 |

**本阶段不做**：不为阶段三的 Agent 协作引入新术语；不把"集群"等同于"多区域"；不使用"主节点/从节点"描述实例关系（实例之间完全对等）。

## 3. 设计目标

阶段二的设计目标可以用六个词概括：**不停、不重、不丢、不改、可运、少依赖**。前三个词定义多实例下必须成立的语义，后三个词定义它给用户与运维带来的代价上限。

| 目标 | 目标内容 | 衡量方式 |
|------|---------|---------|
| **不停** | 水平扩展与高可用：加副本就加容量；单副本故障或滚动升级期间，对外服务不中断 | 2 → 4 副本加速比 ≥ 0.8；滚动升级期间消息零丢失，单副本不可用窗口 = 在途请求排空时间；3 副本 + PostgreSQL 高可用下可用性目标 99.9% |
| **不重** | 恰好一次语义：五类动作跨副本只做一次（会话轮次、定时触发、入站事件、渠道属主、知识重建） | 每个 `fire_time` 恰好 1 行 `task_executions`；同一会话并发打到 3 副本时回复不重不乱；同渠道任意时刻只有一个属主 |
| **不丢** | 崩溃不丢数据：已提交的会话数据、审计行、任务执行历史、已提交知识代次，在副本猝死后仍然存在且可查 | 副本被 `kill -9` 后重启或由其他副本接管，审计无空洞；崩溃轮次有明确失败记录而不是消失；已提交代次仍在服务 |
| **不改** | 单机档零改动：单机档代码路径不新增协调调用、配置结构向前兼容、工作区目录结构不变、Agent 目录写法不变 | 单机档回归测试全绿；单机档不依赖 PostgreSQL 与共享卷；只把 `cluster.enabled` 置为 false 就能回退到单机档行为 |
| **可运** | 可运维可观测：用企业现有 K8s 与监控体系能部署、能升级、能排障、能追溯 | `helm upgrade` 完成一次滚动升级；`GET /api/v1/instances` 与审计的 `instance_id` 口径一致；一次跨副本处理能用同一 `traceId` 拼回链路 |
| **少依赖** | 不引入新中间件：协调复用已有的 PostgreSQL 部署档，文件面复用通用共享卷，不新增 Redis/ZooKeeper/etcd/消息队列 | 集群档新增的外部依赖只有两项：PostgreSQL 14+ 与共享卷（RWX）；无新增常驻进程 |

三点补充判断，避免这六个词被读成"什么都要"：

1. **"不停"的量级是本周期可验证的规模，不是无限扩展。** 本周期验证的副本数上限 32、单集群 Agent 数 ≥ 100、并发 Session ≥ 1000。再往上属于下一周期的容量模型。
2. **"不重"是有边界的承诺。** 恰好一次只承诺在五个粒度上（决断 D3）；审计落库、通知推送、外部系统调用这类链路是"至少一次 + 幂等键"，文档必须把边界写清而不是笼统宣称 exactly-once（见 8.3）。
3. **"少依赖"是刻意的代价交换。** 复用 PostgreSQL 做协调，意味着数据库成为协调单点与轮询压力的承受方；少一个中间件的收益大于这些代价，但代价必须在容量与高可用设计里被正面处理（见 12 章风险表）。

**本阶段不做**：不承诺跨区域高可用（异地多活）、不承诺数据库侧的高可用实现（由部署方决定，OryxOS 只给出要求）、不承诺在协调基质不可用时继续服务（选择只读降级拒服务）。

## 4. 典型场景

以下四个场景描述阶段二的目标用法。前两个是"必须成立"的日常，后两个是"出事时也要成立"的边角；每个场景末尾点明阶段二在其中的角色。

### 场景一：从部门试点走向全公司

某制造企业的 IT 部门先用 OryxOS 服务了客服一个部门：一个实例、一支客服 Agent 团队、飞书上的一个机器人。半年后 HR、法务、供应链都要接进来，Agent 从十几个涨到上百个，每天早上九点全公司的定时日报集中触发，飞书机器人在同一时刻被几千人 @。单个实例的线程池和数据库连接池先扛不住，运维的第一反应是"换个更大的机器"，但扩容窗口只有一条：垂直加配置，而且下次还得再来一次。

阶段二之后，这个团队的扩容动作变成把副本数从 1 调到 3：K8s 里改一个值，或者 `helm upgrade --set replicaCount=3`。容量随副本增加，而 Agent 目录、渠道配置、知识库都只有一份——工作区在共享卷上，各副本读到的是同一份；会话、定时、事件回执在 PostgreSQL 上，谁处理都正确。

**阶段二在此场景的角色**：共享状态层把"多副本"变成"多份算力共用一份状态"，实例治理让运维看得见每个副本的状态，误配拒启动把"配错存储组合"挡在扩容动作之前。

### 场景二：滚动升级与单副本故障

周二下午两点，运维把 OryxOS 从 v1.4 升到 v1.5。`helm upgrade` 触发 RollingUpdate：先起一个新副本，探针通过后摘掉一个旧副本，旧副本收到 SIGTERM，停止接受新请求、把在途请求排空、主动释放渠道属主租约，然后退出。这个过程重复三轮，集群从 3 个 v1.4 副本变成 3 个 v1.5 副本。同一时间，飞书群里的客服机器人一直在回话——用户唯一的感受是某几条消息的回复比平时慢了一两秒。

三天后，一个副本因为节点故障被直接杀掉（`kill -9`，没有停机流程）。它当时正在跑的两个会话轮次、一个定时触发、以及一个飞书长连接属主都留在了半成品状态。渠道属主租约过期后被另一个副本接管，机器人恢复回话；那个定时任务在 `task_executions` 里留了一行失败记录而不是被重放；两个会话轮次被标为失败，用户重发消息就恢复了。审计表里能查到这三个动作分别发生在哪个实例上、什么时间失败的。

**阶段二在此场景的角色**：优雅停机链路保证"计划内的下线不丢消息"，租约 TTL 与接管时序保证"计划外的猝死能被接管"，崩溃轮次标失败不重放（决断 D6）保证"接管不会造成重复副作用"。

### 场景三：定时任务与知识库重建的集群化

早上八点五十五，三个副本各自算出了同一个 cron 的理论触发时刻，同时到点。三个副本都去做认领，`(schedule_id, fire_time)` 上只有一个能写成功，另外两个拿到冲突后直接放弃——日报只发了一遍。九点半，法务部把新一批合同模板放进知识目录，触发知识索引重建：三个副本又同时发起，只有一个认领成功，其余返回 409 排队。重建要跑二十几分钟，这期间员工在飞书上的提问照常被检索回答，读的是上一个已提交代次；重建完成后新代次被提交，下一次提问开始命中新索引。

**阶段二在此场景的角色**：认领 + 租约把"多个副本同时想做同一件事"收敛成"恰好一个执行"；代次化把"重建"与"检索"解耦，让重建不再是服务中断事件。

### 场景四：运维抢救

凌晨，一个 Agent 在飞书上持续给出明显跑偏的回答。值班工程师判断是 `AGENT.md` 正文被改坏了。他没有走管理面，而是直接 SSH 到共享卷挂载点，把文件改回去，然后调一次 `POST /api/v1/workspace/refresh` 逃生舱——所有副本立刻重载工作区，机器人恢复正常。如果问题更深（比如共享卷本身没挂对、需要离线做数据修复），流程变成另一条：先在管理面申请对应域的**管理写互斥预约**（不自动过期，人工确认），确认没有其他写者后走**读写者停机预约**把副本逐台停掉，做离线修复，再从管理面释放预约并逐台拉起。

**阶段二在此场景的角色**：版本号总线 + 轮询保证正常情况下变更能被自动感知，逃生舱保证"绕过总线直接改盘"这条运维路径也能收敛，管理写互斥预约与读写者停机预约保证破坏性操作前有一个"最后一个写者关灯"的确认。

**本阶段不做**：不做自动化运维编排（自愈、自动扩容、自动预约）；不做跨区域切换；不做面向业务的灰度发布（只做副本级灰度）。

## 5. 核心功能

> 核心功能是阶段二必须完成的最短链路：**让一组无状态实例共享同一份状态、对外表现成一个 OryxOS**。它对应 README 第 2 章线内清单（其中"崩溃语义与租约接管时序"并入 5.3 / 5.6；5.12"命令行与 API 增量"为运维面新增），全部落在 M0–M5 内，是第 13 章验收的硬条件。每一节写清三件事：要什么（需求条目）、期望行为、边界在哪（本阶段不做）。

### 5.1 集群开关与运行档位

**要什么：** 同一个 jar、同一个镜像、同一份配置结构，能运行在两种档位下，且档位只影响是否打开协调原语。

| 需求条目 | 内容 | 为什么 |
|---------|------|--------|
| **档位开关** | `oryxos.cluster.enabled`，默认 `false`（单机档）。`true` 即集群档 | 单机档是绝大多数试点场景的形态，必须零成本；集群档是扩容时的显式选择（决断 D1） |
| **实例标识** | 集群档必须有全局唯一 `oryxos.cluster.instance-id`。缺省由主机名 + 短随机后缀生成；K8s 下建议显式用 Pod 名 | 实例标识是审计口径、租约持有者、实例视图三处的引用键，重复标识会让"哪个副本做的"不可回答 |
| **档位校验** | 启动时校验档位与存储面是否自洽，不自洽即拒启动并给出恢复指引（决断 D11） | 错的存储组合会让多实例静默读写各自的数据副本，故障发生在几天之后且不可审计 |
| **档位不可热切** | 档位在进程生命周期内不可切换，改了配置必须重启 | 运行期切换协调原语等于在飞行中拆掉安全带；重启的代价远小于语义不确定性 |

集群档启动校验的误配组合共 **7 类**（每一项都必须"启动即拒"而不是降级）；另有一类**运行期 fail-closed**（协调基质不可用时拒服务，不降级为单机），不占启动校验的 7 类名额：

| 误配组合 | 为什么拒 | 恢复指引方向 |
|---------|---------|------------|
| 集群档 + SQLite 数据源 | SQLite 是文件级单写者，多进程跨节点共用不可靠 | 切到 PostgreSQL 14+（阶段一已支持该部署档） |
| 集群档 + markdown（文件）记忆后端 | 多副本并发追加同一文件会互相覆盖，且无跨副本可见性 | 切到数据库记忆后端 |
| 集群档 + 内存知识后端 | 索引只在单进程内存在，各副本检索结果不一致 | 切到数据库/共享卷知识后端 |
| 集群档 + `oryxos.workspace.storage=local` | 各副本读各自的工作区，Agent 配置与产出物分裂 | 改 `shared` 并把工作区放到 RWX 共享卷 |
| 集群档 + 工作区标识缺失或不匹配 | 挂错了卷或挂到了旧卷，等价于读错数据 | 校验共享卷根下的 `.workspace-id`，一致后重启 |
| 集群档 + 主密钥与其他副本不一致 | 加密字段解不开或解成乱码，属静默错误 | 统一 `ORYXOS_MASTER_KEY`（见 5.11） |
| 集群档 + 实例标识重复 | 双属主、租约互踩、审计口径混乱 | 换唯一标识（K8s 下用 Pod 名） |

以上 7 类即 README 第 4 章 D11 的**启动校验七类**。**数据库（协调基质）不可用不属于启动校验**——它是本文档里唯一的**运行期 fail-closed** 一类（见 8.1），不占启动 7 类的名额。

**期望行为**：单机档下不加载任何协调组件、不产生任何额外的数据库读写、不要求共享卷（零回归）；集群档启动日志明确打印档位、实例标识、存储模式、各协调原语的默认参数，便于排障时一眼确认"这台风向标在哪一档"。

**本阶段不做**：不做档位热切换、不做自动档位探测（按存储面猜档位）、不做多集群（一个 OryxOS 进程只属于一个集群）。

### 5.2 实例注册、心跳与实例视图

**要什么：** 集群档下每个副本在共享状态层登记自己、周期心跳，运维能在一个端点上看到整组实例的当前状态。

| 需求条目 | 内容 | 默认值 |
|---------|------|--------|
| **注册** | 启动时写入 `instances`（`status=starting`），完成初始化后置 `ready` | — |
| **心跳** | 周期性更新 `last_heartbeat_at` | `oryxos.cluster.heartbeat-interval` = 10s |
| **失效判定** | 超过心跳超时未见更新的实例在实例视图中标记 `stale` | `oryxos.cluster.heartbeat-ttl` = 30s |
| **停机标记** | 收到停机信号后置 `draining`，排空完成或进程退出后不再心跳、由 TTL 判定为 `stale` | — |
| **实例视图** | `GET /api/v1/instances` 返回实例清单：`instance_id`、`host`、`port`、`version`、`status`、`started_at`、`last_heartbeat_at` | — |

`instances.status` 是固定枚举：`starting`、`ready`、`draining`、`stale`。四种状态的含义分别是"在起还没好"、"能服务"、"正在退场"、"已失联"，**不引入第五种状态**，需要更细的信息用版本号与日志回答。

**边界**：实例视图是只读观测面，不承担流量调度职责——某个实例是否接流量由 K8s readiness 探针决定，不由实例视图决定。这一点必须写清，否则运维会误以为把某实例标成 `stale` 就能摘流量。

**本阶段不做**：不做实例级资源指标（CPU/内存/GC）展示、不做实例的远程启停接口、不做跨集群的统一实例视图（属社区共建的多集群管理台）。

### 5.3 会话轮次跨副本恰好一次

**要什么：** 同一个会话的同一个轮次，在集群里恰好被处理一次；同一会话的不同轮次在集群里串行，不并发；副本崩溃留下的半成品轮次有明确失败记录且不自动重放。

| 需求条目 | 内容 | 默认值 |
|---------|------|--------|
| **同会话互斥** | 以 `session_id` 为主键占住 `session_turn_leases`，同一时刻只有一个持有者 | — |
| **租约 TTL / 续约** | 持有方周期性续约，崩溃后租约自然过期 | `oryxos.cluster.session-turn-lease-ttl` = 60s / 续约 20s |
| **跨副本排队** | 第二、第三个副本拿到冲突后等待前一个释放，超上限即放弃并给出明确错误 | `oryxos.cluster.session-turn-wait-timeout` = 120s |
| **接管时限** | 租约过期后由其他副本接管 | 租约过期后 ≤ 60s |
| **崩溃语义** | 崩溃轮次在租约行上落 `state=failed` 与 `last_error`，不重放（决断 D6） | — |
| **轮次标识** | 幂等键取（会话 + 轮次序号），轮次序号记录在 `turn_seq` | — |

`session_turn_leases.state` 是固定枚举：`claimed`（已认领、还没开始跑）、`running`（正在跑）、`failed`（崩溃或异常结束，终态）。

| 场景 | 期望行为 | 失败表现（必须可解释） |
|------|---------|---------------------|
| 同会话两条消息恰好被两个副本收到 | 一个处理，另一个排队；用户看到两轮完整回复，顺序与到达顺序一致 | 排队超 120s 时后到的请求返回明确的"会话忙"错误，而不是静默丢弃 |
| 同会话的一条消息被网关重发（同一轮次） | 与上一条同语义，不产生第二个回复 | 同上 |
| 持有副本在跑轮次时被 `kill -9` | 租约过期后另一副本可接管该会话的**新**请求；崩溃轮次标 `failed` | 崩溃轮次没有被重放，用户需要重发；审计里能看到该轮次以失败结束 |
| 持有副本在续约时短暂失联又恢复 | 若租约未被他人抢走则继续持有；若已被接管则放弃本轮次并自行退出 | 放弃方不产生对外副作用，不产生双回复 |

**本阶段不做**：不做会话粘性路由与会话迁移（本方案的前提是任意副本都能处理任意会话）、不做崩溃轮次的自动重放、不做跨会话的分布式事务、不做轮次级优先级或公平调度。

### 5.4 定时任务到点恰好一次

**要什么：** 同一个 cron 任务的同一个触发时刻，在集群里恰好执行一次，不多不少；到点没跑成的处理方式（misfire）有明确策略且可解释。

| 需求条目 | 内容 | 默认值 |
|---------|------|--------|
| **幂等键** | 取（任务 + 理论触发时刻），落 `schedule_claims` 的 `(schedule_id, fire_time)` 唯一约束（决断 D5） | — |
| **认领** | 所有副本各自算出同一个理论触发时刻并尝试认领，只有一条能写成功 | — |
| **认领 TTL** | 认领方周期性续约；认领方崩溃后租约过期，允许其他副本接管：接管方以新的 `lease_id` 对同一 `fire_time` 做 CAS 改写（不是插入新行，因为 `(schedule_id, fire_time)` 是唯一键） | `oryxos.cluster.schedule-claim-ttl` = 120s |
| **执行留痕** | 每次实际执行在 `task_executions` 留一行，带 `instance_id` 与 `fire_time` | 每个 `fire_time` 恰好 1 行 |
| **misfire 处理** | 到点未执行（副本不在、认领冲突后原持有方已死等）按统一策略处理，策略记录在认领行的 `state` 上 | 默认策略见第 12 章未决事项 |
| **未认领成功者** | 认领冲突的副本直接放弃，不写 `task_executions`、不写 `schedule_claims` | — |

`schedule_claims.state` 是固定枚举：`claimed`（已认领待跑）、`running`（在跑）、`succeeded`、`failed`、`skipped`（按 misfire 策略判定为本次不执行，**不算故障**）。`skipped` 与 `failed` 必须在报表与告警里区分开，否则运维会把"策略主动跳过"当成故障排查。

**边界**：定时任务的"恰好一次"承诺的是**执行动作的发起**恰好一次。任务内部的对外副作用（发消息、调外部系统）如果失败，属于该次执行的失败，不做自动重试补偿——重试语义由 Agent 自己的工具重试策略承担。

**本阶段不做**：不做分布式任务编排与依赖（DAG）、不做任务级优先级与资源配额、不做补跑历史时刻的批量补偿接口、不做跨集群调度。

### 5.5 入站事件回执去重跨副本生效

**要什么：** 阶段一用进程内 Map 做事件回执去重，集群档下这个 Map 必须换成共享状态层的去重，使得同一条入站事件无论被哪个副本收到都只处理一次。

| 需求条目 | 内容 | 默认值 |
|---------|------|--------|
| **去重键** | （渠道 + 事件 id），落 `event_receipts` 的 `(channel, event_id)` 唯一约束 | — |
| **写入时机** | 在处理事件**之前**完成去重占位，占位成功才继续处理 | — |
| **保留窗口** | 回执行按保留窗口过期并定期清理，避免表无限增长 | `oryxos.cluster.event-receipt-ttl` = 24h |
| **重复处理** | 去重命中即丢弃该事件，不产生第二次回复，并留下可观测痕迹（计数 + 日志） | — |
| **跨副本生效** | 副本 A 收到过的事件，被平台重推到副本 B 时同样被判定为重复 | — |

保留窗口取 24h 的理由是"平台重推的时间尺度是分钟到小时，24h 覆盖绝大多数重推窗口"；窗口太短会在平台长时间重试时重复处理，太长会让表与清理成本上升（见第 12 章未决事项）。

**边界**：这一条的语义是**至少一次投递 + 幂等去重**，不是投递保证（决断 D3）。事件在网络里丢了、平台根本没推，OryxOS 无从知晓也不负责补偿；OryxOS 保证的是"同一事件只要到达过并被处理，就不会被处理第二次"。

**本阶段不做**：不做事件重放接口、不做全局事件有序性、不做事件积压队列与背压（引入消息队列属扩展功能，见第 6 章）、不做跨渠道的去重（不同渠道的事件 id 空间不互通）。

### 5.6 渠道长连接属主与停机

**要什么：** 每个 IM 渠道的长连接在任意时刻只有一个实例持有（属主），多副本启动时**永不互踢**，属主故障后由其他副本在租约过期后接管，属主优雅停机时先主动释放属主。

| 需求条目 | 内容 | 默认值 |
|---------|------|--------|
| **单属主** | 以 `channel_name` 为主键占住 `channel_ownerships`，同一渠道只有一个属主 | — |
| **租约 TTL / 续约** | 属主周期性续约，续约记录在 `last_renew_at` | `oryxos.cluster.channel-lease-ttl` = 30s / 续约 10s |
| **永不互踢** | 非属主副本**不得**建立该渠道的长连接；属主只在租约过期后才允许被接管（决断 D10） | — |
| **接管时限** | 属主崩溃后，其他副本在租约过期后接管 | 租约过期后 ≤ 30s |
| **停机先释放** | 优雅停机时先释放属主（以 `expires_at` 立即到期表达），再走连接关闭，且关闭不阻塞停机链路 | 释放后其他副本可立即接管，不等 TTL |
| **可观测** | 实例视图与渠道状态能回答"这个渠道现在谁是属主、上次续约在什么时候" | — |

| 场景 | 期望行为 |
|------|---------|
| 三个副本同时启动 | 三个都尝试认领同一渠道，只有一个成为属主并建立连接，另两个不建连接、只做候选 |
| 属主副本被 `kill -9` | 租约过期后某个候选副本接管并建立连接；平台侧只看到一次连接切换，不出现多连接互踢 |
| 属主副本优雅停机（滚动升级） | 先释放属主，候选副本立即接管；旧连接按既有纪律限时关闭（阶段一对长连接关闭已有限时纪律：SDK 关闭阻塞时放弃等待并继续停机链路） |
| 被接管的旧属主又恢复上线 | 它已是非属主，不得重新建立连接；若它发现属主是别人，保持候选状态 |
| 属主续约失败但连接还活着 | 续约失败即视为放弃属主并主动断开连接，避免出现"我连着你、但别人以为可以接管"的双属主窗口 |

**边界**：一个渠道一个属主，属主承担该渠道全部入站事件的接收与分发。这带来一个已知热点（属主副本的入站压力最大），本阶段接受它：入站接收轻、处理重，事件处理可以并发分摊，真正重的工作不绑在属主上。把入站也做成多活需要消息队列，属扩展功能。

**本阶段不做**：不做渠道级负载均衡与多活接收、不做渠道属主的主动迁移（只能停机释放或崩溃后接管）、不做跨渠道的属主亲和、不做平台侧 webhook 回调模式的渠道改造。

### 5.7 共享工作区与变更感知

**要什么：** `.oryxos/` 工作区从"进程本地目录"变成"多副本共读写的共享目录"，同时保证：写入原子、变更可感知、工具执行拿到的是本机真实可用的路径、运维能越过版本号直接改盘、管理面的破坏性写操作有人工闸门。

| 需求条目 | 内容 | 为什么 / 边界 |
|---------|------|--------------|
| **存储插件化** | 工作区访问统一走存储抽象（`WorkspaceStorage.root()/resolve()`），由 `oryxos.workspace.storage` 选择 `local` / `shared` 两种模式 | 业务代码不出现裸文件 API；切换模式不改业务代码（决断 D9）。同一个工作区目录结构在两种模式下完全一致 |
| **本机执行视图** | 逻辑路径在共享模式下先映射为**本实例上真实可执行的本地路径**，文件 Tool 与 Shell Tool 一律用本机执行视图 | 共享卷的挂载点在各副本上可以不同（甚至同一存储的不同挂载方式），把逻辑路径直接当文件路径用必然出错 |
| **工作区标识校验** | 共享模式启动时校验共享卷根下的 `.workspace-id` 与配置中的 `oryxos.workspace.id` 是否一致，不一致即拒启动，**绝不回退本地** | 挂错卷 = 读错数据，回退本地 = 数据分裂；两者都必须失败得干脆（决断 D9、D11） |
| **原子落盘** | 所有工作区写入先写临时文件再 rename 到目标路径，保证读者不会读到半个文件 | 只依赖"读写可见 + rename 原子"，不依赖文件锁、inotify、内存映射一致（决断 D7） |
| **多文件发布** | 多文件发布（如整个 Agent 目录、整个 Skill 目录）按"可恢复"设计：中断后可被识别并重做，但**不承诺目录级原子快照** | 目录级原子快照依赖文件系统事务，通用共享卷不提供；把这个能力从设计假设里删掉 |
| **版本号总线** | `workspace_versions` 按 `domain` 维护单调递增 `version`，管理面写路径落盘后 bump 对应域 | 版本号是"工作区变了"的**唯一真相源**，不依赖文件系统事件（决断 D8） |
| **轮询重载** | 各副本按轮询间隔比对自身已加载版本，落后即重载对应域；集群档不装文件 watcher | `oryxos.workspace.poll-interval` = 1s ⇒ 变更传播 P99 ≤ 3s（轮询间隔的 2 倍以内） |
| **保留路径** | `.workspace-*` 与 `.staging` 为底座内部保留，业务 Agent 不得使用；发布状态、临时区一律落在这里 | 保留路径被业务占用会让原子落盘与恢复流程失效 |
| **运行输出隔离** | Agent 运行产生的输出按 Agent/run 隔离存放，两次并发运行互不覆盖 | 阶段一的产出物路径在多副本并发下会互相踩 |
| **管理写互斥预约** | 管理面对某类工作区数据的破坏性写操作必须先持有 `admin_write_reservations`（按 `scope`），**不自动过期**，人工释放 | 人工闸门，保证"没有别人正在写"这件事被确认过，而不是靠猜 |
| **逃生舱** | `POST /api/v1/workspace/refresh` 强制各副本重载工作区 | 运维绕过版本号总线直接改盘后，需要一条收敛路径（见场景四） |

六个可独立重载的域（`workspace_versions.domain` 的取值集合）：`agents`、`skills`、`personas`、`knowledge`、`channels`、`bootstrap`。域划分的意义是"改一个 Agent 不必重载知识索引、改一个 Skill 不必重载所有渠道"——**重载粒度是需求，不是实现细节**。

**边界与约束**：
- 阶段一的 `WatchService` 在共享卷上不可靠（事件会丢、跨节点不可见），集群档**不装**文件 watcher；单机档的 watcher 行为零回归
- 所有工作区写入必须经过 `AtomicFiles` 一类的原子改名路径，不得直接原地覆盖
- 管理写互斥预约与读写者停机预约是两个不同层级的闸门：前者约束"某类数据正在被管理面写"，后者约束"停机时最后一个写者已退场，可以做离线恢复动作"

**本阶段不做**：不做目录级原子快照、不做写者与读者的强一致读（不做文件锁）、不做工作区的自动迁移与搬迁（集群档迁移是运维流程，见第 2 章术语）、不做跨集群工作区复制。

### 5.8 知识库代次化与重建认领

**要什么：** 知识索引在集群档下从"一个可被覆盖的索引"变成"一串不可变代次"，检索恒读已提交代次；重建通过认领保证跨副本恰好一次；导入索引段与重建互斥。

| 需求条目 | 内容 | 默认值 / 边界 |
|---------|------|--------------|
| **代次** | 每次重建产出一个 `knowledge_generations` 行，`generation_id` 唯一 | `state` ∈ {`building`, `committed`, `retired`} |
| **检索恒读已提交代次** | 检索只使用 `state=committed` 的代次；重建期间旧代次继续服务，**检索不断服** | 这是本节最重要的一条：重建不是服务中断事件 |
| **提交原子性** | 新代次先以 `building` 构建，构建完成后再置 `committed`（提交动作是不可逆的单点切换） | 提交前任何失败都不影响在服务的代次 |
| **代次保留** | 保留当前与上一代共 2 个已提交代次，更早的置 `retired` 并清理索引数据 | `oryxos.knowledge.keep-generations` = 2 |
| **重建认领** | 以 `(backend, scope)` 为主键占住 `knowledge_build_claims`，同一作用域同时只有一个重建者 | 认领冲突方返回 409 并排队，不重复构建 |
| **认领 TTL / 续约** | 认领方周期性续约；崩溃后租约过期，其他副本可接管重建 | `oryxos.cluster.knowledge-claim-ttl` = 30min / 续约 5min |
| **导入互斥** | 向已有代次追加索引段（导入文档）与全量重建走同一认领，二者不并发 | 并发的重建与导入会互相覆盖索引分片 |
| **冲突不丢** | 认领失败方进入排队等待，等待期结束仍未轮到则返回明确错误（不静默丢弃请求） | 排队语义在 Demo D 中被验收 |

**边界**：代次是"索引数据的一致快照"，不是"文档内容的事务"。文档原文在工作区里，由版本号总线负责让各副本看到最新原文；代次负责的是"索引与原文之间不会出现半新半旧"。

**本阶段不做**：不做增量索引（本节只要求全量重建的代次化与互斥）、不做跨后端联合检索、不做代次回滚到任意历史版本（只保留 2 代）、不做重建耗时的自动窗口调度。

### 5.9 容器交付与滚动升级

**要什么：** 企业不是手搓 `docker run`。阶段二交付官方 Helm Chart，让 OryxOS 能被企业现有的 K8s 发布流程直接接管（决断 D12）。

| 需求条目 | 内容 | 默认值 / 边界 |
|---------|------|--------------|
| **官方 Chart** | 提供 `charts/oryxos/`，覆盖 Deployment、Service、探针、卷、密文引用、滚动策略 | 阶段一已有 Docker 镜像与官方 compose 形态，chart 是纯增量 |
| **探针** | liveness 探针只判进程存活；readiness 探针必须包含数据库连通性 | readiness 不把在途依赖抖动判成不可用，避免滚动升级期间误摘流量 |
| **优雅停机** | 停机先停止接受新请求、排空在途请求、**先释放渠道属主租约**，再关闭长连接 | `spring.lifecycle.timeout-per-shutdown-phase` = 10s；Pod `terminationGracePeriodSeconds` = 40s |
| **共享工作区卷** | 工作区使用 RWX 类型 PVC；本地开发仍可用 `emptyDir`/本地卷跑单机档 | 只依赖"读写可见 + rename 原子"（决断 D7），支持矩阵见第 8.5 与第 12 章 |
| **密文引用** | 数据库连接三键与 `ORYXOS_MASTER_KEY` 通过 Secret → 环境变量注入，不落配置文件 | 复用阶段一既有的环境变量原生面 |
| **滚动策略** | `maxUnavailable: 0` / `maxSurge: 1`，升级期间可用副本数不减 | 单副本不可用窗口 = 在途请求排空时间 |
| **副本伸缩** | `replicaCount` 默认 3（推荐值），区间 2 ~ 8，本周期验证上限 32 | 与第 8.2 的容量目标一致 |

**边界**：Chart 只覆盖 OryxOS 自身。PostgreSQL 与共享存储由企业自行提供（或引用企业已有的 Operator/存储类），Chart 只给出连接配置与文档化的前置条件——把数据库的部署方式塞进 Chart 会让 Chart 无法适配企业现状。集群档不要用 `emptyDir` 作为工作区卷（会被直接拒绝或至少在文档中明确不支持）。

**本阶段不做**：不做 K8s Operator（属社区共建）、不做自动扩缩容（HPA）、不做多区域/多云发布的 chart 变体、不做数据库与共享存储的 Provision（只做引用）。

### 5.10 跨副本可观测与审计

**要什么：** 一次消息处理可能跨多个副本完成（属主接收、某个副本执行、崩溃后另一个副本接管），但它在审计、日志、追踪三处必须仍然能拼回同一条链路（决断 D13）。

| 需求条目 | 内容 | 为什么 |
|---------|------|--------|
| **traceId 同源** | 一次消息处理 = 一个 `traceId`；无论中间换了几个副本，`traceId` 不变 | `traceId` 是跨副本链路的唯一缝合线，阶段一已有该字段（021） |
| **审计带实例** | `tool_invocations`、`llm_calls`、`task_executions` 增加 `instance_id` | 回答"这件事是哪个副本做的"，也是实例视图与审计对账的口径 |
| **同计时区间** | 审计行的 `duration_ms` 与 trace span 的计时区间一致，事后补记不改变区间 | 审计与 trace 相互印证，而不是两套各说各话的耗时 |
| **OTel 可选导出** | `oryxos.otel.endpoint` 配置后才导出；不配置零开销 | 企业可接自己的 OTel 后端，不强制引入新依赖 |
| **指标** | 按实例与集群两个维度暴露：实例数/状态、轮次吞吐与排队、租约接管次数、定时认领冲突次数、变更传播延迟、渠道属主切换次数、知识重建次数与耗时 | 这些指标同时是运维面与验收证据（第 13 章的性能与 HA 验收直接读它们） |
| **告警** | 至少覆盖：实例长时间 `stale`、租约接管频繁（抖动）、认领冲突异常升高、审计写入失败、数据库不可用 | 前三类是集群档特有的故障模式，按阶段一的告警面覆盖不到 |
| **日志** | 沿用阶段一的结构化 JSON 日志，集群档每条日志带 `instance_id` 与 `traceId` | 排障时先按实例过滤、再按 trace 串联 |

**边界**：可观测是"能回答问题"，不是"收集一切"。指标基数要可控（不把 `session_id`、`event_id` 之类高基数标签打进指标，它们属于审计与日志）。审计写入本身是"至少一次"（见 8.3），指标是采样观测，两者都不承诺与业务动作的强一致。

**本阶段不做**：不做内置的可视化大盘（提供指标与模板，社区出大盘）、不做日志聚合与长期存储（交企业现有体系）、不做调用链的采样率调优策略、不做审计的 SIEM 导出。

### 5.11 集群档安全与密钥

**要什么：** 阶段一的加密与沙箱机制在集群档下不改语义，但要补三件事：主密钥多副本一致、加密字段在共享状态层可解、工作区卷权限不被副本间互相破坏。

| 需求条目 | 内容 | 边界 |
|---------|------|------|
| **主密钥一致** | 所有副本使用同一把主密钥（`ORYXOS_MASTER_KEY` 环境变量优先，缺省 `.oryxos/master.key`）；不一致时启动即拒并指路恢复 | 集群档下不得依赖"每个副本自动生成一份 master.key"——那样加密字段跨副本不可解 |
| **加密字段** | 落库凭证（如 `providers.api_key`、`notify_channels.config` 敏感项）沿用阶段一 `enc:v1:` AES-GCM 格式加密存储 | 加密格式不变，单机档已加密的数据迁移后仍可解 |
| **工作区卷权限** | 镜像非 root（uid 1000），卷权限由部署方预置；副本不得修改保留路径之外的目录权限 | 多副本共写同一卷时，"某个副本改了权限"会成为其他副本的故障源 |
| **不绕过沙箱** | 文件/Shell/HTTP 白名单校验在共享模式下依然生效；本机执行视图仍要过真实路径校验（软连接防逃逸，原则六） | 共享卷把"路径白名单"的语义从单机文件系统扩展到挂载点，校验必须基于真实路径 |
| **网络边界** | 集群档运维端点（实例视图、逃生舱、集群状态）只应在集群内网或 K8s Service 内可达，不直接暴露到公网 ingress | 阶段一沿用内网假设（无认证），这条假设在集群档下必须由部署拓扑来兜住 |
| **数据库凭据** | 连接串与口令只经环境变量/Secret 注入，不明文入库、不明文入 chart values | 与阶段一的密钥加载规则一致 |
| **不新增信任面** | 不引入新的常驻中间件（Redis/ZooKeeper/etcd/MQ），因此不新增一套需要单独加固的组件 | 决断 D2 的安全侧收益 |
| **审计留痕** | 管理写互斥预约的申请与释放、逃生舱的调用、属主接管都留下可查痕迹 | 破坏性动作要有负责人与时间 |

**边界**：认证与授权不在本阶段（沿用阶段一"假设内网、无认证"的边界）。这意味着集群档的正确部署前提是"这些端口不对外"，这件事必须在 Chart 与部署文档里写清楚，而不是靠调用方自觉。

**本阶段不做**：不做 RBAC/SSO/多租户、不做 mTLS 的实例间互认证（实例之间不直接通信）、不做密钥轮转（阶段一已有主密钥机制，轮转属后续）、不做审计字段的自动脱敏策略配置。

## 6. 扩展功能

扩展功能不在阶段二的链路上，记录在这里的目的是：**把"什么条件下才该做"写清楚，而不是先把技术做出来再找理由**。每一条都必须有真实数据作为判断信号。

### 6.1 引入 Redis / 消息队列

| 候选 | 用途 | 会换掉什么 | 判断信号（出现才做） |
|------|------|-----------|-------------------|
| **Redis（或同类）** | 协调原语下沉（租约、去重、分布式锁），减轻 PostgreSQL 的协调压力 | 替换 D2 的协调基质选择，或作为第二套协调实现 | 轮询/认领带来的数据库读压力成为实际瓶颈（例如协调类写入占数据库负载的显著比例），且短期无法用参数与索引缓解 |
| **消息队列** | 入站事件投递、跨副本任务分发、事件积压与背压 | 改变"事件由属主直接处理"的模型，支持入站多活 | 需要渠道入站本身多活（不只是处理多活）、或需要事件积压量与重放能力 |

**判断原则**：阶段二的取舍是把"少一个中间件"排在"少一点数据库压力"前面（决断 D2）。只有真实压测与线上数据表明数据库侧扛不住协调负载时，才引入第二套基质；引入时也必须保留不引入时的实现路径（多实现共存，而非替换），否则单机与小型部署会被迫背上 Redis。

### 6.2 多区域 / 多活

跨地域部署要求状态层能跨区域复制并处理写冲突。本方案是**单写者 + 中心协调**的 CP 取向，跨区域会把这个前提打破（跨区域写延迟进入关键路径、区域故障切换与租约语义冲突）。判断信号是"出现必须在多区域同时低延迟服务的硬性要求，且企业已有跨区域复制的关系型数据库形态"，届时要重新设计写入拓扑，不是加配置能解决的。

### 6.3 分区容忍

本方案在脑裂场景下选择**拒服务而不是各自服务**（只读降级拒服务）：协调基质不可用时，实例不接受新轮次与新的定时触发。要改成分区容忍（AP 取向）意味着引入冲突合并与最终一致的业务语义——对本项目所服务的企业场景（会话、审计、定时）而言，最终一致带来的解释成本高于可用性收益。判断信号是"企业明确接受最终一致并愿意承担冲突处理"，届时应作为独立设计议题评估。

### 6.4 Agent 级调度亲和

把某个 Agent、某类任务固定调度到某些副本（例如有本地 GPU、有特殊网络权限的副本）。当前方案的前提恰恰是**任意请求落到任意副本都正确**（README 第 2 章线外清单第 6 条），引入亲和会把这个前提变成"需要路由决策"，同时引入路由层的新单点。判断信号是"出现必须依赖副本本地能力（算力、网络位置、专用硬件）的 Agent"。

### 6.5 边界：跨节点 Agent 协作不在扩展功能里

**跨节点 Agent 协作（Agent 跨实例发现、委托、可靠异步协同、A2A 对接）不是阶段二的扩展功能，而是阶段三的独立一层——「Agent 通信底座」。** 它解决的问题是"Agent 之间怎么协作"，而阶段二解决的是"一组实例怎么共用一个底座"，两者的抽象层次不同：阶段二里没有任何 Agent 需要知道别的 Agent 跑在哪个实例上，阶段三里这恰恰是核心问题。

因此本文档、本套文档都不给阶段三留接口、不做预留设计。**本阶段不做**：不在阶段二的表结构、API、配置里为 Agent 协作预留字段或端点；不把"Agent 发现"混进实例视图（实例视图是运维面，不是 Agent 通信目录）。

## 8. 非功能需求

### 8.1 可用性与故障恢复

集群档的可用性下限**由数据库侧决定**，OryxOS 侧做的是"不因为自己的原因额外降低可用性"。

| 指标 | 口径 |
|------|------|
| **集群可用性目标** | 99.9%（3 副本 + PostgreSQL 高可用）。这是一个目标值而非承诺值：它依赖部署方的数据库复制模式与共享存储可用性 |
| **单副本故障 RTO** | 渠道属主接管 ≤ 30s（租约过期后）；会话轮次接管 ≤ 60s（租约过期后）；两者都不需要人工介入 |
| **计划内停机 RTO** | 单副本不可用窗口 = 在途请求排空时间（`timeout-per-shutdown-phase` = 10s 量级） |
| **协调基质故障** | 进入**只读降级拒服务**（**运行期 fail-closed 1 类**，与启动校验 7 类并列、不占其名额）：不接受新的轮次与定时触发，已在进行的工作按停机链路收尾；恢复时间由数据库侧决定 |
| **共享卷故障** | 集群档视为不可服务（工作区是 Agent 定义的来源）：实例不静默回退本地工作区，按拒服务处理 |
| **RPO（审计与状态数据）** | 由部署方的 PostgreSQL 复制模式决定：**同步复制 RPO = 0**，**异步复制为秒级**（典型为亚秒到数秒）。OryxOS 侧的承诺是**不静默丢数据**——写失败必须报错、可观测、可追溯，不允许"写不进去就跳过" |
| **RPO（工作区文件面）** | 由部署方的共享存储与卷快照策略决定；OryxOS 侧保证落盘原子（不会留下半个文件）与版本号单调 |

故障分类与期望表现：

| 故障 | 期望表现 |
|------|---------|
| 单个副本崩溃（`kill -9`） | 所属会话的新轮次在租约过期后被接管；渠道属主被接管；崩溃轮次标 `failed` 不重放；审计无空洞 |
| 滚动升级（逐副本替换） | 消息零丢失、每个 `fire_time` 恰好一次；用户侧只感知到个别请求变慢 |
| 数据库主库故障切换 | 秒级到分钟级拒服务窗口；窗口内新请求得到明确错误（不是超时黑洞），恢复后自动继续服务 |
| 数据库不可用较长时间 | 保持只读降级拒服务，不做兜底本地写（否则数据分裂），恢复后按正常路径继续 |
| 共享卷短暂不可用 | 读缓存在内存中的工作区可继续服务既有 Agent；需要读新文件的工具调用失败并报错 |
| 整组副本同时重启 | 恢复后实例重新注册；未过期的租约数据仍在数据库中，不会因为重启而产生重复执行 |

**本阶段不做**：不做跨区域容灾、不做数据库自身的高可用实现（只提出要求与验证 readiness）、不做流量的自动降级策略编排（只做拒服务这一档）。

### 8.2 性能与容量

目标数字统一引用 README 第 6 章，本文档不另立口径：

| 维度 | 单机档（阶段一） | 集群档目标（阶段二） |
|------|----------------|-------------------|
| 副本数 | 1 | 2 ~ 8（推荐 3），本周期验证上限 32 |
| 单集群 Agent 数 | ≥ 10 | ≥ 100 |
| 单集群并发 Session | ≥ 100 | ≥ 1000 |
| 单副本吞吐（mock provider 固定时延） | 参照阶段一 | ≥ 50 消息/秒 |
| 集群加速比 | — | 2 → 4 副本 ≥ 0.8 |
| 工作区变更传播延迟 | 即时（同进程） | 轮询间隔的 2 倍以内（默认 1s → P99 ≤ 3s） |
| 渠道属主接管 | — | 租约过期后 ≤ 30s |
| 会话轮次接管 | — | 租约过期后 ≤ 60s，且崩溃轮次被标失败 |
| 定时触发重复计数 | 不适用 | 每个 `fire_time` 恰好 1 行 `task_executions` |
| 滚动升级 | 停机即中断 | 零消息丢失，单副本不可用窗口 = 在途请求排空时间 |
| 集群可用性目标 | 单点 | 99.9%（3 副本 + PostgreSQL 高可用，可用性下限由数据库侧决定） |

**数字口径（必须随数字一起引用）**：吞吐与时延指标在**固定时延的 mock provider** 下测量（`-Doryxos.mock.latency-ms`），把 LLM 侧不确定性排除在外；真实吞吐由企业所接 Provider 决定，不作为底座的承诺指标。

**容量相关的要求（不是数字，是约束）：**
- 加速比目标（≥ 0.8）隐含要求：协调开销不能随副本数显著恶化。认领与竞争失败的路径必须廉价（冲突即放弃，不重试风暴）
- 轮询放大是刻意接受的代价：`副本数 × 1/轮询间隔` 的读压力必须被容量评估覆盖，且轮询查询必须走索引、只读单行
- 排队必须有上限（会话轮次 120s），不能让请求在队列里无限等待，否则"塞住了"会表现为"超时黑洞"
- 数据库连接池上限要按副本数 × 每副本池大小核算，避免扩容后把数据库连接打满

**本阶段不做**：不做十万级 Agent 的容量模型、不做按租户的配额与限流、不做跨集群容量调度。

### 8.3 一致性与幂等语义

**恰好一次只承诺在五个粒度上**（决断 D3），其余链路是"至少一次 + 幂等键"。这条边界必须写进文档、写进验收，而不是笼统宣称 exactly-once。

| 粒度 | 幂等键 | 语义 | 失败表现（必须可解释） |
|------|--------|------|---------------------|
| **会话轮次** | `session_id`（同一时刻一个持有者）+ `turn_seq` | 同一会话的同一轮次恰好被处理一次；同会话不同轮次串行 | 排队超 120s 返回明确错误；崩溃轮次标 `failed`，用户重发 |
| **定时触发** | `(schedule_id, fire_time)` | 每个理论触发时刻恰好执行一次 | `task_executions` 每个 `fire_time` 恰好一行；策略性不执行记 `skipped` |
| **入站事件** | `(channel, event_id)` | 同一条事件只处理一次 | 重复事件被丢弃并计数；事件丢失不补偿（至少一次投递） |
| **渠道属主** | `channel_name` | 任意时刻只有一个属主，永不互踢 | 旧属主失去租约即断开；接管不早于租约过期 |
| **知识重建** | `(backend, scope)` | 同一作用域同时只有一个重建者 | 冲突方 409 排队；崩溃后 TTL 到期可重新认领 |

**其余链路是至少一次 + 幂等键：**

| 链路 | 语义 | 幂等/兜底手段 | 边界 |
|------|------|--------------|------|
| **审计落库**（`tool_invocations`、`llm_calls`、`task_executions`） | 至少一次写入 | 写失败要报错并告警，不静默丢弃；审计行以自增主键区分，重复行可识别 | 审计写入失败**不阻塞**业务主链路，但必须可观测（决断：审计是地基，不因协调复杂度牺牲） |
| **通知推送**（`notify`） | 至少一次 | 由通知渠道的幂等能力与业务幂等键兜底 | 可能重复推送，不做跨副本去重 |
| **工具调用的对外副作用** | 至少一次 | 工具自身的重试策略 + 业务侧幂等键 | 崩溃轮次不重放（D6）正是为了不放大这类副作用 |
| **工作区写入** | 单写者 + 原子落盘 | 保留路径 + 管理写互斥预约 | 多文件发布可恢复但非目录原子快照 |

> **一条判断**：集群档没有让 OryxOS 变成"分布式事务系统"。它做的是把阶段一里"因为只有一个进程所以自然成立"的互斥，换成"用共享状态层显式表达的互斥"，其余语义（至少一次 + 幂等）与阶段一保持一致。

**本阶段不做**：不做跨多张表的业务级分布式事务、不做全局快照读、不做跨副本的因果序或全序保证、不对审计行承诺恰好一次。

### 8.4 可运维性

| 需求 | 内容 |
|------|------|
| **配置变更** | 工作区里的配置（Agent、Skill、人格、渠道）通过版本号总线自动传播，P99 ≤ 3s 生效，不需要重启；进程级配置（数据库、档位、协调参数）改动需重启，重启按滚动升级进行 |
| **灰度与回滚** | 支持副本级灰度：新版本先起一个副本，异常即下线该副本回滚，流量由其余副本承担；不做业务级灰度（按用户/租户切流） |
| **实例上下线** | 下线走优雅停机（摘流量 → 排空 → 释放属主 → 关闭长连接 → 退出）；上线先 `starting` 再 `ready`，readiness 通过才接流量 |
| **实例视图** | `GET /api/v1/instances` 回答"有几个副本、什么版本、谁失联"（5.2） |
| **集群状态** | 档位、协调基质连通性、各原语参数、认领冲突与接管计数的可查入口（5.12） |
| **日志与追踪** | 结构化 JSON 日志带 `instance_id` + `traceId`；OTel 可选导出（5.10） |
| **逃生舱** | 直接改盘后 `POST /api/v1/workspace/refresh` 强制重载（5.7） |
| **管理写互斥预约** | 破坏性管理写操作前的人工闸门，不自动过期，人工释放（5.7） |
| **集群档迁移** | 从单机档到集群档有文档化的迁移顺序：备份 SQLite → 切 PostgreSQL → 迁移工作区到共享卷并预置 `.workspace-id` → 备齐配置 → 停单机实例 → 逐副本启动集群档 |

**项目宪章约束在集群档下的落点**（README 第 8 章写作纪律第 1 条要求逐条说明）：

| 原则 | 集群档下如何成立 |
|------|----------------|
| **原则一**（自实现 ReAct Loop） | 多副本不改变 ReAct 的归属与 Tool 调度权：协调逻辑放在触发源外层，`ReActLoop` 循环体不认识"集群"这个概念 |
| **原则二**（Spring AI 只用两件事、禁用自动 tool 执行） | 协调原语不触碰 LLM 调用路径；轮次被认领之后，ReAct 循环仍然自己调度 Tool，不引入任何"框架自动执行"的路径 |
| **原则三**（Provider 显式映射） | 多副本各自持有显式映射表，映射关系来自同一份配置；不做"从容器里扫 Bean 类型"这类在集群下更容易出错的推断 |
| **原则四**（一个目录 = 一个 Agent；Skill 相对软连接 + 渐进披露） | 共享模式下 Skill 绑定仍只允许指向 `.oryxos/skills/` 的**相对软连接**；软连接与真实路径校验基于**本机执行视图**（`nativePath`）的真实路径；域重载包含 `skills`，不改变"一个目录 = 一个 Agent"的形态 |
| **原则五**（审计 day one 落库） | 集群档每条审计行带 `instance_id`，跨副本可追溯；审计写入失败必须告警（8.3） |
| **原则六**（不用 SecurityManager、软连接校验真实路径） | 共享模式下路径白名单基于**本机执行视图的真实路径**校验，软连接仍必须落在允许根内，且只依赖"读写可见 + rename 原子" |
| **原则七**（同步执行模型，不引入 Reactor/WebFlux/CompletableFuture） | 租约续约、版本轮询、心跳都在专用调度线程上**同步阻塞**完成；跨副本等待（排队）与超时也走同步等待，不引入响应式编排 |
| **原则八**（Tool 模块三合一） | 不因集群化拆模块；协调原语与存储抽象按依赖倒置放在契约层，由下游实现 |

**本阶段不做**：不做自动扩缩容、不做自动故障自愈编排、不做面向运维的管理台（Web UI）、不做配置的自动回滚。

### 8.6 安全

安全要求的完整清单见 5.11，此处只列非功能侧的口径：

- **不新增信任面**：集群档不引入新的常驻中间件，因此不新增一套需要单独加固、监控、备份的组件
- **最小权限延续**：文件/Shell/HTTP 白名单、真实路径校验在共享模式下不变；镜像非 root
- **密钥不落地**：主密钥与数据库凭据只经环境变量/Secret 注入；加密字段沿用阶段一 `enc:v1:` AES-GCM 格式
- **网络边界是安全边界**：沿用阶段一"假设内网、无认证"的边界，运维端点不应暴露到公网；这条假设必须由 Chart 默认值与部署文档承接
- **审计不可抵赖**：管理写预约、逃生舱调用、属主接管留痕

**本阶段不做**：认证、RBAC、SSO、多租户隔离、mTLS、密钥轮转、审计字段脱敏策略。

### 8.7 合规

| 要求 | 口径 |
|------|------|
| **数据驻留** | 与阶段一一致：所有状态（会话、审计、工作区、知识索引）留在企业自己的 PostgreSQL 与共享存储上，不主动外发 |
| **审计跨副本完整** | 多副本下审计不出现"因为换了副本所以没记"的空洞：每条审计行带 `instance_id`，与 `traceId` 一起构成"谁在什么时候对哪次处理做了什么"的完整答案。副本崩溃时，崩溃前已落库的审计行保留；崩溃轮次本身留下 `failed` 记录 |
| **留证口径** | 审计三表（`tool_invocations`、`llm_calls`、`task_executions`）跨重启与跨副本可查；`task_executions` 带 `fire_time` 与 `instance_id`，使"这个时刻的任务是否执行过、谁执行的"可回答 |
| **留证边界** | OryxOS 承诺"审计写到共享状态层"，不承诺保留期限（由企业按合规要求配置数据库保留策略与备份）。审计写入是至少一次（8.3），不承诺与业务动作的强一致 |
| **不做过度承诺** | 不宣称本阶段满足特定合规认证（SOC 2、等保、GDPR 等）；本阶段只保证"审计数据在集群下不丢口径、可追溯" |

**本阶段不做**：不做审计的加密存储与完整性签名链、不做审计导出到 SIEM、不做按合规要求的数据分级与自动脱敏。

## 9. 关键流程

以下七个流程是阶段二的正确性骨架。每个流程图后面点明"这一步靠哪条决断或哪个原语保证正确"。

### 流程一：跨副本消息处理

```
用户消息进来（CLI / REST / IM 属主副本收到）
  → 入站事件去重：以 (channel, event_id) 在 event_receipts 占位
      ├─ 占位失败（平台重推的重复事件）→ 丢弃，不回复
      └─ 占位成功 → 继续
  → 定位会话，以 session_id 为主键向 session_turn_leases 发起认领
      ├─ 认领失败（他副本持有）→ 同步排队等待，上限 120s
      │     ├─ 等到前一个释放 → 重新认领
      │     └─ 等待超上限 → 返回明确错误（会话忙），不静默丢弃
      └─ 认领成功 → state=claimed，启动续约（TTL 60s / 续约 20s）
  → 组装 Prompt（ContextLoader + Memory + 会话历史 + ToolRegistry）
  → ReAct 循环：
      LLM 调用（写 llm_calls，带 traceId + instance_id）
      Tool 执行（写 tool_invocations，带 traceId + instance_id）
  → 生成本轮回复，落盘会话历史
  → state 收敛为终态、释放租约 → 通过渠道把回复发给用户
```

**靠什么保证正确**：同会话串行由 `session_turn_leases` 的 `session_id` 主键这一个约束保证（决断 D4 的 CAS 单语句 + TTL 租约）；重复事件由 `(channel, event_id)` 唯一约束挡掉；跨副本链路可拼回由 `traceId` + `instance_id` 保证（决断 D13）。

### 流程二：定时触发认领

```
副本 A / B / C 的调度线程各自算出同一个理论触发时刻 fire_time（CronTrigger，决断 D5）
  → 各自以 (schedule_id, fire_time) 尝试写入 schedule_claims（唯一约束）
      ├─ 写失败（唯一冲突）→ 直接放弃：不写 task_executions、不执行业务
      └─ 写成功 → state=claimed，成为该 fire_time 的唯一认领者
  → 按 misfire 策略判定本次是否执行
      ├─ 不执行 → state=skipped（不算故障，与 failed 区分）
      └─ 执行 → state=running，启动续约（TTL 120s）
  → 触发 AgentService（与人工触发共用同一条链路）
  → 执行结束 → 写 task_executions（instance_id + fire_time）
             → state=succeeded / failed
  → 认领方崩溃 → 租约 120s 后到期 → 其他副本以新的 lease_id 对同一 fire_time 做 CAS 接管（改写既有行，不插入新行——(schedule_id, fire_time) 是唯一键）
```

**靠什么保证正确**：幂等键取理论触发时刻（决断 D5），多个副本因此算出同一个值，才能在数据库上做唯一约束；重复计数以"`task_executions` 每个 `fire_time` 恰好一行"作为验收判据。

### 流程三：副本崩溃与会话接管

```
副本 A 持有会话 S 的轮次租约，正在跑 ReAct 循环
  → A 被 kill -9（没有停机流程）
  → A 停止续约，租约到期（≤60s）
  → 用户的下一条消息落到副本 B
      → B 以 session_id 认领，发现旧租约已过期 → CAS 接管成功
      → B 检查 S 的轮次状态：A 留下的轮次仍停在 claimed/running 且已过期
          → 标 state=failed 并写 last_error（崩溃轮次，决断 D6）
  → B 处理用户的【新】轮次，不重放 A 的旧轮次
  → 审计：旧轮次以 failed 结束（instance_id=A），新轮次由 B 记录
```

**靠什么保证正确**：标失败不重放（决断 D6）避免重复外部副作用；接管不早于租约过期（决断 D4）避免双处理；审计带 `instance_id` 让"谁失败的"可回答。

### 流程四：渠道属主接管

```
渠道 C 的属主是副本 A（channel_ownerships: channel_name=C, owner=A；续约 10s / TTL 30s）
  ├─ 情况一：A 优雅停机
  │     → 停机链路先释放属主（expires_at 立即到期）
  │     → 候选副本 B 立即认领成功并建立长连接（不互踢）
  │     → A 再限时关闭旧连接（关闭阻塞则放弃等待，不拖住停机链路）
  └─ 情况二：A 被 kill -9
        → A 停止续约，last_renew_at 不再更新
        → 租约到期（≤30s）→ 候选副本 B 认领成功并建立长连接
        → A 若之后恢复上线：它已非属主，保持候选，不建立连接
  任一副本在续约失败时 → 视为放弃属主并主动断开连接（不留"我连着你、别人以为可接管"的窗口）
```

**靠什么保证正确**：单属主 + 永不互踢（决断 D10）——属主只在租约过期后才允许被接管，接管前先让旧连接走完停机链路；释放优先于 TTL，把双属主窗口压到最小。

### 流程五：滚动升级

```
运维执行 helm upgrade（maxUnavailable: 0 / maxSurge: 1）
  → 起 1 个新版本副本 P_new
      → 写入 instances(status=starting) → 初始化 → 探针通过 → status=ready
  → 摘掉 1 个旧版本副本 P_old 的流量（readiness 不再通过）
  → P_old 收到 SIGTERM
      → 停止接受新请求
      → 排空在途请求（spring.lifecycle.timeout-per-shutdown-phase = 10s）
      → 先释放渠道属主租约（接管方秒级接管，不等 TTL 30s）
      → 限时关闭长连接
      → status=draining → 退出（terminationGracePeriodSeconds = 40s 兜底）
  → 逐个替换，直到全部副本为新版本（期间可用副本数不减）
```

**靠什么保证正确**：零丢失靠"先摘流量、再排空、先释放属主"的停机顺序；10s（应用阶段）与 40s（Pod 级）是两层兜底——阶段一已有实测教训：长连接 SDK 的关闭可能阻塞，必须限时放弃等待，否则停机被拖满。

### 流程六：工作区变更传播

```
管理面（API / CLI）修改工作区
  → 校验写者是否持有对应 scope 的 admin_write_reservations（不自动过期，人工释放）
  → 写入经原子改名落盘（先写 .staging，再 rename 到目标路径）
  → 落盘成功后 bump workspace_versions 对应域
      （agents / skills / personas / knowledge / channels / bootstrap）
各副本（含发起方自己）：
  → 每个轮询间隔（1s）读一次 workspace_versions
      ├─ 版本未变 → 继续服务
      └─ 版本变新 → 重载该域（P99 ≤ 3s）
运维绕过版本号总线的路径（直接改盘）：
  → POST /api/v1/workspace/refresh → 各副本无条件重载全部域
```

**靠什么保证正确**：版本号是"工作区变了"的唯一真相源（决断 D8），轮询给出确定的上限；原子落盘只依赖"读写可见 + rename 原子"（决断 D7）；逃生舱兜住绕过总线的运维路径，避免"改了盘但集群不知道"。

### 流程七：知识重建认领

```
触发源（定时 / 手工 / 文档变更）× 多个副本同时发起重建（backend=X, scope=Y）
  → 各自以 (backend, scope) 尝试写 knowledge_build_claims
      ├─ 冲突 → 返回 409 并排队等待（等待期结束仍未轮到则明确报错，不静默丢）
      └─ 成功 → state=claimed，启动续约（TTL 30min / 续约 5min）
  → 构建新代次：knowledge_generations 写入 state=building（记录 chunk_count）
      → 检索继续读 state=committed 的上一代（检索不断服）
  → 构建完成 → 提交：新代次置 state=committed（单点、不可逆的切换）
  → 超出保留数（keep-generations=2）的旧代次置 state=retired 并清理索引数据
  → 认领方崩溃 → 30min 后租约到期 → 其他副本可重新认领同一次重建
```

**靠什么保证正确**：认领 + TTL 租约把"多副本同时想做"收敛成"恰好一个执行"（决断 D4）；代次化把"重建"与"检索"解耦，检索恒读已提交代次，因此重建不再是服务中断事件。

**本阶段不做**：不做流程的自动编排引擎（这些流程是语义约束，不是可配置的编排图）；不做跨流程的分布式事务；不做流程的人工暂停/恢复控制面。

## 10. 数据模型

### 10.1 建表与迁移落点

集群档新增 9 张表，字段设计要能直接支撑 README 第 4 章的决断（认领靠条件写、去重靠唯一约束、过期判断靠 `expires_at`）。

- 表名、列名、状态枚举一律用 README 第 5 章的口径，**不另起名字**
- 创建与演进走 Flyway 双轨目录（`db/migration/sqlite/`、`db/migration/postgresql/`）：**同一变更两 vendor 各写一份、同版本号、只增不改**；集群档新增的 9 张表同样在两轨各写一份，SQLite 轨保留**结构等价的最小实现**，以保证迁移序列对称、单机档与集群档的表结构可对照
- **是否允许启用这些表由集群档启动校验决定**（误配拒启动，见 5.1），而不是靠"只在 postgresql 轨建表"
- `hibernate.ddl-auto` 保持 `none`
- 下表类型以 PostgreSQL 为准；SQLite 轨用等价最小类型（TEXT / INTEGER）

### 10.2 `instances`

| 字段 | 类型 | 说明 |
|------|------|------|
| `instance_id` | VARCHAR(64) | **主键**。集群内全局唯一，重复标识导致启动被拒 |
| `host` | VARCHAR(255) | 实例自报的主机名或地址（展示与排障用） |
| `port` | INT | 实例服务端口 |
| `version` | VARCHAR(32) | 应用版本，用于灰度与排障时确认版本分布 |
| `status` | VARCHAR(16) | 状态枚举：`starting` / `ready` / `draining` / `stale` |
| `started_at` | TIMESTAMP | 启动时间 |
| `last_heartbeat_at` | TIMESTAMP | 最近心跳时间；超过 `oryxos.cluster.heartbeat-ttl`（30s）即判 `stale` |

索引：`idx_instances_heartbeat(last_heartbeat_at)`。写入模式：启动注册、周期心跳更新、停机置 `draining`。

### 10.3 `session_turn_leases`

| 字段 | 类型 | 说明 |
|------|------|------|
| `session_id` | VARCHAR(128) | **主键**。主键即"同一会话同一时刻只有一个持有者"（同会话串行的唯一保证） |
| `owner_instance_id` | VARCHAR(64) | 当前持有副本 |
| `lease_id` | VARCHAR(64) | 本次租约的凭据，用于区分"同一持有者的不同次认领"与续约的有效性 |
| `turn_seq` | BIGINT | 轮次序号；与 `session_id` 一起构成会话轮次的幂等键 |
| `state` | VARCHAR(16) | 状态枚举：`claimed` / `running` / `failed` |
| `acquired_at` | TIMESTAMP | 认领时间 |
| `expires_at` | TIMESTAMP | 租约到期时间（TTL 60s、续约 20s）；小于当前时间即允许被 CAS 接管 |
| `last_error` | TEXT | 崩溃或异常结束的原因（崩溃轮次标 `failed` 时写入，决断 D6） |

索引：`idx_session_turn_leases_expires(expires_at)`。约束：认领与接管必须是**单语句条件写**（条件为"无行 / 租约已过期 / 持有者是自己"），不得用应用层读-改-写（决断 D4）。

### 10.4 `schedule_claims`

| 字段 | 类型 | 说明 |
|------|------|------|
| `schedule_id` | VARCHAR(64) | 关联阶段一的 `scheduled_tasks` |
| `fire_time` | TIMESTAMP | **理论触发时刻**（`CronTrigger` 给出，不是墙钟时间），决断 D5 |
| `owner_instance_id` | VARCHAR(64) | 认领副本 |
| `lease_id` | VARCHAR(64) | 认领凭据 / 栅栏令牌（fencing token）；续约与释放必须同时匹配 `owner_instance_id` 与 `lease_id` |
| `state` | VARCHAR(16) | 状态枚举：`claimed` / `running` / `succeeded` / `failed` / `skipped` |
| `claimed_at` | TIMESTAMP | 认领时间 |
| `expires_at` | TIMESTAMP | 认领租约到期（TTL 120s）；到期后允许接管：接管方以新的 `lease_id` 对同一 `fire_time` 做 CAS 改写（不是插入新行，因为 `(schedule_id, fire_time)` 是唯一键） |
| `finished_at` | TIMESTAMP | 执行结束时间（可空） |
| `error_message` | TEXT | 失败原因（可空）；`skipped` 不写失败原因，避免与故障混淆 |

唯一约束：`uq_schedule_claims_schedule_fire(schedule_id, fire_time)` —— 这是定时任务跨副本恰好一次的唯一保证。索引：`idx_schedule_claims_expires(expires_at)`。

**接管语义（栅栏令牌）**：到期接管由接管方写入**新的 `lease_id`**；旧持有者即使从长暂停（GC / STW / 网络隔离）中醒来，其续约语句（同时匹配 `owner_instance_id` 与 `lease_id`）也只影响 0 行，因此无法用过期凭据"复活"。接管是对既有行的 CAS 改写，不插入新行——`(schedule_id, fire_time)` 是唯一键。这与 `session_turn_leases` / `channel_ownerships` / `knowledge_build_claims` 三张认领表同构。

### 10.5 `event_receipts`

| 字段 | 类型 | 说明 |
|------|------|------|
| `channel` | VARCHAR(64) | 渠道标识（飞书 / 企微 / 钉钉 / CLI） |
| `event_id` | VARCHAR(128) | 平台侧事件 id |
| `instance_id` | VARCHAR(64) | 首次处理该事件的副本（排障用） |
| `received_at` | TIMESTAMP | 首次处理时间 |
| `expires_at` | TIMESTAMP | 保留窗口到期（`oryxos.cluster.event-receipt-ttl` = 24h）；到期即可清理 |

唯一约束：`uq_event_receipts_channel_event(channel, event_id)` —— 集群档替换阶段一进程内 Map 的唯一依据。索引：`idx_event_receipts_expires(expires_at)`（供定期清理）。

### 10.6 `channel_ownerships`

| 字段 | 类型 | 说明 |
|------|------|------|
| `channel_name` | VARCHAR(64) | **主键**。一个渠道一个属主 |
| `owner_instance_id` | VARCHAR(64) | 属主副本 |
| `lease_id` | VARCHAR(64) | 本次属主租约的凭据（防止旧属主用过期凭据续约成功） |
| `acquired_at` | TIMESTAMP | 获得属主的时间 |
| `expires_at` | TIMESTAMP | 属主租约到期（TTL 30s、续约 10s）；小于当前时间才允许被接管（决断 D10） |
| `last_renew_at` | TIMESTAMP | 最近续约时间；属主健康度的判断依据 |

索引：`idx_channel_ownerships_expires(expires_at)`。释放语义：优雅停机时把 `expires_at` 置为当前时刻（等价"立即过期、候选可马上接管"），**不新增释放列**——停机释放的诉求是"接管的等待时间为零"，而不是"记录一次释放事件"（释放事件写审计）。

### 10.7 `workspace_versions`

| 字段 | 类型 | 说明 |
|------|------|------|

| `updated_by` | VARCHAR(64) | 触发 bump 的实例标识 |

约束：`version` 只增不减；轮询查询必须只读单行且走主键（轮询放大的代价控制，见 8.2）。

### 10.8 `admin_write_reservations`

| `reserved_at` | TIMESTAMP | 预约时间 |
| `note` | TEXT | 预约原因（供后来者判断能否释放） |

## 11. 里程碑规划

阶段二按 **M0 ~ M5** 六个里程碑推进，每个里程碑结束都有可演示成果。里程碑顺序即依赖顺序：**先把共享状态基座立住，再把恰好一次三件套做对，然后才是渠道、文件面、知识面与交付。**

| 里程碑 | 目标 | 主要产出 | 可演示成果 |
|--------|------|---------|-----------|
| **M0** | 共享状态基座 | 集群开关、实例标识、误配拒启动、实例注册与心跳、PostgreSQL 档 | 拉起 2 副本，`GET /api/v1/instances` 看到两个实例与心跳；误配组合启动即拒并给出恢复指引 |
| **M1** | 恰好一次三件套 | 会话轮次租约、调度到点认领、事件回执去重 | 同一会话并发打到 3 副本，回复不重不乱；同一 cron 在 3 副本上每个 `fire_time` 只执行一次 |
| **M2** | 渠道属主与停机链路 | 渠道属主租约、永不互踢、接管时序、停机先释放 | 同一渠道多副本启动只有一个是属主；kill 属主后 TTL 内接管且不互踢、不双回复 |
| **M3** | 共享工作区 | 存储插件、原子落盘、版本号总线、本机执行视图、管理写预约、逃生舱 | 一个副本改 `AGENT.md` / 绑 Skill，其余副本 P99 ≤ 3s 生效；直接改盘后逃生舱强制重载 |
| **M4** | 知识库代次化 | 重建认领、已提交代次、导入互斥 | 多副本同时触发重建只有一个执行（其余 409 排队），检索全程读已提交代次不断服 |
| **M5** | 交付与验证 | Helm Chart、探针、滚动升级、跨副本可观测、HA 演练 | 滚动升级期间消息零丢失；压测报告（加速比、传播延迟、接管时间） |

### 各里程碑详细内容

**M0（共享状态基座）**
- 档位开关与启动校验：`oryxos.cluster.enabled`、`oryxos.cluster.instance-id`，7 类误配组合全部"启动即拒 + 恢复指引"（5.1）
- `instances` 表和实例注册/心跳/失效判定（10s / 30s），`GET /api/v1/instances` 与实例状态枚举（5.2）
- PostgreSQL 部署档打通：连接、Flyway 双轨迁移（两 vendor 同版本号、只增不改）、连接池按副本数核算
- 验收：2 副本互见；误配组合启动即拒；单机档回归全绿（`cluster.enabled=false` 行为不变）

**M1（恰好一次三件套）**
- 会话轮次租约：`session_turn_leases`、CAS 认领、续约（60s / 20s）、排队上限 120s、崩溃轮次标 `failed`（5.3）
- 调度到点认领：`schedule_claims` 唯一约束、理论触发时刻、认领 TTL 120s、misfire 策略落 `state`（5.4）
- 事件回执去重：`event_receipts` 唯一约束替换进程内 Map、24h 保留与定期清理（5.5）
- 验收：同会话并发打 3 副本不重不乱；3 副本同时到点只执行一次；重复事件被丢弃并计数

**M2（渠道属主与停机链路）**
- 渠道属主租约：`channel_ownerships`、单属主、永不互踢、续约（30s / 10s）、续约失败即断开（5.6）
- 停机链路：停止接新请求 → 排空（10s）→ 先释放属主 → 限时关闭长连接 → `draining` → 退出（40s 兜底）
- 接管演练：优雅停机接管（秒级）、`kill -9` 接管（≤30s）、旧属主恢复上线保持候选
- 验收：不互踢、不双回复；接管过程不产生重复入站处理

**M3（共享工作区）**
- 存储抽象与两种模式：`oryxos.workspace.storage` = `local` / `shared`，业务代码不出现裸文件 API（5.7）
- 工作区标识校验（`.workspace-id`，不匹配拒启动、绝不回退本地）、本机执行视图、原子改名落盘、保留路径（`.workspace-*` / `.staging`）、运行输出按 Agent/run 隔离
- 版本号总线（6 个域）与轮询重载（1s），集群档不装文件 watcher（单机档 watcher 零回归）
- 管理写互斥预约（不自动过期）与逃生舱 `POST /api/v1/workspace/refresh`
- 验收：变更 P99 ≤ 3s 生效；直接改盘后逃生舱强制重载；并发运行输出不互相覆盖

**M4（知识库代次化）**
- `knowledge_generations` 代次模型（`building` / `committed` / `retired`）、提交的单点切换、检索恒读 `committed`
- `knowledge_build_claims` 重建认领与 TTL（30min / 5min）、冲突 409 排队、导入索引段与重建互斥
- 保留 2 代（当前 + 上一代）与 `retired` 代次的索引清理
- 验收：多副本同时触发只有一个执行、其余排队不丢；重建全程检索不断服；崩溃后 TTL 到期可重认领

**M5（交付与验证）**
- 官方 Helm Chart：探针（readiness 含数据库）、RWX PVC、密文引用、`maxUnavailable: 0` / `maxSurge: 1`
- 跨副本可观测：审计带 `instance_id`、`traceId` 同源、OTel 可选导出（不配置零开销）、集群档专属指标与告警
- 集群档安全收口：主密钥多副本一致、`enc:v1:` 兼容、卷权限与网络边界
- HA 演练与压测报告：滚动升级零丢失、副本猝死接管、定时恰好一次、重建恰好一次、加速比与传播延迟（13 章口径）

**本阶段不做**：不把里程碑拆到周级人力安排（本文档只定依赖顺序与可演示成果）；不为某个里程碑单独引入中间件；不跨里程碑并行开工 M1 之前的内容（基座未立住前做的恰好一次不可验证）。

## 12. 风险与未决事项

### 已识别风险

| 风险 | 描述 | 应对措施 |
|------|------|---------|
| **共享卷语义差异** | NFS / CIFS / 各类云盘 RWX 对 rename 原子性、可见性延迟、权限模型的行为不一致；"我这边写完了"不等于"对方马上看得到" | 设计只依赖"读写可见 + rename 原子"（决断 D7），不依赖文件锁与 inotify；给出支持矩阵方向（8.5），未经实测的实现不列入支持名单；实测矩阵交社区共建（第 7 章） |
| **数据库成为协调单点** | 协调基质复用 PostgreSQL（决断 D2），库不可用则全集群拒服务；库的可用性下限决定了集群的可用性上限 | 明确写入可用性口径（8.1）与只读降级拒服务策略；readiness 含数据库连通性，故障库的副本不被接流量；把"数据库 RPO/RTO 由部署方复制模式决定"写进验收而非含糊承诺 |
| **双属主窗口** | 旧属主尚未停机完成、新属主已因租约过期而接管，短暂重叠可能造成重复连接或重复处理 | 属主只在租约过期后允许接管（决断 D10）；优雅停机**先释放**属主再关连接；续约失败即主动断开；窗口期内的重复入站事件仍由 `(channel, event_id)` 去重挡掉（双重保险） |
| **时钟与 TTL 判定** | 各副本墙钟漂移会让 TTL 判断偏离预期；用墙钟做定时幂等键会直接错 | 定时幂等键取理论触发时刻而非墙钟（决断 D5）；TTL 判定以数据库时间为准（应用不拿本机时间做仲裁）；部署要求各节点 NTP 同步 |
| **轮询放大数据库压力** | 副本数 × 轮询频率带来持续读压力；副本扩到上限时压力线性增长 | 轮询只读单行主键、走索引；版本号表极小；容量评估覆盖此项（8.2）；必要时通过调整 `oryxos.workspace.poll-interval` 在"传播延迟"与"数据库压力"之间取舍（未决事项 5） |
| **brownfield 改造破坏单机档** | 为了共享状态层改动核心链路，可能让单机档多出协调调用、多出依赖或行为变化（决断 D1 被破坏） | 单机档代码路径零新增协调调用；单机档回归测试作为每个里程碑的门禁；档位不可热切换，避免半开状态；`cluster.enabled=false` 是唯一的回退开关 |
| **集群档调试难度** | 问题从"进程内时序"变成"跨副本时序"，本地复现困难；"在我机器上是好的"会变多 | 强化可观测（`traceId` + `instance_id` + 实例视图 + 集群状态）；把"跨副本时序"的关键路径做成可单机复现的测试（多副本在测试里以多实例进程模拟）；所有接管类行为有明确的状态枚举可查 |
| **组织上"必须共享 PostgreSQL"的部署门槛** | 试点期的部门可能只有一台服务器、不想维护数据库；集群档要求企业提供 PostgreSQL 14+ 与共享存储 | 单机档保持零配置默认（SQLite + 本地工作区）；把"何时该上集群档"写成判断信号（多部门共用、需要 HA、需要扩容），而不是默认推荐；给出集群档迁移步骤（8.4）降低切换成本 |

### 未决事项

| # | 事项 | 现状与未决点 | 决议时间 |
|---|------|------------|---------|
| 1 | **租约 TTL 取值** | 统一默认参数已定（会话轮次 60s / 续约 20s、渠道属主 30s / 10s、定时认领 120s、知识重建 30min / 5min），未决的是：哪些部署形态（跨机房、共享卷延迟高、GC 停顿长）需要偏离默认值，以及偏离时如何仍满足"接管 ≤ 60s / ≤ 30s"的目标 | M1 / M2 压测后 |
| 2 | **misfire 默认策略** | 未定。候选：到点未执行即跳过并记 `skipped`（默认倾向）／允许在 TTL 内补跑一次／由任务配置显式选择。策略会直接影响"每个 `fire_time` 恰好一行"与用户对"日报为什么没发"的解释 | M1 定稿 |
| 3 | **是否提供 Redis 协调实现** | 当前决断 D2 是不引入（默认实现只有 PostgreSQL）。未决的是：是否值得提供第二种协调实现（不改变默认、不改变单机档），以及它的维护成本由谁承担 | M5 后按真实压力数据评估（判断信号见 6.1） |
| 4 | **事件回执保留窗口** | 默认 24h 已定，未决的是：是否需要按渠道可配（IM 与 webhook 的重推尺度不同）、清理任务的频率与批量、是否需要"窗口内重复计数"的观测指标 | M1 定稿 |
| 5 | **共享卷支持矩阵的最终名单** | 方向已定（只依赖读写可见 + rename 原子的 NFS/云盘 RWX），未决的是：具体厂商与挂载参数组合的实测名单、CIFS/SMB 是否列入、以及在延迟高的共享卷上是否要放宽传播延迟目标 | M3 后由实测与社区共建补齐 |
| 6 | **轮询间隔与传播延迟目标的最终取舍** | 默认 1s → P99 ≤ 3s 已定，未决的是：在超大规模工作区（大量 Agent 与 Skill）下重载本身的耗时是否会成为新的延迟瓶颈，是否需要按域分级轮询 | M3 压测后 |

**本阶段不做**：不把上述未决事项当作阻塞项（每项都有可用的默认可执行方案）；不引入需要先决议才能开工的设计依赖。

## 14. 总结

OryxOS 阶段二只做一件事：**让一组无状态实例共享同一份状态，对外表现成一个 OryxOS。**

| 维度 | 阶段一 | 阶段二 |
|---|--------|--------|
| 覆盖的形态 | 一个实例服务一个场景（一个部门、一个试点） | 一组实例服务全公司（多部门共用、容量与故障都有余量） |
| 状态的归属 | 状态与进程同生共死（SQLite + 本地工作区 + 进程内 Map） | 状态外置到共享状态层（PostgreSQL + 共享卷），实例本身无状态 |
| 互斥的手段 | 靠"只有一个进程"自然成立 | 靠共享状态层上显式表达的认领 + TTL 租约（决断 D4） |
| 关键承诺 | 五大核心能力跑通、审计 day one 落库 | **恰好一次在五个粒度上成立**，其余是至少一次 + 幂等键（决断 D3） |

**"恰好一次"是这一切的地基。** 水平扩展之所以能"加副本就加容量"，前提是任意请求落到任意副本都正确；滚动升级之所以能"零丢失"，前提是停机与接管不会造成重复或遗漏；多部门之所以能共用同一套底座，前提是定时任务、渠道连接、知识重建这些"只会发生一次的事"在多副本下真的只发生一次。所以阶段二的优先级很明确：先把恰好一次的五个粒度做对，再谈容量、交付与可观测。

**边界重申**（与 README 第 2 章一致）：不做跨节点 Agent 协作（属阶段三的「Agent 通信底座」）、不做多区域多活、不做多主与分区容忍、不做分布式事务、不引入新中间件（Redis/ZooKeeper/etcd/消息队列）、不做 Agent 级调度亲和与会话粘性路由、不做阶段三及以外的容量模型。**单机档零变化**是这整套设计的第一条纪律：同一个 jar、同一个镜像、同一份配置结构，`oryxos.cluster.enabled=false` 就是阶段一。
