## 一、什么是多实例 Agent 底座

### 1.1 一个明确的定义

**多实例 Agent 底座** = 运行 N 个对等实例、共享一份状态、对外表现成一个 Agent OS。

这句话里有三个限定词，每一个都不能省：

- **N 个对等实例**：实例之间没有主从、没有"调度节点 / 执行节点"分工、没有必须固定落在某台的 Agent。任一请求落到任一实例，结果都正确。
- **共享一份状态**：会话、审计、定时任务、事件回执、渠道属主、工作区文件，这些状态都放在实例之外、多个实例都能读写的地方。实例自己不持有任何不可重建的状态——这就是宪章里的「**无状态实例，状态外置**」。
- **对外表现成一个**：最终用户看到的是一个 OryxOS。同一个会话不会因为请求落到不同实例而出现两条并发回复；同一个定时任务不会在三个实例上各跑一遍；同一个渠道不会有两个实例同时应答。

这三条合起来，是阶段一调研第六章那个设想的精确化：阶段一交付的是"一个实例服务一个部门"，阶段二交付的是"一组实例服务全公司"。前者是一个进程里的一堆对象；后者是一堆进程共享一份状态，且这份共享对业务代码基本透明。

一个合格的**多实例 Agent 底座**必须解决五件事：

1. **实例对等与可替换**。每个实例有全局唯一标识，能注册、能被观测（`instances` 表 + `GET /api/v1/instances`），能被随意 kill 掉再由编排平台拉起一个等价的新实例，不需要人工干预、不需要数据搬迁。
2. **状态外置与共享**。关系型状态（会话、审计、任务、回执、租约）落在共享数据库；文件面状态（`.oryxos/` 工作区：Agent 目录、Skill、人格、知识索引）落在共享卷。实例重启不丢状态，实例扩容不迁移状态。
3. **跨副本互斥与恰好一次**。真正需要"同一时刻只有一个实例在做"的动作——同一会话的一轮处理、同一个 `fire_time` 的定时触发、同一条入站事件的回执、同一个渠道的长连接——必须在跨副本范围内互斥。这是多实例里唯一"做错了会直接产生业务副作用"的部分。
4. **共享工作区与变更感知**。一个实例改了 `AGENT.md` 或绑定了一个 Skill，其他实例要在有限时间内看到同一份新内容；知识库重建期间检索不能断服；运维直接改盘要有逃生舱。
5. **容器化交付与滚动升级**。部署形态是企业已有的 K8s：探针、优雅停机、滚动策略、卷与密文引用。这一条不是"锦上添花"，因为前四条的正确性最终要在滚动升级和 Pod 猝死这两种常态事件下被验证。

> 留给 OryxOS 的判断：五件事里，前三件是**正确性**问题（做错了会产生重复副作用或数据分裂），后两件是**可用性**问题（做错了会中断服务或让副本读到旧内容）。验收判据按这个权重分配——**正确性类（跨副本互斥与恰好一次）由 Demo B/C 压，可用性类（变更感知与交付）由 Demo A/D 压，实例治理由 Demo E 压**。

### 1.2 它长什么样

部署形态（集群档，3 副本为例）：

```
负载均衡 / K8s Service ──▶ oryxos #1 / #2 / #3（对等，任意请求落任意副本）
                              │            │            │
                              └────────────┴────────────┘
                                           ▼
                PostgreSQL（会话/审计/租约/回执/版本号/认领）
                共享卷 RWX（.oryxos/ 工作区：Agent/Skill/人格/知识）
```

四块拼起来：

| 组成 | 承担 | 阶段二口径 |
|------|------|-----------|
| N 个对等副本 | 接消息、调模型、跑工具 | 同一个 jar、同一个镜像，只有 `oryxos.cluster.enabled` 与存储面不同（D1） |
| 负载均衡 / Service | 把请求分到任意副本 | **不做会话粘性路由**——任意请求落到任意副本都必须正确 |
| 共享数据库 | 关系型状态 + 全部协调原语 | PostgreSQL 单写者，复用已在部署面的那一套（D2） |
| 共享卷 | 文件面状态 | 只依赖「读写可见 + rename 原子」（D7） |

运维面要提供三件事：

1. **实例视图**。`instances` 表记录实例的 `host`、`port`、`version`、`status`（`starting` / `ready` / `draining` / `stale`）、`started_at`、`last_heartbeat_at`；心跳 10s、失效判定 30s。运维能一眼看出"现在有几个实例、哪个在退场、哪个已心跳超时"。
2. **滚动升级**。`maxUnavailable: 0` / `maxSurge: 1`；Pod 收到 SIGTERM 后进入 `draining`：先释放渠道属主租约、再排空在途请求（停机 phase 10s，`terminationGracePeriodSeconds` 40s）。
3. **故障接管**。副本猝死不做任何"抢救半成品"的动作：租约自然过期后由其他副本接管（渠道属主 30s TTL、会话轮次 60s TTL）。崩溃轮次**标失败、不重放**（D6）。

> 留给 OryxOS 的判断：这张图里没有 Redis、没有 ZooKeeper、没有 etcd、没有消息队列。这不是省略，是 D2 与 D14 的直接结果——多一个中间件就多一套高可用、监控、备份、权限与审计面，而阶段二需要的协调语义（条件写、唯一约束、TTL 判断、行级可见性）关系库都已具备。第六章会逐项论证。

### 1.3 跟相邻概念的区分

多实例 Agent 底座容易被归到三个已经存在的概念里，但都不是它。

| 维度 | **多实例 Agent 底座** | **无状态 Web 服务水平扩缩容** | **编排平台 worker 扩容** | **分布式任务调度框架** |
|------|---------------------|---------------------------|------------------------|---------------------|
| 扩的是什么 | 共享一份状态的等价副本 | 完全无状态的请求处理单元 | 执行 workflow 节点的 worker | 被调度的作业 |
| 状态在哪 | 外置到共享数据库 + 共享卷 | 外置到数据库 / 缓存，但**没有跨副本互斥语义** | 平台的调度中心 + 队列 | 调度中心 + 数据库 |
| 实例之间要不要协调 | **要**，且是正确性的一部分 | 基本不要 | 不要（队列天然去重） | 要（选主/分片） |
| 长连接 | 有（飞书/企微/钉钉长连接），必须做单属主 | 无 | 无 | 无 |
| 定时触发 | 有，且必须跨副本恰好一次 | 通常无 | 有，但由平台调度中心负责 | 有，是核心能力 |
| 会话轮次 | 有，同一会话必须跨副本串行 | 无此概念 | 无此概念 | 无此概念 |
| 共享文件面 | 有（工作区），且要变更感知 | 无 | 无 | 无 |
| 复杂度落点 | 互斥、幂等、属主、变更感知 | 会话粘性、缓存一致性 | 队列与重试 | 调度精度与分片 |

逐条说明：

- **跟无状态 Web 服务水平扩缩容的区别。** 一个纯无状态的 Web 服务加副本几乎是免费的：请求之间互不相关，加一个副本就多一份算力，一致性交给数据库自己的事务。多实例 Agent 底座不是这样：它有**长连接**（同一渠道多副本同时连会互踢或随机投递）、有**定时触发**（多副本各自扫描会重复执行）、有**共享工作区**（多实例读同一份文件，需要变更感知）、有**会话轮次**（同一会话的两条消息落到两个副本，必须串行而不是并发）。这四件事都不在"无状态 Web 服务"的模型里，所以"把 Agent OS 当无状态服务加副本"是一个看起来对、实际会静默出错的直觉。
- **跟编排平台 worker 扩容的区别。** Dify 这类编排平台的 worker 扩容之所以简单，是因为它前面有一个**调度中心 + 队列**：任务入队，worker 抢单，队列本身保证一条任务只被一个 worker 取走。OryxOS 的入站事件来自 IM 平台的长连接推送，不是从队列里取的——它没有那个天然的队列层，必须自己用共享状态层把"抢单"语义补出来。
- **跟分布式任务调度框架的区别。** Quartz、XXL-JOB 这类框架解决的是"作业如何被可靠地、不重复地触发"，是 OryxOS 需要**复用其思路**的一个子问题（见 3.3），而不是 OryxOS 本身。OryxOS 还要管长连接属主、会话轮次、共享工作区变更——这些不在任何调度框架的范围内。

> 留给 OryxOS 的判断：不要用"加副本"这个词描述阶段二。阶段二不是把 OryxOS 变成无状态服务，而是把 OryxOS 里原本寄生在**单进程内存与单机文件系统**上的四类状态（互斥、去重、属主、变更感知）搬到共享状态层上。措辞的准确度直接决定实现会不会漏项。

## 二、业界开源 Agent 项目的多实例现状

### 2.1 部署形态现状

阶段一调研已经确认的格局是：开源 Agent OS 领域两个代表性项目 **OpenClaw**（Node.js）与 **Hermes Agent**（Python）都以**单进程、单机自托管**为主要部署形态，服务对象从个人起步、向小团队延伸。这一点与它们的定位是自洽的：个人与小团队不需要 3 副本、不需要滚动升级、不需要故障接管，需要的是"装上就能跑"。

**这里必须把口径说清楚**：下面关于"为什么多实例困难"的分析，是**从这类项目的公开架构形态（本地文件工作区、进程内状态、单条长连接）出发做的架构层面推断，不是这些项目的官方结论，也不代表它们没有多实例相关的社区方案或讨论**。我只写有把握的部分：工作区是本地文件目录（Agent、Skill、记忆以本地目录 + markdown 为真相源，OryxOS 借用了这个形态）；会话与去重状态在进程内（内存 Map 每个进程各一份）；定时器在进程内（多副本会在同一时刻各醒来一次）；长连接单条（多副本变成 N 条，见 3.5 与 D10）。

至于"这些项目是否已经在主线里提供原生的多实例 / HA 模式"、"社区是否有成熟的外部方案"，**我没有找到可核查的官方来源，因此不做判断**。可以确定的是：这不是这些项目对外宣传的能力重点，公开材料里也很少把"多副本共享状态"当作一等能力来讲。

| 维度 | 单进程/单机自托管（当前主流形态） | 多实例 Agent 底座（阶段二目标） |
|------|-------------------------------|------------------------------|
| 副本数 | 1 | 2 ~ 8（推荐 3），本周期验证上限 32 |
| 工作区 | 本机目录 | 共享卷 + 存储抽象 + 本机执行视图 |
| 事件去重 | 进程内 Map | 共享表（`event_receipts`）+ 唯一约束 |
| 定时任务 | 进程内调度器 | 到点认领 + 理论触发时刻做幂等键 |
| 长连接 | 进程自己持有 | 属主租约，单属主，永不互踢 |
| 升级 / 故障 | 停服换包 / 单点人工重启 | 滚动升级零丢失 / 租约过期自动接管，崩溃轮次标失败 |

### 2.2 为什么这块空白难填：四个结构性原因

"多实例困难"不是工程量问题，是**架构假设**问题。四个原因，每一个都不是加一段代码能解决的。

**第一，状态在本地文件。** 本地文件系统的语义很强：`rename` 原子性、文件锁、`inotify` 事件通知、内存映射一致性。这些语义一旦换到共享卷（NFS / CIFS / 云盘 RWX）就**全部降级**（见 3.4 与 6.2）：`rename` 在单目录内通常仍原子，文件锁和 inotify 不再可靠。把工作区放到共享卷，不是"换个路径"，而是**要把设计假设里那几条不成立的能力删掉**——这是 D7 的全部内容。

**第二，长连接是单进程独占的。** IM 平台的入站连接（飞书长连接、企微智能机器人、钉钉 Stream）通常被当作"一个应用一条连接"来用，但平台侧语义并不统一：有的把旧连接踢掉，有的把消息随机投给多连接中的某一条，有的只认最后一条；Slack 官方甚至明确允许最多 10 条并发 Socket Mode 连接且不保证分发模式（见 3.5）。多副本各自建连，落在哪种语义上不可控，因此"多副本同时连"这条路本身就不通（见 3.5 与 D10）。

**第三，定时器在进程内。** 进程内的 `CronTrigger` 是"每个副本都会算"的：3 个副本在同一个秒醒来 3 次。而墙钟时间不能做幂等键（漂移、GC 停顿、NTP 校正都会让三个副本算出不同的毫秒），必须用**理论触发时刻**作为幂等键（D5）。

**第四，去重状态在内存。** 内存 Map 的生命周期等于进程生命周期：进程一重启，去重记录全丢，平台重推的事件会被再处理一遍。去重状态必须落到共享状态层并带保留窗口（`event_receipts`，保留 24h）。

| 结构性原因 | 单机形态下的做法 | 换成多实例后失效的点 | 需要的替代 |
|-----------|----------------|-------------------|-----------|
| 状态在本地文件 | 本机目录 + 文件锁 + inotify | 锁与 inotify 在共享卷上不可靠 | 共享卷 + 只依赖读写可见/rename 原子（D7） |
| 长连接单进程独占 | 一个进程一条连接 | 多副本 = 多条连接，平台侧行为不一致 | 渠道属主租约（D10） |
| 定时器在进程内 | 进程内调度器 | N 个副本各触发一次 | 到点认领 + 理论触发时刻幂等键（D5） |
| 去重在内存 | 进程内 Map | 每个副本各一份 Map | 共享回执表 + 唯一约束（D3 粒度之一） |

### 2.3 留下的空白

把上面的分析收成一句话：**企业要的是"能横向加副本、升级不停机、故障自动接管"，而开源 Agent 项目普遍把这件事留给用户自己解决。** 这个空白有三个具体表现：

1. **存储档位不区分单机与集群。** 单机档用 SQLite + 本机目录是最合理的默认（零配置），但同一份配置直接拿去跑 3 副本会静默出错——三个副本各自读写自己的 SQLite、各自扫自己的目录，几天后才会有人发现数据分裂。这正是 D11 的由来：**错的存储组合必须在启动时报错，而不是在几天后表现为无法审计的异常。**
2. **"恰好一次"没有被拆成可承诺的粒度。** 笼统宣称 exactly-once 是这类讨论里最常见的表述，但端到端恰好一次通常靠"至少一次 + 幂等"实现（见 3.2）。这直接对应 D3：**只承诺五个粒度**，其余链路写清是"至少一次 + 幂等键"。
3. **升级与故障没有设计语义。** 单进程下崩溃就是重启、升级就是停服；多实例下这两件事必须变成有语义的流程：崩溃轮次**标失败不重放**（D6），停机要**先释放渠道属主租约**再排空在途请求（D10；D12 承接停机链路的交付面）。

> 留给 OryxOS 的判断：这块空白的价值不在于"业界没做"，而在于**它必须用企业已有的基础设施来做**。企业不会为了跑一个 Agent 底座再引入一套 Redis + ZooKeeper；企业会问的是"我的 PostgreSQL 和我的 K8s 能不能把这个撑起来"。阶段二的答案必须是"能"（D2、D12），否则这个空白填不上。

## 三、分布式协调的成熟做法

这一章是整份调研的重心。多实例下真正难的不是"加副本"，而是六个具体问题；每个问题在分布式系统领域都已经有被验证多年的成熟做法。下面逐个给出：**业界做法 → 一致性保证与代价 → 可迁移性**。

### 3.1 跨副本互斥与选主

这是最基础的一件：**同一时刻，让 N 个副本里的一个"持有"某样东西**。它的成熟做法按"依赖什么"分成五类。

| 做法 | 一致性保证 | 故障检测 | 额外依赖 | 运维成本 | 适用面 |
|------|-----------|---------|---------|---------|--------|
| 数据库条件写 / CAS | 由数据库事务隔离级别给出，单行原子 | 靠租约列 `expires_at` 判断，无主动探测 | 无（复用已有数据库） | 最低：不新增组件 | 任意粒度（行级）；OryxOS 全部互斥走这条路（D4） |
| PostgreSQL advisory lock | 会话级或事务级，由数据库持有 | 会话断开自动释放；**没有过期时间概念** | 无 | 低 | 粗粒度选主；长事务场景要小心 |
| Kubernetes Lease 对象 | 由 API Server 的乐观并发（`resourceVersion`）给出 | `renewTime` + `leaseDurationSeconds`，超时即视为持有者失效 | 无（K8s 自带） | 低（但只在 K8s 里可用） | 进程级选主，尤其适合"每个 Deployment 选一个 leader" |
| etcd / ZooKeeper 临时节点 | 由共识协议（Raft / ZAB）给出，强一致 | 会话/租约过期即删节点，watch 立即通知 | **一套共识集群** | 高：独立集群的高可用、备份、监控、权限面 | 需要毫秒级选主与变更通知的大型系统 |
| Redis 分布式锁 | 单实例 `SET NX PX` 语义清晰；多实例的 Redlock 在公开文献中存在安全性争议 | 靠 TTL，无主动探测 | **一套 Redis（要 HA）** | 中高 | 已有 Redis 时的轻量互斥 |

逐条说明：

- **数据库条件写 / CAS。** 形如"`UPDATE ... WHERE owner IS NULL OR expires_at < now()`，检查影响行数是否为 1"。一条语句完成"判断 + 抢占"，不存在"先读再写"的竞态；配合 `expires_at` 列就是**租约**。这是本方案唯一使用的互斥原语（D4）——不需要新依赖，粒度可细到单行。
- **PostgreSQL advisory lock。** 分会话级（`pg_advisory_lock`）与事务级（`pg_advisory_xact_lock`），见 [PostgreSQL 文档·Advisory Locks](https://www.postgresql.org/docs/current/explicit-locking.html)。它与本方案不匹配的地方是**没有过期时间**：锁绑定在会话或事务上，进程假死而连接未断时锁不会被释放。会话轮次可能跑几分钟（LLM 调用很慢），放进一个事务会长时间占用连接，违背 D4"不用悲观长事务"的判断。因此它在本方案里**不用作主互斥**——CAS + TTL 能表达同样的语义，还多了一个可查询、可审计的 `expires_at`。
- **Kubernetes Lease 对象。** `coordination.k8s.io/v1` 的 `Lease` 资源核心字段是 `holderIdentity`、`leaseDurationSeconds`、`renewTime`、`acquireTime`、`leaderTransitions`，见 [Lease API 参考](https://kubernetes.io/docs/reference/kubernetes-api/coordination/lease-v1/) 与 [协调式领导者选举](https://kubernetes.io/docs/concepts/cluster-administration/coordinated-leader-election/)。客户端标准形态是三个时间参数：**租约时长、续约截止、重试周期**，三者依次递减。K8s 组件自身的默认值量级是**秒到十几秒**（如 15s / 10s / 2s），但**这是 K8s 组件的默认行为，与 OryxOS 自己的取值无关**。它的优点是"不用额外组件"，缺点是**只在 K8s 里存在**——OryxOS 也要支持裸机与 docker compose，把核心互斥绑在 K8s API 上会让集群档变成"只能在 K8s 跑"。
- **etcd / ZooKeeper 临时节点。** 共识集群给出最强保证：会话过期即删节点，其他副本通过 watch 立刻感知，不需要轮询。代价是**多一整套需要独立运维的共识集群**（3 或 5 节点、磁盘 fsync、备份、监控、权限）。对"装在企业自己基础设施上"的底座，这个代价只有在真实规模证明必要时才值得（D14 的立场）。
- **Redis 分布式锁。** 单实例下 `SET key value NX PX ttl` 语义清楚；跨多实例的 Redlock 在公开文献里存在明确的安全性争议（[Antirez 的辩护](https://antirez.com/news/101)与 Kleppmann 的质疑是讨论的两侧代表）。但对本方案而言，Redis 的问题不是"锁对不对"，而是**它是一套新的、需要 HA 的状态系统**：一旦引入，就在 PostgreSQL 之外制造了第二份状态，两个状态源之间的一致性（锁在 Redis、业务数据在 PG）会成为新的故障面。

> 留给 OryxOS 的判断：**统一走「CAS 单语句 + TTL 租约」（D4）**，落在已经在部署面的 PostgreSQL 上（D2）。K8s Lease 的价值在于它证明了"租约 + 续约 + 过期接管"这套形状是业界共识，OryxOS 借用这个**形状**，但把落点放在数据库而不是 K8s API——这样同一份代码在 K8s、裸机、docker compose 上行为一致。advisory lock 保留为将来"跨进程粗粒度选主且不介意后台连接"时的备选，阶段二不用。

### 3.2 恰好一次与幂等

第二个问题：**同一件事不能被做两遍**。这是分布式系统里被讨论得最多、也最容易说错的一个。

先把业界共识写清楚：

> **端到端恰好一次（exactly-once）在分布式系统里通常不是靠协议魔法实现的，而是靠"至少一次（at-least-once）投递/执行 + 幂等（idempotency）"实现的。** 消息可能被投递两次，但第二次处理会被幂等键挡住，对外表现为恰好一次。

这个共识有具体的技术形态：

| 机制 | 解决什么 | 关键点 | 典型代表 |
|------|---------|--------|---------|
| 唯一约束 + 幂等键 | 同一件事重复到达时只允许一条记录落库 | 幂等键必须由**所有副本算出同一个值**，不能含墙钟、UUID、进程 ID | 关系库唯一索引；本方案的 `(schedule_id, fire_time)`、`(channel, event_id)`、`session_id` |
| 消费组语义 | 同一分区同一时刻只有一个消费者 | 分区数决定并行度上限；再平衡期间会有重复消费的窗口 | Kafka 消费组（一个分区同时只被组内一个消费者消费） |
| 事务性发件箱（transactional outbox） | "业务数据写库"与"事件对外发出去"不能分别失败 | 两者写进**同一个本地事务**，再由独立投递者从表里取出发送（至少一次 + 幂等消费） | [Microservices.io: Transactional outbox](https://microservices.io/patterns/data/transactional-outbox.html) |
| 去重表 + TTL | 事件去重记录不能无限增长 | 记录带保留窗口，过期清理；窗口内重复即拒绝 | 本方案的 `event_receipts`（保留 24h） |

这个共识有三条工程纪律：**幂等键要"可重复计算"**——若含墙钟、随机数、进程标识，两个副本就会算出两个不同的键，唯一约束形同虚设（这就是 D5 的全部理由：定时任务取 `CronTrigger` 给出的理论触发时刻，而不是执行那一刻的墙钟时间）；**幂等的落点要尽量靠数据库**——应用层"先查再插"有竞态，交给唯一索引（插入冲突即重复）或带条件的单语句更新（影响行数 0 即没抢到）才无竞态；**去重状态要有保留窗口，并且要知道窗口外的语义**——保留 24h 意味着同一条事件 id 在 24h 后重投会被当成新事件，平台侧重推通常在秒到分钟量级，24h 是足够宽的余量。

**事务性发件箱跟本方案的关系**要说清：outbox 解决的是"本地事务 + 对外副作用"的原子性。OryxOS 阶段二的对外副作用主要是**给 IM 用户回消息**，而这个动作天然是"至少一次 + 用户能容忍"的——最坏情况是收到两条相同消息，而不是数据不一致。所以本方案**不引入发件箱表**（那需要额外的投递者与重试状态机），而是把恰好一次承诺集中在 D3 的五个粒度上；这五个粒度每一个都能用"唯一约束 + CAS"精确表达，不需要 outbox。

> 留给 OryxOS 的判断：**明确写"恰好一次只承诺在五个粒度上"（D3）**，其余链路是「至少一次 + 幂等键」。文档里写清边界比笼统宣称 exactly-once 更重要——前者能被验收（Demo C 判据是 `task_executions` 每个 `fire_time` 恰好一行），后者不能。

### 3.3 分布式定时调度

第三个问题：**一个 cron 表达式在 N 个副本上只能触发一次**。业界的四种做法，各有取舍。

| 做法 | 机制 | 优点 | 缺点 | 与本方案的关系 |
|------|------|------|------|--------------|
| Quartz 集群模式 | 全部实例连同一个数据库，`JDBCJobStore` 用行锁（`SELECT ... FOR UPDATE`，可配置 `selectWithLockSQL`）把待触发的 trigger 锁给一个实例；实例故障后由其他实例接管 | 成熟、语义完整、支持 misfire 策略 | 需要一个共享数据库；调度精度受扫描间隔限制；行为集中在框架内部 | **借用形状**（"到点抢一条记录"），不引入框架 |
| XXL-JOB / Airflow HA scheduler | 中心化调度：调度中心负责算时间点并派发，执行器只执行 | 调度与执行解耦，执行器可无状态扩容 | 调度中心自身要 HA（如 Airflow 支持多个 scheduler 同时运行）；多一个组件 | 不采用（引入中心组件，违反 D2） |
| Kubernetes CronJob | 由集群控制器创建 Job 对象 | 无需代码，天然用 K8s 对象做去重 | 去重范围**限于单个 CronJob 对象内**；`concurrencyPolicy` 管的是同一个 CronJob 的前后两次运行是否重叠，不管"跨两个 CronJob 对象的同一时刻"；多个客户端/多集群各自 `kubectl apply` 同名 CronJob 会各建一套 | 不作为核心机制（只在 K8s 上生效，且语义边界与 D5 不一致） |
| 多副本各自扫描 + 到点认领 | 每个副本都算 cron，到点各写一次"认领"，靠 `(schedule_id, fire_time)` 唯一约束决出一个赢家 | 无新组件；三个副本各算各的，数据库裁决；实现简单、可审计 | 每次触发有 N 次失败的插入尝试（N 很小，可忽略）；依赖各副本时钟不至于离谱 | **本方案采用（D4 + D5）** |

关于 Kubernetes CronJob 要补一句保守表述：`concurrencyPolicy` 的三个取值 `Allow` / `Forbid` / `Replace` 管的是**同一个 CronJob 的前一次运行还没结束、下一次触发时刻又到了**时该怎么办，它**不是**跨副本去重机制——因为 CronJob 本身只由集群控制器单点创建 Job，不存在"N 个副本各触发一次"的问题。误解在于把 CronJob 当成"Agent 底座里的定时任务实现"，用它可以解决最简单的场景，但一旦定时任务需要访问 OryxOS 内部状态（会话、Agent 配置、审计带 `instance_id`），就必须回到进程内的调度器 + 共享状态层去重。

把本方案的形状写出来（`schedule_claims` 表，主键 `(schedule_id, fire_time)` 唯一，列含 `owner_instance_id`、`state`、`claimed_at`、`expires_at`、`finished_at`、`error_message`）：

```
所有副本：每个扫描周期算 cron → 得到统一的理论触发时刻 fire_time
   │
   ├─ 副本 1：INSERT ... (schedule_id, fire_time)          → 成功 → state=claimed → 执行
   ├─ 副本 2：INSERT ... 同一 (schedule_id, fire_time)      → 唯一约束冲突 → 放弃
   └─ 副本 3：同上                                        → 唯一约束冲突 → 放弃
   │
执行中：state=claimed → running → succeeded / failed
崩溃：  state=running 而租约（TTL 120s）过期 → 另一副本接管判决，标 failed，不重跑
```

两个细节值得单独说：

- **`state` 枚举穷尽所有结果**：`claimed` / `running` / `succeeded` / `failed` / `skipped`。`skipped` 的存在是为了让"本该跑但因为前置条件不满足而没跑"也有明确落库记录，而不是消失在日志里（对齐审计 day one 落库的原则）。
- **崩溃的语义是"标失败不重跑"**（D6）。这是刻意的：定时任务往往已经产生外部副作用（发过通知、调过工单系统），重跑会产生重复副作用。标失败 + 让运维看到 + 由人决定是否补偿，是唯一安全的语义。

> 留给 OryxOS 的判断：**采用「多副本各自扫描 + 到点认领 + 理论触发时刻做幂等键」**（D4、D5）。它不需要任何新组件；每次触发只多出 N−1 次注定失败的插入，成本可忽略；去重依据落在唯一约束上，可查询、可审计、可验收（Demo C）。

### 3.4 共享文件系统上的变更感知

第四个问题：**一个副本写了工作区文件，其他副本怎么知道**。这件事在单机上根本不是问题（`WatchService` 监听目录，同进程内立即可见），一旦文件放到共享卷，整个语义基础就变了。

先把共享卷的语义讲清楚。NFS 与 CIFS 的**客户端属性缓存**会让"另一个节点写了他看到的"不立即可见；文件锁的语义在网络文件系统上历来是最不可靠的部分之一（NFS 的文件锁经历了从独立 NLM 协议到并入主协议的过程，各实现与挂载选项差异很大，见 [nfs(5) man page](https://man.freebsd.org/cgi/man.cgi?query=nfs&sektion=5)）。`inotify` 是 **Linux 本机内核**机制，它只能观察到"本机文件系统操作"，**观察不到另一个节点通过网络写进来的变化**。

| 机制 | 变更粒度 | 跨节点可见 | 可靠性 | 代价 | 是否适合阶段二 |
|------|---------|-----------|--------|------|--------------|
| 共享卷 + `inotify` / `WatchService` | 文件级 | **不可靠** | 依赖内核与文件系统，跨节点通知缺失 | 低 | **不用**（D8：集群档不装 watcher） |
| 共享卷 + 文件锁 | 无（锁不产生变更事件） | 不可靠（网络文件系统语义差异） | 低 | 低 | 不用（D7：不把锁写进设计假设） |
| 共享卷 + 版本号 + 轮询 | 域级（agents / skills / personas / knowledge...） | **可靠**（读到的就是可见的） | 高：版本号是唯一真相源 | 轮询间隔内的读放大 | **采用**（D8） |
| 共识存储 watch（etcd / K8s API） | 键级 | 可靠（watch 流） | 高 | 多一套集群（etcd）或限定 K8s（API watch） | 不采用（D2、D14） |
| 对象存储 + list 轮询 | 对象级 | 可靠 | 中：list 的结果一致性语义要按对象存储文档确认 | 需改文件面存储实现（无 rename 原子语义） | 不采用（6.2） |

业界在"配置变更感知"这个子问题上给出的成熟答案是**版本号 + 观察（watch）**，K8s 的 ConfigMap / Secret 就是最好的例子：每个对象有 `resourceVersion`，乐观并发靠它做前提条件，客户端靠 `watch` + `resourceVersion` 增量拉取变化。这个形状的可迁移部分是**"版本号是唯一真相源，客户端把自己的已加载版本跟它比对"**；不可迁移的部分是"watch 这个推送通道"——共享卷上没有 watch。

于是本方案的形状就清晰了（`workspace_versions` 表，主键 `domain`，列含 `version`（单调递增）、`updated_at`、`updated_by`）：

```
管理面写路径：落盘（AtomicFiles 原子改名）→ bump 对应域版本号（一个事务）
各副本：每 1s 轮询 workspace_versions：
        已加载版本 == 表中版本 → 什么都不做（绝大多数轮次）
        已加载版本 <  表中版本 → 重载该域（agents / skills / personas / knowledge）
运维直接改盘（绕过版本号）：POST /api/v1/workspace/refresh（逃生舱）→ 强制各副本重载
```

三个设计要点：**版本号是唯一真相源，不是"事件流"**（事件推送会丢、会乱序、会重复；版本号单调递增，漏一次轮询不会丢变更）；**轮询成本可算**（成本 = 副本数 × 1/间隔 次主键点查，默认 1s、3 副本 = 3 QPS 级，与业务量无关）；**必须有逃生舱**（只要运维可能绕过应用直接改盘，就需要一个"忽略版本号、强制重载"的入口——没有逃生舱的版本号方案，在第一次人工介入时就会变成"数据对了但副本不知道"）。

> 留给 OryxOS 的判断：**共享文件面上做变更感知，版本号 + 轮询比事件推送更可靠**（D8）。这不是"因为实现简单所以选它"，而是"共享卷的语义不支持可靠的推送，所以版本号 + 轮询是唯一在所有共享存储实现上都正确的形状"。代价是变更传播有确定上限（默认 1s 轮询 → P99 ≤ 3s），这个上限是写在量级目标里、可验收的（Demo D）。

### 3.5 长连接的单属主

第五个问题：**同一条渠道的长连接，只能有一个副本持有**。这一条比前四条更棘手，因为它的约束来自外部平台，不由 OryxOS 决定。

IM / 消息平台对"同一个应用建立多条连接"的语义**并不一致**，公开可核查的行为大致分三类：

| 平台侧语义 | 表现 | 对底座的约束 |
|-----------|------|------------|
| 互踢（新连接挤掉旧连接） | 新副本启动建连成功后，旧副本的连接被断开 | **绝不能"多副本都连"**：会造成旧副本反复重连、消息在断连窗口丢失，最坏情况是所有副本互相踢、谁也连不稳 |
| 只认最后一条 / 单连接独占 | 平台侧把应用视为一个连接端点 | 同"互踢"，且可能表现为静默的"消息只到其中一条" |
| 随机或轮询投递到某一条连接 | 两条连接都能收到消息，但一条消息只到其中一条 | 消息不丢但会"分裂"到多个副本，需要应用层统一处理点 |

可以确认的一个具体例子是 **Slack 的 Socket Mode**：Slack 官方允许最多 10 条并发 Socket Mode 连接且不保证 payload 分发模式；而社区实现（如 [openclaw#79938](https://github.com/openclaw/openclaw/pull/79938) 对共享 Socket Mode 连接告警）选择只维持一条连接。**官方语义与客户端实践不一致**，这正是底座不能依赖任何一种平台语义的理由。至于**飞书长连接、企微智能机器人、钉钉 Stream 在同应用多连接下的确切行为**，我没有找到可核查的官方说明，因此**不做断言**。

面向"平台语义未知"的设计只有一个答案：**属主租约**（D10）。形状如下（`channel_ownerships` 表，主键 `channel_name`，列含 `owner_instance_id`、`lease_id`、`acquired_at`、`expires_at`、`last_renew_at`）：

```
启动/接管：副本 A 用 CAS 认领 channel_name（WHERE owner IS NULL OR expires_at < now()）
          抢到 → 建长连接 → 每 10s 续约（TTL 30s）
          没抢到（副本 B/C）→ 待命，不建连（关键：不建连就永不互踢）
崩溃：    不再续约 → 30s 后租约过期 → 副本 B 认领成功 → 建连
停机：    SIGTERM → 主动释放租约（接管秒级到位，不必等 TTL 过期）→ 再排空在途请求
```

两条纪律：**"接管只发生在租约过期之后"，不能提前**——提前接管意味着旧属主可能还活着、还持有连接，这是互踢与双回复的唯一来源；宁可多等 30s，也不冒"两个副本同时连着同一个渠道"的风险（与会话轮次租约 60s 同形状，只是 TTL 更短，代价是接管窗口内该渠道无法处理消息）。**停机流程必须先释放租约**——若只是"关连接、退场"，接任者要等 TTL 过期才能接手（最长 30s 的渠道不可用窗口）；主动释放把它压到秒级，这是 D10（D12 承接停机链路的交付面）与 M2 里程碑的验收点。

业界的对应思路是 **Kafka 消费组的再平衡**：一个分区同时只被组内一个消费者消费，消费者进出触发重新分配。它证明的是同一个形状——**"独占 + 失效后重新分配"是长连接 / 长任务类资源的标准做法**；区别在于 Kafka 的重新分配由 broker 侧的 group coordinator 负责，OryxOS 没有协调者，用数据库上的租约把这个角色替代掉。

> 留给 OryxOS 的判断：**长连接必须做属主租约，接管只发生在租约过期后**（D10）。非属主副本**根本不建连**——这是"永不互踢"的实现方式，也是本方案对"平台语义未知"的唯一稳健回应。停机主动释放租约把接管从"等 TTL"压缩到"秒级"。

### 3.6 本机执行视图问题

最后一个问题看起来最小，却最容易在生产上咬人：**共享卷上的路径，不是本机可执行路径**。

场景很具体：`.oryxos/` 工作区挂载为共享卷，某个 Agent 目录里有 Skill 附带的脚本，或 Tool 需要读取工作区里的文件。共享卷在容器里的挂载点可能是 `/data/.oryxos`（K8s PVC 挂载），也可能是宿主机上的 `/mnt/nfs/oryxos`（compose bind mount），甚至可能是 Windows 共享路径（CIFS，路径分隔符与大小写语义都不同）。而工作区里记录下来的引用（例如 Agent 目录里的相对软连接、`AGENT.md` 里引用的路径）是**逻辑路径**——它是"相对于工作区根的位置"，不是"这台机器上的绝对路径"。

两个具体的坑：

1. **软连接在共享卷上的解析风险。** 软连接的目标是"相对于连接所在目录的路径"。这在单机上很好用，跨机器就有两类问题：一是**目标可能指向本机不存在的路径**（如果连接是绝对路径，且原机器与当前机器的挂载点不同）；二是**软连接的解析结果超出了工作区根**（无论是有意还是无意），在共享卷上这个风险被放大，因为工作区的内容可能由多个来源写入。宪章原则六要求软连接**必须校验真实路径**（`toRealPath()` 仍在白名单根内，且只允许指向 `.oryxos/skills/` 的相对软连接），在共享卷下这条纪律要更严而不是更松。
2. **逻辑路径与执行路径分离。** 如果业务代码把工作区里的逻辑路径直接当文件路径交给 Shell 执行（或者交给 `Path.of` 绕回默认存储），在单机上恰好能跑，在共享卷上会失败或更糟——**静默跑到另一个位置**。这就是工作区存储约束（`CLAUDE.md` 042 节）的由来：业务代码只能通过 `WorkspaceStorage.root()/resolve()` 拿路径，需要真正执行时必须取**本机执行视图**（`nativePath`）。

| 概念 | 含义 | 谁用 | 在共享卷下的要求 |
|------|------|------|----------------|
| 逻辑路径 | 相对于工作区根的位置（例如 `agents/ops-agent/AGENT.md`），跨副本一致 | 版本号总线、Agent/Skill 引用、审计记录 | 可跨副本比较、可落库；**不是本机可执行路径，不能用于真实路径校验** |
| 本机执行视图（`nativePath`） | 该逻辑路径在本实例上真实可执行的本地路径 | 文件 Tool、Shell Tool、脚本执行 | 必须由存储抽象给出，业务代码不得自行拼接 |
| 保留路径 | `.workspace-*` 与 `.staging` | 底座内部 | 业务 Agent 不得占用；跨副本共享时必须被视为内部路径 |

这个问题在业界被踩过很多次，形态都类似：**把"文件在某个位置"和"文件能在这台机器上被这样打开"混为一谈**。经典的失败模式包括：容器里挂载点变了导致配置里的绝对路径全部失效；软连接指向构建机路径导致运行机读到空目录；多人共享的 NFS 目录里出现指向别的用户的软连接（这是安全事件而不是功能故障）。它们的共同修复方式都是**引入一层"逻辑 → 本机"的解析**，而不是让每个调用点各自拼路径。

> 留给 OryxOS 的判断：**"逻辑路径 / 本机执行视图"必须显式分开，并落在存储抽象里**（D9）。共享模式启动先校验 `.workspace-id`，不匹配**拒启动、绝不回退本地**（否则就是数据分裂）；软连接校验在共享卷下按原则六从严；业务代码不出现裸文件 API。

### 3.7 六个问题的收敛表

把本章六个问题收成一张表，作为第六章取舍的输入：

| 问题 | 业界成熟做法 | 需要额外依赖吗 | OryxOS 的选择 | 对应决断 |
|------|------------|--------------|--------------|---------|
| 跨副本互斥与选主 | CAS 条件写 / advisory lock / K8s Lease / etcd / Redis 锁 | etcd、Redis 需要；CAS 与 advisory lock 不需要 | 统一 CAS 单语句 + TTL 租约，落在 PostgreSQL | D2、D4 |
| 恰好一次与幂等 | 唯一约束 + 幂等键、消费组、outbox、去重表 | outbox 需要投递者；消费组需要队列 | 唯一约束 + 幂等键；去重表带 TTL；不引 outbox | D3、D5 |
| 分布式定时调度 | Quartz 集群行锁、中心化调度、K8s CronJob、多副本扫描 + 认领 | 前三者都需要额外组件或平台 | 多副本扫描 + 到点认领 + 理论触发时刻 | D4、D5 |
| 共享文件变更感知 | watch（etcd/K8s API）、inotify、版本号 + 轮询 | watch 需要共识存储 | 版本号总线 + 轮询 + 逃生舱 | D7、D8 |
| 长连接单属主 | 消费组再平衡思路；平台侧限制 | 队列需要额外组件 | 属主租约，非属主不建连，停机先释放 | D10；D12 承接停机链路的交付面 |
| 本机执行视图 | 引入"逻辑 → 本机"解析层 | 无 | 存储抽象 + `nativePath`，共享模式校验标识 | D9、D11 |

> 留给 OryxOS 的判断：六个问题里有五个的答案是「复用数据库」（CAS 单语句 + TTL 租约 + 唯一约束 + 版本号轮询），第 6 个（本机执行视图）是文件面纪律（D9）——**没有一个需要新增中间件**。这不是巧合——分布式协调领域里，"用一个已有的事务型存储做条件写 + 租约"这条路的适用范围比想象中大得多；引入 etcd / Redis / 消息队列真正换来的是**共识级的低延迟通知**与**队列化的流量削峰**，而阶段二的量级目标（2 ~ 8 副本、≥ 1000 并发 Session）都还远没到需要它们的程度。

## 四、企业为什么需要多实例底座

第三章讲的都是"怎么做"。这一章回答"为什么非做不可"，论证方式跟阶段一调研第三章一致：**锚在不变的约束上，而不是锚在一个技术概念上。**

### 4.1 可用性：Agent 已经嵌进业务流程

阶段一的位置是"一个部门试点"，Agent 挂了只是助手暂时不可用；阶段二的位置是"服务全公司"，Agent 已经嵌进业务流程：审批流里的一个环节由 Agent 处理，工单系统的自动分派由 Agent 完成。这时候**停服等于业务停摆**——不是体验下降，是流程卡住。

单实例有一个无法用工程手段绕过的性质：**它是一个单点**。无论进程多稳定、服务器多可靠，重启、升级、宿主机维护、机房网络抖动都会让它不可用。多实例的价值不是"每个实例更稳"，而是**把"整体不可用"从"任何单点故障"降级为"多数副本同时故障"**。集群档目标因此写成 99.9%（3 副本 + PostgreSQL 高可用），并明确：**可用性下限由数据库侧决定**——这是诚实的表述，因为中心协调意味着数据库不可用则集群档拒服务（6.4）。

### 4.2 容量：单实例上限与部门数量增长

单实例的容量上限来自三处：JVM 堆与线程、数据库连接数、单进程内所有串行化操作（会话轮次、调度扫描、事件去重）的锁竞争。阶段一的量级是"单集群 ≥ 10 个 Agent、≥ 100 并发 Session"，对一个部门够用；阶段二的目标是"≥ 100 个 Agent、≥ 1000 并发 Session"——而这只是本周期要验证的量级，不是天花板。

关键是**增长曲线的形状**：企业从试点走向全公司时，Agent 数按部门数增长、Session 数按员工数增长，都不是"翻一倍"而是"每多一个部门就多一份"。垂直扩容能顶一阵，但受单进程锁竞争与数据库连接数限制，且换机器的成本与风险远高于加一个无状态副本。

> 一个具体判断：**垂直扩容的上限是单进程内串行点的吞吐，而不是 CPU**。阶段二把会话轮次、定时认领、事件去重这些串行点全部搬到数据库上，正是为了把"单进程内的串行"换成"数据库上可并发的行级互斥"。

### 4.3 变更：不停机升级与配置灰度

企业的 Agent 底座不是"装完就不动"的系统，它要跟着业务变：新增部门 Agent、调整 prompt、绑新 Skill、换 Provider、改工具治理策略。这些变更分四类：

| 变更类型 | 单实例的做法 | 需要的多实例语义 |
|---------|------------|----------------|
| 代码/镜像升级 | 停服 → 换包 → 起服，期间不可用 | 滚动升级：`maxUnavailable: 0` / `maxSurge: 1`，在途请求排空，零消息丢失 |
| 工作区内容变更（Agent/Skill/人格） | 写完即生效（同进程读文件） | 版本号总线 + 轮询，P99 ≤ 3s 生效；运维直接改盘走逃生舱 |
| 知识库重建 | 重建期间检索可能不可用 | 代次化：检索恒读已提交代次，重建期间旧代次继续服务 |
| 配置/密文变更 | 重启生效 | Secret 引用 + 滚动升级；主密钥多副本一致 |

后三行不是"有副本就能解决"，而是**在有多副本之后才出现的新问题**：单机上"写完即生效"是免费的，多实例上需要版本号 + 轮询（D8）；单机上"重建期间检索短暂不可用"可以接受，多实例上一个副本在重建而另两个在服务，检索必须读到**一致的已提交代次**，否则不同副本返回不同结果。

### 4.4 治理与合规：跨实例审计完整、故障可追溯

这是 OryxOS 最核心的差异化能力（审计表 day one 落库，原则五）在多实例下最难的地方。企业要回答的问题在单机与多实例下不同：

| 企业要回答的问题 | 单实例下 | 多实例下 |
|----------------|---------|---------|
| 这次会话是谁处理的 | 唯一实例，不用问 | **哪个 `instance_id`**，且要能查到它的 `host` / `version` |
| 一次消息处理跨了几个副本 | 不适用 | 轮次可能被接管（崩溃后重发），**审计行要能拼回同一条链路**（D13） |
| 一个定时任务执行了几次 | 不适用 | `task_executions` 每个 `fire_time` 恰好一行，且带 `instance_id` |
| 崩溃的那一轮发生了什么 | 日志里翻 | 崩溃轮次**标失败落库**（`state=failed` + `last_error`），可审计 |
| 哪个副本申请过渠道属主 | 不适用 | `channel_ownerships` 的 `owner_instance_id` 与 `acquired_at` 全程留痕 |

多实例**放大了审计的价值，同时提高了审计的门槛**。可审计不是"多写一列 `instance_id`"，而是"跨副本的链路能拼起来"（D13：审计行、日志、trace span 同 `traceId`、同计时区间、带实例标识）。这一条做不到，企业就没法回答"这个 Agent 到底做了什么、谁批准的"——而这是严监管企业过审的硬条件。

### 4.5 结论：锚在不变的约束上

> 无论 Agent OS 这个概念怎么演变、中间层最后是独立存在还是被某一层吸收，**"企业要一个能横向扩、故障能接管、升级不停机的 Agent 底座"这件事不会变。**

它锚在四个不会变的约束上：企业从试点走向全公司是**必然**（阶段一调研第三章的论证）；可用性要求不会因为 Agent 变聪明而降低——**业务嵌得越深，要求越高**；容量要求随部门数与员工数增长，而**垂直扩容有单进程串行上限**；合规要求不会因为技术演进放松——**跨实例审计完整、故障可追溯**是过审硬条件。

这四条里没有一条依赖"Agent OS 这个词会不会继续流行"。这就是本套文档跟阶段一调研共用同一个论证结构的原因。

## 五、Java 生态在这件事上的位置

### 5.1 Java/Spring 生态现成的分布式能力

Java 生态在"多实例共享状态"这件事上积累了非常完整的一层设施。阶段二不需要重新发明任何协调原语，只需要**选对哪些复用、哪些不引入**。

| 能力 | 代表组件 | 阶段二是否复用 | 说明 |
|------|---------|--------------|------|
| 关系型状态与事务 | Spring Data JPA / `JdbcTemplate` / `@Transactional` | **复用** | 会话、审计、租约、回执、版本号落在同一套连接池与事务上；`instance_id` 追加列走 Flyway |
| 条件写与唯一约束 | PostgreSQL `UPDATE ... WHERE`、唯一索引、`ON CONFLICT` | **复用**（核心原语） | D4 的全部实现基础；不需要新依赖 |
| 迁移协调 | Flyway | **复用** | 迁移开始时获取数据库迁移锁（PostgreSQL 上为 advisory lock），拿不到按 1s 间隔重试（默认 50 次）——多实例并发迁移只有一个执行、其余等待重试；这是**短事务、框架内部行为**，与 3.1「不用悲观长事务、advisory lock 不作主互斥」不矛盾（[Flyway: Lock retry count](https://documentation.red-gate.com/flyway/reference/configuration/flyway-namespace/flyway-lock-retry-count-setting)） |
| 应用内调度 | Spring `TaskScheduler` / `@Scheduled` / Quartz API | **复用 `CronTrigger`** | 理论触发时刻的来源（D5 的幂等键）；不用 Quartz 集群作业存储 |
| 优雅停机 | Spring Boot `server.shutdown=graceful` + `spring.lifecycle.timeout-per-shutdown-phase` | **复用** | 在途请求排空的基础（[Spring Boot: Graceful Shutdown](https://docs.spring.io/spring-boot/reference/web/graceful-shutdown.html)） |
| 并发模型 | JDK 21 virtual thread | **复用** | 同步阻塞 + 虚拟线程处理并发（原则七）；续约与轮询在调度线程上同步阻塞 |
| 指标与追踪 | Micrometer / Prometheus + Grafana、OTel | **复用** | 实例视图、接管次数、传播延迟的观测面 |
| 容器编排协调 | Kubernetes Lease | **不复用** | 借用"租约 + 续约 + 过期接管"的形状，落点放在数据库，避免集群档只能在 K8s 跑 |
| 服务注册与配置中心 | Nacos / Eureka / Spring Cloud Config | **不引入** | `instances` 表 + 心跳 + 版本号总线已覆盖注册、健康与配置传播（6.1） |
| 限流熔断 / 链路追踪 | Sentinel / Resilience4j / SkyWalking / Zipkin | **不引入** | 阶段二不做限流；追踪复用 OTel 可选导出（`oryxos.otel.endpoint`，不配零开销），不另搭一套 |
| 分布式缓存与锁 / 共识 / 消息队列 | Redis（Redisson）/ ZooKeeper / etcd / Kafka / RocketMQ | **不引入** | 见 6.1；OryxOS 的入站不是队列，回执去重用共享表 |

### 5.2 为什么 Java 做多实例是顺手的

四个具体支点：

1. **连接池与事务是现成的、经过验证的。** 多实例协调的核心原语是"一条带条件的写语句 + 事务"，而 Java 生态对这件事的支持是三十年积累：HikariCP 的连接管理、Spring 的声明式事务、JDBC 的批处理与超时。**协调原语的实现成本几乎全在 SQL 语句本身**，不在框架适配。
2. **调度与定时设施成熟，而且天然是同步的。** `CronTrigger` 给出**理论触发时刻**（D5 的关键依赖），`ScheduledExecutorService` 提供续约与轮询所需的固定周期任务。这里有一个容易被忽略的巧合：**分布式协调本来就是"阻塞等待 + 定期重试"的形状**，恰好是同步模型（原则七）最擅长的地方，不需要异步 / 反应式。
3. **运维工具链可以直接复用。** 实例视图、指标、日志、JFR、Arthas、Prometheus + Grafana，企业现有体系不需要为它单独搭一套——这直接支撑 4.4 的可审计要求。
4. **K8s 的原生面在 Java 侧是成熟的。** 探针、`terminationGracePeriodSeconds`、`preStop`、RWX PVC、Secret → 环境变量都有清晰的接入方式（D12 的 Helm Chart 就是把这套面固化下来）。

Java 侧容易踩的坑也很具体，阶段二必须明确规避：

| 坑 | 症状 | 规避方式 |
|----|------|---------|
| 连接池与虚拟线程配比失当 | 虚拟线程数远超连接池容量时大量线程阻塞在 `getConnection()`；池开太大又会压垮数据库 | 连接池大小按**数据库实际并发能力**设，不按虚拟线程数设；相关讨论见 [loom-dev 邮件列表](https://mail.openjdk.org/pipermail/loom-dev/2024-July/006997.html) 与 [HikariCP#2151](https://github.com/brettwooldridge/hikaricp/issues/2151) |
| 过度依赖容器内文件锁 / `WatchService` | 本机能跑，共享卷上静默失效 | D7（只依赖读写可见 + rename 原子）、D8（集群档不装 watcher） |
| 用应用层"先查再写"做互斥 | 两个副本同时通过检查，产生重复副作用 | D4：互斥必须是单语句 CAS，靠影响行数判定 |
| 用墙钟时间做幂等键 | 各副本算出不同键，唯一约束不生效 | D5：用 `CronTrigger` 的理论触发时刻 |
| 长事务持有锁 | 连接池被拖垮，接管变慢 | 租约在同一个短事务里续约（一条 `UPDATE`），不把 LLM 调用时长放进事务 |

### 5.3 OryxOS 的判断

> **不重新发明协调原语**：所有跨副本互斥都落在已经存在于部署面的 PostgreSQL 上（CAS 单语句 + TTL 租约，D2 + D4）。也**不引入** Java 生态里那套需要额外中间件的方案（Nacos / Redis / ZooKeeper / etcd / 消息队列），除非真实数据证明必要（D14）。

三层理由：**其一**，"租约 + 续约 + 过期接管"这套形状被 K8s Lease、etcd、Quartz、Kafka 消费组反复验证过，OryxOS 借用形状不缺任何东西；真正要自己写的是"落在自己的表结构、状态枚举与审计口径上"这一层，而用 Nacos 或 Redis 反而会把协调状态搬到别处，与审计口径脱节。**其二**，复用已有依赖是"少一边界"而不是"省一点工作量"——多一个中间件就多一套高可用、监控、备份、权限与审计面（6.1 详述）。**其三**，Nacos 解决的是"几十个微服务的注册发现与配置推送"，Redis 解决的是"热点数据的高并发读写"，消息队列解决的是"削峰与多消费者解耦"，而阶段二的量级（2 ~ 8 副本、≥ 1000 并发 Session）都不需要这些；真到需要时，引入位置与判断信号见 6.1。

## 六、OryxOS 的取舍

前面五章把业界做法和企业约束都摆清了。这一章逐条给出取舍，并对齐 D2、D7、D8、D11、D3、D14。

### 6.1 为什么复用 PostgreSQL 而不引入 Redis / ZooKeeper / etcd / 消息队列

| 方案 | 能解决什么 | 代价（多一个中间件） | 何时才值得引入 |
|------|-----------|-------------------|--------------|
| **PostgreSQL CAS + 唯一约束 + TTL**（采用） | 跨副本互斥、选主、恰好一次幂等、去重、版本号 | **无新增组件**；代价是数据库成为协调单点（6.4），且轮询带来读放大（6.3） | — （就是本方案） |
| Redis | 低延迟分布式锁、会话/热点缓存、计数器 | 多一套 HA（哨兵/集群）、持久化策略与数据丢失窗口、内存容量规划、监控、备份、权限面；且它在 PostgreSQL 之外制造**第二份状态**，两者一致性成为新故障面 | 当实测证明"数据库上的 CAS 成为吞吐瓶颈"（例如锁争抢导致 P99 恶化），且此时需要的是**毫秒级锁**而不是更强的持久化语义 |
| ZooKeeper / etcd | 共识级选主与毫秒级 watch 通知；配置分发 | 多一套共识集群（3 或 5 节点、磁盘 fsync 敏感、独立备份与监控、独立权限面）；选主与业务状态分居两处 | 当集群规模大到"轮询 1s 的读放大不可接受"（例如副本数上百），且企业已有运维好的共识集群 |
| 消息队列（Kafka / RocketMQ 等） | 入站事件排队、削峰、消费组天然去重、跨系统解耦 | 多一套集群 + topic 规划 + 消费者组运维；入站路径从"平台长连接直推"变成"平台 → 队列 → 实例"两跳，故障面增加 | 当入站量级远超单次处理的承载能力、必须靠排队削峰时；或当入站来源从"平台长连接"扩展为"企业内多个系统的事件总线"时 |
| 对象存储 | 大文件的低成本、高持久化存储；审计归档 | 文件面存储实现必须放弃 **rename 原子语义**，并让"本机执行视图"问题更复杂（对象没有"本机路径"） | 当审计归档、导出包、知识原始文件等**只读大对象**的体量成为存储成本主体时，作为归档层引入（而不是作为工作区的真相源） |

> **协调基质复用 PostgreSQL（D2）**。判断的依据不是"数据库够快"，而是"**这些协调语义关系库本来就都有**"：条件写（`UPDATE ... WHERE`）、唯一约束（`UNIQUE`）、TTL 判断（`expires_at` 列 + `now()`）、行级可见性（事务隔离级别）。有了这四样，跨副本互斥、选主、恰好一次幂等、去重、版本号五件事不需要任何新组件。每多一个中间件就多一套高可用、监控、备份、权限与审计面——这是 D2 与 D14 的完整理由。

#### 6.1.1 与阶段一"未来分布式"设想的收敛说明

阶段一的公开文档里已经有一版**粗略的分布式设想**，本套文档必须明确回应它，否则读者会觉得前后矛盾。两处出处：

1. [../oryxos-docs/IndustryResearch.md](../oryxos-docs/IndustryResearch.md) 第 6.1 节设想：会话与短期上下文外置到 **Redis 一类内存存储**、长期记忆与 Skill 库外置到 **PostgreSQL**、审计日志与大文件外置到**对象存储**、Agent 配置与租户信息外置到**配置中心和数据库**；第 6.4 节提到分布式用 **Nacos**（注册与配置）、Sentinel、Spring Cloud Gateway、SkyWalking。
2. `docs/oryx-vs-hermes-分析报告.md` 复述了同一套设想，并把分布式协调留给 **Nacos / ETCD**。

阶段二的结论是**收敛**，按三组对照说明：

| 组 | 阶段一设想 | 阶段二的收敛 | 理由 |
|----|-----------|-------------|------|
| 会话与短期上下文 | 外置到 Redis 一类内存存储 | **不引 Redis**：会话已经在关系库里（阶段一的 `sessions` 表），跨副本串行靠的正是同一张表上的 CAS 租约（`session_turn_leases`） | 引 Redis 会在 PostgreSQL 之外制造**第二份状态**与两套一致性语义：会话历史在关系库、并发控制锁在 Redis，二者之间的时序无法用单个事务表达。而阶段二需要的正是"用一条事务同时完成'抢占轮次'与'写入会话状态'"，这只有在同一个存储里才成立 |
| 文件面（记忆 / Agent 配置 / Skill） | 长期记忆与 Skill 库外置到 PostgreSQL，审计与大文件外置到对象存储 | **不上对象存储**：工作区（Agent 目录、Skill、人格、知识索引）整体放**共享卷**，经存储抽象访问 | 对象存储没有 **rename 原子语义**（本方案文件面唯一依赖的原子操作，D7），会把"多文件发布"的原子性设计推倒重来；同时对象没有"本机路径"，会让 3.6 的**本机执行视图**问题从"解析一层"变成"必须先物化到本地"，复杂度和延迟都更高。对象存储是**归档层**的候选（见 6.1 表末行），不是工作区的真相源 |
| 实例注册与配置中心 | Agent 配置与租户信息外置到配置中心（Nacos）与数据库 | **不用 Nacos / ETCD**：`instances` 表 + 心跳（10s / 30s）+ `workspace_versions` 版本号总线 + 轮询（1s）已覆盖三件事 | 实例注册与健康 = `instances` 表 + 心跳；配置传播 = 版本号总线 + 轮询；两者都在数据库里，不需要一个独立的注册配置中心，也不需要共识集群 |

统一收口：

> **每多一个中间件就多一套高可用、监控、备份、权限与审计面，而阶段二需要的协调语义关系库都已具备。** 这是从"设想"收敛到"设计"的核心依据——阶段一的设想是从"分布式系统一般长什么样"出发的直觉；阶段二是从"**OryxOS 已经有 PostgreSQL、企业已经有 K8s**"这个具体约束出发的工程选择。

**"真实数据证明瓶颈时在何处引入"** 也写清楚（口径与插入位置见 TechnicalSolution 的边界与演化章节，本节引用其 19.3 小节）：

| 观察到的信号 | 说明什么 | 引入什么、落在哪一层 |
|------------|---------|-------------------|
| CAS 争抢导致轮次接管 P99 恶化，且数据库 CPU 不是瓶颈 | 行锁争抢成为串行点 | 先做实现层优化（缩小事务范围、减少续约频率）；仍不足时引入 Redis 承载**锁**，但会话状态仍留在 PostgreSQL |
| 轮询读放大不可忽略（副本数 × 1/间隔 接近数据库容量可观比例） | 版本号轮询成为读压力源 | 先调大轮询间隔（牺牲传播延迟）；仍不足时引入 watch 通道（etcd 或 K8s API），版本号仍是真相源 |
| 入站事件量级远超单次处理承载能力 | 需要削峰 | 引入消息队列，把"平台直推"改为"投递到队列 + 实例消费"，回执去重语义保持不变 |
| 只读大对象（归档、导出）成为存储成本主体 | 存储成本问题，不是协调问题 | 引入对象存储作为**归档层**，工作区真相源不变 |

> **诚实写出这次收敛的代价**（不做隐藏）：
>
> 1. **数据库成为协调单点。** CP 取向的直接后果：PostgreSQL 不可用则集群档拒服务（6.4）。可用性上限由数据库侧的高可用方案决定，不由 OryxOS 决定。
> 2. **轮询放大数据库读压力。** 版本号轮询是"副本数 × 频率"的固定读负载，与业务量无关；好消息是量级小（主键点查）且可调，坏消息是它不会因为系统空闲而消失。
> 3. **共享卷语义不如对象存储宽松。** 共享卷要求企业提供 RWX 存储（NFS / CIFS / 云盘 RWX），并接受"只依赖读写可见 + rename 原子"的能力降级；跨可用区的共享卷延迟与一致性差异需要企业侧评估（见 [../oryxos-docs/SharedVolumeGuide.md](../oryxos-docs/SharedVolumeGuide.md) 的支持矩阵）。

### 6.2 文件面：共享卷 vs 对象存储 vs 数据库存文件

| 维度 | **共享卷（RWX）** | **对象存储** | **数据库存文件** |
|------|-----------------|-------------|----------------|
| 适用 | 工作区：Agent 目录、Skill、人格、知识索引——**多副本读写同一份目录树** | 只读大对象：归档、导出包、附件、知识原始文件 | 小配置、结构化状态 |
| 原子性 | **单目录内 rename 原子**（本方案唯一依赖的原子语义，D7） | 对象写入是整体替换；**无目录 rename 语义** | 事务原子 |
| 变更感知 | 只靠"读得到"，事件通知不可靠 → 必须版本号 + 轮询（D8） | 靠 list / 版本号轮询；list 一致性语义需按厂商文档确认 | 靠事务 + 版本号 |
| 本机执行视图 | 有（挂载点 → 本机路径，经存储抽象解析） | **没有**"本机路径"，必须先物化（下载）到本地 | 没有；需先落盘 |
| 文件锁 / inotify | **不可靠**（网络文件系统语义差异） | 不适用 | 不适用 |
| 与 Agent 目录形态的契合 | 高（一个目录 = 一个 Agent 天然映射） | 低（对象键不是目录树） | 低（文件内容入库会更难与"目录 = Agent"形态对齐） |
| 成本模型 | 企业已有存储（PVC / NFS） | 按量计费 + 网络流量 | 数据库存储 + 备份体积膨胀 |
| 阶段二定位 | **采用**（工作区真相源） | 不采用（归档层候选，见 6.1） | 不采用（工作区不用数据库存文件） |

选择共享卷的理由收成三条：**(1)** 它跟"一个目录 = 一个 Agent"的形态天然契合（原则四），换对象存储意味着重新定义 Agent 的组织方式；**(2)** `rename` 原子性是实现"原子落盘"（`AtomicFiles`）的最便宜手段，对象存储没有等价物；**(3)** 本机执行视图在共享卷上是"解析一层"，在对象存储上是"先下载再执行"，后者对 Tool 执行（文件、Shell）是不可接受的延迟与复杂度。

代价是**必须接受一组纪律**（D7）：只依赖**读写可见 + rename 原子**，不依赖文件锁、不依赖 inotify、不依赖内存映射一致性；全部写入走**原子改名**落盘；多文件发布写明"**可恢复但不是目录原子快照**"；运行输出按 Agent/run 隔离；`.workspace-*` 与 `.staging` 为内部保留路径（业务不得占用）。这些纪律的意义是：**把"不保证的能力"从设计假设里删掉，才能在所有共享存储实现上都正确**——而不是"在 NFS 上能跑，在 CIFS 上偶发故障"。

### 6.3 轮询 vs 推送

| 维度 | 推送（事件 / watch） | **轮询 + 版本号（采用，D8）** |
|------|-------------------|---------------------------|
| 传播延迟 | 低（毫秒级） | 有确定上限：轮询间隔 × 2（默认 1s → P99 ≤ 3s） |
| 可靠性 | 依赖通道：共享卷上无可靠通道；共识存储上有 | 只依赖"读得到"，任何共享存储实现上都成立 |
| 漏事件 | 会（断线、丢事件、跨节点不可见） | 不会（版本号单调递增，漏一次下轮补齐） |
| 成本模型 | 长连接/订阅的内存与心跳成本 | **副本数 × (1 / 轮询间隔) 次主键点查**，与业务量无关 |
| 复杂度 | 需要处理重连、重复、乱序、补偿 | 一次比对 + 必要时重载 |
| 逃生舱 | 不适用 | 必需（运维直接改盘后强制重载） |

**为什么阶段二选轮询 + 版本号**：这不是在"更好的方案"和"更简单的方案"之间做取舍，而是**共享卷根本不提供可靠的推送通道**（3.4）。在"没有可靠推送"的前提下，版本号 + 轮询是唯一在所有共享存储实现上都正确的形状。K8s 的 ConfigMap / Secret 用 `resourceVersion` + watch 提供了推送，但那是**共识存储**的能力（API Server 后面的 etcd），不是文件系统的能力。

**轮询的成本模型要算清**：成本与"副本数"和"轮询频率"成正比，与"业务量"无关。默认 1s、3 副本 = 3 QPS 的主键点查（单行）；这个负载在 PostgreSQL 上可以忽略，且不随业务增长而增长。它的真正上限来自副本数：如果副本数扩到上百，读压力就会进入需要评估的区间——这也是 6.1 表格里"何时引入 watch 通道"的判断信号之一。

### 6.4 CP 而不是 AP

中心协调的直接后果：**数据库不可用则集群档拒服务**（fail-closed）。

| 维度 | CP 取向（采用，D11） | AP 取向（不采用） |
|------|-------------------|-----------------|
| 数据库不可用时的行为 | 拒服务（启动与运行期都是 fail-closed） | 静默降级：各副本用自己的本地状态继续跑 |
| 最坏结果 | 一段时间不可用，恢复后状态一致 | **数据分裂与重复副作用**：两个副本各自认领同一件事、审计对不上、事后无法追溯 |
| 与企业的对齐 | 可用性有明确边界，可监控、可告警、可演练 | 故障静默发生，几天后才被发现，且不可审计 |
| 与本方案的契合 | 与"审计 day one 落库"一致：不能落库就不能做事 | 与审计原则矛盾：降级期间的操作没有可信记录 |

为什么这比静默降级更符合企业场景：企业的运维体系需要的是**可观测的确定性**——"数据库挂了，Agent 服务不可用，告警响了，按预案恢复"，这是一条能被监控、被演练、被写进应急预案的路径。而"数据库挂了，Agent 还在跑，只是状态开始分叉"是一条**无法被监控的故障**，等它被发现时已经在审计上留下了无法回答的问题。对严监管企业来说，后者是不可接受的。

同一条原则也解释了 **D11（集群档误配启动即拒）**：如果集群档配了 SQLite 或本机 markdown 记忆后端，多个副本会各自读写自己的数据副本——这不是"降级可用"，而是"从此开始产生两份互相矛盾的真相"。宁可在启动时报错并给出恢复指引。

### 6.5 恰好一次的实际边界

支撑 D3：**只承诺五个粒度，其余是"至少一次 + 幂等"。**

| # | 粒度 | 承诺 | 机制（表 / 键） |
|---|------|------|---------------|
| 1 | 会话轮次 | 同一会话的一轮处理跨副本**恰好一次**（同会话串行、跨副本排队） | `session_turn_leases`，键 `session_id`；`state` ∈ {`claimed`, `running`, `failed`}；TTL 60s / 续约 20s / 排队等待上限 120s |
| 2 | 定时触发 | 每个 `fire_time` **恰好执行一次**（每个 `fire_time` 恰好 1 行 `task_executions`） | `schedule_claims`，唯一键 `(schedule_id, fire_time)`；`state` ∈ {`claimed`, `running`, `succeeded`, `failed`, `skipped`}；TTL 120s |
| 3 | 入站事件 | 同一条事件**只处理一次**（回执去重跨副本生效） | `event_receipts`，唯一键 `(channel, event_id)`；保留 24h |
| 4 | 渠道属主 | 任意时刻同一渠道**恰好一个属主** | `channel_ownerships`，键 `channel_name`；TTL 30s / 续约 10s |
| 5 | 知识重建 | 同一后端同一作用域的重建**恰好一个执行者**，其余 409 排队 | `knowledge_build_claims`，键 `(backend, scope)`；TTL 30min / 续约 5min |

**其余链路明确是"至少一次 + 幂等"，不承诺恰好一次**：

- **审计落库**（`tool_invocations` / `llm_calls`）：每条记录是"发生过一次调用"的留痕，同 `traceId` 下可能出现多条（例如 Provider fallback 时每次尝试各写一条——这是**有意为之**的主备留痕）。不承诺去重。
- **通知推送**（`notify`）：至少一次。重复推送的最坏结果是用户收到两条相同通知，可接受。
- **给 IM 用户的回复**：至少一次。崩溃后由用户重发恢复（D6：崩溃轮次标失败不重放），即"用户重发"替代"系统重放"。

> 把边界写清的价值在于**可验收**：Demo C 的判据是"`task_executions` 每个 `fire_time` 恰好一行"，这是一条可执行的断言；而"系统保证恰好一次"无法被验收。文档里写清"哪些恰好一次、哪些至少一次"，比笼统宣称 exactly-once 更诚实、也更有用。

### 6.6 阶段边界

阶段二**不做**的事，逐条给出理由与"什么时候再谈"：

| 不做 | 理由 | 什么时候再谈 |
|------|------|------------|
| 多区域 / 多活 / 跨地域部署 | 跨地域的一致性与延迟需要另一套架构（分区、异步复制、冲突解决），与阶段二的量级无关 | 企业出现"同一底座服务多个地域且要求本地低延迟"的真实需求时 |
| 多主数据库、分区容忍 | 本方案是 CP 取向下的**单写者**模型，不做冲突合并；引入多主会把"恰好一次"的证明前提打掉 | 需要跨地域写入且能接受冲突解决语义时 |
| 分布式事务（跨多表的业务级原子性） | 阶段二的所有互斥都在**单行/单表**上完成（CAS 影响行数），不需要跨表原子性；引入 2PC / Saga 会带来远超收益的复杂度 | 出现跨多个业务系统、且必须原子提交的真实流程时 |
| Agent 级调度亲和 / 会话粘性路由 | 本方案的**前提**恰恰是"任意请求落到任意副本都正确"（README 第 2 章线外第 6 条）；引入亲和会把这个前提变成可选项，掩盖协调缺陷 | 不计划——这是设计前提，不是阶段边界 |
| 引入新中间件（Redis / ZooKeeper / etcd / 消息队列） | 见 6.1；阶段二只在 PostgreSQL 与共享文件面上做 | 见 6.1 表的"何时才值得引入"与 6.1.1 的判断信号 |
| **跨节点 Agent 协作（A2A）** | **属于阶段三的另一个层**：阶段二做的是"多个副本表现成一个 OryxOS"，阶段三做的是"多个 OryxOS 节点上的 Agent 互相发现与委托"。前者是底座自身的分布化，后者是 Agent 之间的通信底座，两者的状态模型、协议与验收都不同 | 阶段三（见 [../oryxos-docs/oryxos.md](../oryxos-docs/oryxos.md) 路线图） |
| 阶段三及以外的容量模型（十万级 Agent、跨组织联邦） | 与本周期量级目标（≥ 100 Agent、≥ 1000 并发 Session、2 ~ 8 副本）不在一个量级 | 阶段三 |

> 写在文档里的价值：这些边界让评审时不必反复讨论"要不要顺便把 Redis 也加上"。每一条都是"等真实数据证明必要"的事（D14）。

### 6.7 与项目宪章八原则 + 042 的对齐

项目宪章（`CLAUDE.md`）的八条不可违背原则与 042 工作区存储开发约束，在集群档下依然成立。本节只给对齐关系——**每条落在哪里、对应哪条决断**，不重复论证：

| 原则 | 本方案的落点 | 对应决断 |
|------|------------|---------|
| 一：自实现 ReAct Loop | 多副本不改变 ReAct 归属，协调（认领、排队、续约）在触发源外层，循环本身与 Tool 调度仍由自己控制 | — |
| 二：Spring AI 只用两件事、禁用自动 tool 执行 | 集群档不改这条边界：认领重试只在协调层，与 LLM 调用路径完全分离，不借 Spring AI 的 advisor / 重试抽象 | — |
| 三：Provider 显式映射 | 每副本各自持有 `provider name → ChatModel` 显式映射，不跨副本共享 Provider 状态，每次尝试各写一条可归因的审计 | D13 |
| 四：一个目录 = 一个 Agent；Skill 相对软连接 + 渐进披露 | 共享卷上仍只允许相对软连接（拒绝绝对链接与越界链接），校验用本机执行视图的真实路径；域重载含 `skills` | D9 |
| 五：审计 day one | 审计行带 `instance_id`，与 `trace_id` 一起跨副本可追，不做采样、不因集群化省写 | D13 |
| 六：不用 SecurityManager、软连接校验真实路径 | 共享卷下更严：执行前必须用 `nativePath` 做真实路径校验，dangling / escaped 一律拒绝，不回退旧目标 | D9、D7 |
| 七：同步执行模型 | 续约 / 轮询 / 认领重试 / 排队等待全部在调度线程与 virtual thread 上同步阻塞，不引入 Reactor / WebFlux / `CompletableFuture` 编排 | D4 |
| 八：Tool 模块三合一 | 不因集群化拆模块：存储契约放 `oryxos-core`，`oryxos-tool` 只使用它，`AGENT.md` 加载仍归 `ContextLoader` | D9 |
| 042：工作区存储约束 | 只走存储抽象 + 本机执行视图（共享模式先校验 `.workspace-id`，失败不回退本地）；`.workspace-*` 与 `.staging` 保留；管理写互斥预约不自动过期；多文件发布可恢复但非目录原子快照 | D7、D9 |

本文档只给对齐关系，具体落地见 [TechnicalSolution.md](TechnicalSolution.md) 第 23 章。

## 附录 A：关键术语

术语口径以 [README.md](README.md) 第 3 章为准（阶段一已有术语见 [../oryxos-docs/DemandAnalysis.md](../oryxos-docs/DemandAnalysis.md) 第 2 章）。**OryxOS 侧**：

1. **实例 / 副本**：一个 OryxOS 进程。集群档下每实例有全局唯一 `instance-id`，实例之间完全对等，无主从。
2. **单机档 / 集群档**：由 `oryxos.cluster.enabled` 决定（默认 `false`）。同一个 jar、镜像与配置结构，区别只在开关与所需存储面（D1）。
3. **共享状态层**：集群档下多实例共读写的状态载体 = PostgreSQL（关系型状态 + 协调原语）+ 共享卷（文件面状态）。
4. **认领（claim）/ 租约（lease）**：用带条件的写语句（CAS）把某件事唯一归属到某实例；租约是认领的凭据加过期时间，持有方周期性续约，崩溃后自然过期并由他人接管。
5. **属主（owner）**：某个渠道长连接或某项在跑工作的当前唯一持有实例。
6. **理论触发时刻**：cron 表达式算出的应触发时刻，由 `CronTrigger` 给出，**不是墙钟时间**；定时任务跨副本去重的幂等键（D5）。
7. **幂等键（idempotency key）**：判定"这件事是不是同一件"的键。会话轮次用（会话 + 轮次序号），定时任务用（任务 + 理论触发时刻），入站事件用（渠道 + 事件 id），知识重建用（后端 + 作用域）。
8. **事件回执去重**：入站渠道对同一条消息事件只处理一次。阶段一用进程内 Map，集群档落共享状态层（`event_receipts`）。
9. **版本号总线（version bus）**：`workspace_versions` 按域维护单调递增版本号；管理写路径落盘后 bump，各副本轮询比对已加载版本，落后即重载（D8）。
10. **域（domain）**：版本号总线上可独立重载的一类工作区数据：agents、skills、personas、knowledge、channels、bootstrap。
11. **代次（generation）**：知识索引的一次已提交快照版本。检索**恒读已提交代次**，重建期间旧代次继续服务；保留代次 2（当前 + 上一代）。
12. **本机执行视图（native path）**：共享工作区里的逻辑路径在本实例上真实可执行的本地路径。Tool（文件、Shell）执行必须用它（D9）。
13. **管理写互斥预约 / 读写者停机预约**：前者是管理面写某类工作区数据的前提，人工介入的闸门、**不自动过期**；后者是停机流程里的写者退场确认，保证"最后一个写者关灯"后才允许离线恢复。
14. **保留路径**：`.workspace-*` 与 `.staging`，由底座内部占用，业务 Agent 不得使用。
15. **逃生舱（escape hatch）**：`POST /api/v1/workspace/refresh`。运维绕过版本号总线直接改盘后，强制各副本重载。
16. **崩溃轮次**：实例在跑某轮次或定时触发时崩溃留下的半成品，**标失败、不重放**（D6），由用户重发恢复。
17. **误配拒启动 / fail-closed**：**前半段为 README 第 3 章的「误配拒启动」（启动期）**——集群档遇到不支持的状态组合（SQLite、markdown 记忆后端、内存知识后端等）时启动直接失败并给出恢复指引，不静默降级（D11）；**后半段（协调基质不可用时拒绝服务）为本文档补充**，对应 6.4 的 CP 取向。

**研究侧**：

18. **CAS（条件写）**：一条语句内完成"判断条件 + 写入"，用影响行数判定是否成功。本方案唯一的互斥原语（D4）。
19. **唯一约束幂等**：把幂等判定交给数据库唯一索引——插入冲突即代表重复，避免应用层"先查再插"的竞态。
20. **事务性发件箱（transactional outbox）**：把"业务数据写库"与"待发事件"放进同一个本地事务，由独立投递者至少一次地发送。本方案**不引入**（6.5）。
21. **消费组（consumer group）**：消息系统中"同一分区同一时刻只有一个消费者"的语义。本方案借用其**形状**（独占 + 失效后重新分配），不引入队列。
22. **资源版本（resourceVersion）**：K8s 对象上的乐观并发标记，也是 ConfigMap / Secret 变更感知的基础。本方案借用"版本号是唯一真相源"的形状（6.3）。
23. **inotify / WatchService**：Linux 本机内核的文件变更通知机制与 JDK 的对应抽象，**只能观察本机文件系统操作**，跨节点不可靠（D8）。
24. **RWX 卷**：Kubernetes 的 `ReadWriteMany` 访问模式，多个 Pod 同时读写同一个卷，通常由 NFS / CIFS / 云盘 RWX 提供。
25. **advisory lock（咨询锁）**：PostgreSQL 的应用级锁，分会话级与事务级，**没有过期时间**（3.1）。
26. **无状态实例，状态外置**：项目宪章的设计原则——实例不持有不可重建的状态，这是走向分布式不需要大改设计的前提。
