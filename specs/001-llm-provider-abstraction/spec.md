## Clarifications

### Session 2026-10-07

- Q: Provider 的凭证、模型与接入地址的配置归属——放在 Agent 定义里，还是集中在全局配置？ → A: 集中在**全局 Provider 注册表**；Agent 定义仅按名称引用，不关心 Provider 的任何实现细节（不写厂商、模型名、凭证、接入地址），只保留"选哪一个"的选择权。
- Q: 注册表里一个名称代表什么粒度？ → A: 一个名称 = 一个「厂商 + 模型」的完整组合（业务化别名同样合法，例如 `ops-fast`）；多模型/多档位靠注册多个名称表达，Agent 侧始终只有 Provider 名称一个字段。
- Q: 温度、输出长度上限这类采样参数由谁决定？ → A: 注册表条目提供默认值，Agent 可覆盖（采样参数视为 Agent 的行为策略，而非 Provider 的实现细节；实现细节仍全部留在注册表）。
- Q: 全局 Provider 注册表在核心阶段怎么维护？ → A: 静态配置——启动时加载、运行期只读；本能力只负责"读 + 校验 + 选路"，注册表的运行期管理与热更新不在本能力范围。
- Q: 配置错误在什么时点暴露？ → A: 分层校验——注册表自身的静态一致性错误（重名、地址非法、厂商不受支持）启动即拒；Agent 引用缺失或凭证未就绪不阻断启动（启动期显式告警），在该 Agent 调用前失败。**Provider 是弱依赖：任何一家不健康都不得阻塞应用启动，也不得连带影响其它 Provider 的调用。**
- Q: Provider 健康态势靠什么机制及时感知？ → A: 被动感知 + 状态数据——不做主动探测；每次真实调用的结果（成功 / 失败类别）即时落入审计与结构化日志，并驱动一份可读的 Provider 运行态势数据；展示出口属能力五（运行信息）。

### User Story 1 - 全局注册表 + 按名称显式路由：Agent 只保留选择权 (Priority: P1)

企业管理员在**全局 Provider 注册表**中注册 Provider 条目（例如 `deepseek-chat`、`qwen-plus`、`kimi-k2`），把该条目的实现细节一次性收拢在这里：所属厂商、模型名、凭证引用（环境变量占位）、可选的自定义接入地址、默认采样参数。Agent 作者在 Agent 定义里只写一个 Provider 名称。当上层发起一次模型调用时，系统按名称查注册表，调用只会落到该条目对应的模型连接，多 Provider 并存时不会串到别家；厂商换模型或模型下线时只改注册表，引用了该名称的 Agent 目录零改动。

**Why this priority**: 这是本能力的存在理由。企业私有部署的第一诉求是"同时接多家模型、按 Agent 精确选路"。把实现细节收在注册表、Agent 只持有名称，同时解决两件事：一是多 Provider 并存时的路由错乱（一旦选错，凭证、数据流向、成本归属全部错位），二是厂商模型演进对业务 Agent 目录的污染。没有这一条，后面所有场景都不成立。

**Independent Test**: 在注册表中注册 3 个条目（分别指向 3 个可识别身份的固定响应端点），用 3 个 Agent 各自只声明一个名称发起调用；每个响应都能归因到被声明的条目，非声明端点零流量；Agent 定义中不出现任何模型名、凭证或接入地址。

**Acceptance Scenarios**:

1. **Given** 注册表中已注册 `deepseek-chat` 与 `qwen-plus` 两个条目，**When** 一个声明 `provider: deepseek-chat` 的 Agent 发起调用，**Then** 请求只发往该条目所配的地址与凭证，`qwen-plus` 侧无任何流量。
2. **Given** 一个合法的 Agent 定义，**When** 检视它的 Provider 引用，**Then** 其中只有 Provider 名称一个字段；模型名、厂商、凭证与接入地址一律来自注册表条目，Agent 定义内零出现。
3. **Given** Agent 声明的名称未在注册表中注册，**When** 发起调用，**Then** 系统在产生任何外部调用之前失败，并明确报出未注册的名称；不得回退到任意默认 Provider。
4. **Given** 两个条目使用相同模型名但配置了不同的厂商接入地址与凭证，**When** 分别调用，**Then** 各次调用都使用自身条目的地址与凭证，二者可区分。
5. **Given** 注册表中存在两个同名条目，**When** 系统加载注册表，**Then** 加载期即报错并指出重复的名称，不进入可运行状态。

### User Story 2 - 统一调用契约：厂商差异被吸收，工具定义随请求下发 (Priority: P1)

上层推理循环把"当前 Agent 的运行配置（Provider 名称 + 采样参数）+ 消息序列 + 本次可用的工具声明"交给本能力，拿回一个统一结构的结果：要么是模型的最终文本，要么是若干条工具调用请求（工具名 + 参数），并附带本次 token 用量。上层不需要为任何一家厂商写分支代码，也永远不会被系统偷偷替它执行工具。

**Why this priority**: 这是底座与上层之间的契约面。契约定得住，上层推理循环、审计、Web 出口都能只写一份逻辑；契约一旦泄漏厂商差异，后续每个能力都要重复适配。同时"只转换、不自动执行"是本能力的硬边界，必须在本层用场景锁死。

**Independent Test**: 用同一份请求（含 2 个工具声明）分别打到两个不同厂商协议形态的固定响应端点，得到的响应结构完全同构、可被同一段解析逻辑处理；断言模型请求的工具从未被系统执行（固定响应端点可观察到的副作用为零）。

**Acceptance Scenarios**:

1. **Given** 模型返回纯文本，**When** 调用完成，**Then** 归一响应包含最终文本、工具调用请求为空、并带 token 用量。
2. **Given** 模型返回一条或多条工具调用请求，**When** 调用返回，**Then** 归一响应中包含可解析的工具名与参数；系统未执行该工具、未产生执行结果、未改写会话内容。
3. **Given** 本次调用声明了 2 个可用工具，**When** 请求下发到 Provider，**Then** 这 2 个工具的名称、说明与参数结构随请求一并送达模型。
4. **Given** 上层连续发起多轮调用，**When** 上一轮返回了工具调用请求，**Then** 该请求原样交给上层，工具执行结果的回填完全由上层决定。

### User Story 3 - 弱依赖：故障快速失败、态势可见，绝不静默换 Provider (Priority: P2)

当凭证无效或缺失、被限流、超时、网络不可达、模型名不存在时，调用方拿到的是一个结构化的失败结果：包含 Provider 名称、模型名、失败类别和可直接定位问题的原因摘要。与此同时，这次失败会被立刻计入该 Provider 的运行态势，运维能从运行信息里看到"谁在什么时候因为什么原因连续失败了几次"。系统不会偷偷改用另一个 Provider 重试，也不会返回空文本假装成功；更重要的是，一家模型不健康不会拖住整个应用——启动照常，其它 Provider 的调用照常。

**Why this priority**: 企业场景里"悄悄换了个模型"比"直接失败"危险得多——成本、合规与数据流向都会失真；而"一家模型挂了导致整个 OS 起不来"更是企业部署无法接受的。工程上不可能保证所有 Provider 永远健康，所以正确的目标不是"保证健康"，而是"不健康时不扩散 + 态势及时可见"。

**Independent Test**: 分别构造 5 类失败（凭证错误、限流、超时、地址不可达、模型不存在），逐一调用；每次都得到带 Provider 名称与失败类别的失败结果，失败的 Provider 之外没有任何外部调用发生；同时让注册表中至少一个条目不可达，验证应用仍能正常启动、其它条目的调用不受影响，且态势数据在该次失败返回时即已反映。

**Acceptance Scenarios**:

1. **Given** Provider 凭证对应的环境变量缺失或为空，**When** 发起调用，**Then** 失败结果明确指出缺失的凭证项与所属 Provider 名称，且未对外发起请求。
2. **Given** 上游返回限流、鉴权失败或模型不存在，**When** 调用返回，**Then** 失败结果保留可区分的失败类别与厂商原始错误摘要。
3. **Given** 某个 Provider 调用失败，**When** 本次调用结束，**Then** 系统未向任何其它 Provider 发起补偿调用（无 fallback、无 hedge racing）。
4. **Given** 调用超时，**When** 超时判定生效，**Then** 失败结果在配置的超时上限内返回，不无限等待。
5. **Given** 注册表中存在不可达条目或凭证未就绪的条目，**When** 应用启动并服务引用其它条目的 Agent，**Then** 启动成功、其它 Agent 调用成功率不受影响（零连带失败）。
6. **Given** 某个 Provider 连续失败，**When** 运维查看运行态势数据，**Then** 能看到该条目的最近成功/失败时间、失败类别与连续失败次数；该数据在失败调用返回时即已更新，无需等待额外的探测周期。

### User Story 4 - 调用留痕：每次调用都留下可审计的用量与结果 (Priority: P2)

每一次模型调用尝试（无论成功或失败）都会留下一条审计记录：Provider、模型、prompt/completion/total token 用量、耗时、发起时间，以及失败时的错误摘要；能关联到发起它的会话与单轮处理标识。企业据此回答"这个 Agent 这周花了多少 token、调的是哪家模型、失败了几次"。

**Why this priority**: 可审计是 OryxOS 的核心差异化能力，且必须在第一天就落库——事后从日志反解析代价高且不可靠。成本透明的基础版也建立在这份数据上。

**Independent Test**: 连续发起 3 次成功调用与 1 次失败调用，审计存储恰好新增 4 条记录；每条记录的 Provider、模型、token 用量、耗时与对应响应一致，失败记录含错误摘要。

**Acceptance Scenarios**:

1. **Given** 一次调用成功，**When** 调用返回，**Then** 审计记录中的 Provider、模型、token 用量、耗时与实际调用一致。
2. **Given** 一次调用失败，**When** 调用返回，**Then** 仍然写入一条审计记录，含 Provider、模型、失败类别与错误摘要，token 用量在未知时标记为未知而非 0。
3. **Given** 厂商响应中未提供 token 用量，**When** 记录审计，**Then** 用量字段被标记为"未知"，不伪造成 0。
4. **Given** 审计持久化暂时不可用，**When** 调用本身成功，**Then** 调用结果仍正常返回给上层，同时产生一条显式告警（不静默吞掉）。

---

### User Story 5 - 接入新厂商不动核心链路 (Priority: P3)

管理员要新增一家模型厂商时，改动仅限于配置与凭证（在既有协议形态已被支持的范围内），不需要改动上层推理循环、调用契约或审计逻辑。

**Why this priority**: 这是"边缘扩展、核心不动"架构承诺在本能力上的体现，也是长期不锁云生态的前提。它不是首日可用性的必要条件，所以排在 P3，但必须可验证。

**Independent Test**: 以一个此前未在本环境使用过的 Provider 名（协议形态已有支持）新增配置与凭证，零代码改动完成一次成功调用。

**Acceptance Scenarios**:

1. **Given** 系统已支持至少两家厂商的协议形态，**When** 仅通过配置新增第三家（同一协议形态）的 Provider，**Then** 该 Provider 可被 Agent 引用并成功调用，上层代码无改动。
2. **Given** 新增 Provider 后，**When** 运行既有 Agent，**Then** 既有 Agent 的行为与审计表现不发生任何变化。

### Edge Cases

- **Provider 名重复注册**：加载期报错并指出冲突名；不采用"后者覆盖前者"的静默行为。
- **零凭证 / 部分凭证部署**：凭证未设置不阻断启动；被引用时该次调用失败并指明缺失的凭证项与所属条目，其余条目照常服务。
- **单个 Agent 引用了未注册名称**：启动期显式告警，实例照常启动；该 Agent 的调用在发出外部请求之前失败，其它 Agent 完全不受影响。
- **运行期修改注册表配置**：不热生效、不部分生效；须重启后整体生效，避免出现"改了一半"的中间状态。
- **凭证环境变量存在但为空字符串**：视为缺失，按凭证缺失失败处理，不发出请求。
- **自定义接入地址**：支持指向企业自建网关或代理；未配置时使用厂商默认地址；地址非法（非法 URL）时加载期报错。
- **厂商不返回 token 用量**：审计与响应中标记"未知"，不计为 0，不凭估算填数。
- **模型返回畸形工具调用**（参数不是合法结构、工具名不在本次声明内）：归一响应仍可结构化表达该请求交由上层判定；系统不抛未捕获异常中断调用链。
- **消息内容超出模型上下文窗口**：按厂商错误归一为调用失败，不静默截断、不静默丢弃历史。
- **采样参数未设置或越界**：Agent 未声明时用条目默认值，条目也未声明时用该模型自身默认值；越界时按厂商错误归一为失败，不静默夹取到合法范围。
- **空消息序列或零工具声明**：仍能完成一次合法调用（零工具声明即纯对话）。
- **并发调用**：多个 Agent 同时调用相同或不同 Provider，各自凭证、参数与结果互不串扰，不存在跨调用的状态残留。
- **超长响应 / 慢响应**：受配置的超时约束，超时按失败返回，不占用调用方无限等待。

## Requirements *(mandatory)*

### Functional Requirements

**Provider 注册、配置与选路**

- **FR-001**: 系统 MUST 提供一份**全局 Provider 注册表**，可在其中注册多个 Provider 条目；每个条目 MUST 拥有全局唯一的名称，并声明所属厂商、模型名与凭证引用（以及可选的自定义接入地址与默认采样参数）。注册表 MUST 在启动时从静态配置加载、运行期只读，加载结果 MUST 是确定且可复现的。
- **FR-002**: Provider 凭证 MUST 以环境变量占位的方式注入注册表；MUST NOT 将明文密钥写入配置文件、Agent 定义、审计记录或日志。
- **FR-003**: Provider 条目 MUST 支持可选的自定义接入地址；未配置时 MUST 使用该厂商的默认地址；地址非法时 MUST 在加载期报错。
- **FR-004**: 系统 MUST 维护"Provider 名称 → 实际模型连接"的显式映射（一个名称对应唯一一个「厂商 + 模型」目标）；多 Provider 并存时 MUST 依据该映射按名称精确选择；MUST NOT 通过扫描同类连接、注册顺序或隐式默认来选择 Provider。
- **FR-005**: Agent 定义 MUST 仅通过 Provider 名称引用注册表条目；MUST NOT 在 Agent 定义中出现厂商、模型名、凭证或接入地址。
- **FR-005a**: 每个 Provider 条目 MUST 提供采样参数默认值（如温度、输出长度上限）；Agent 定义 MAY 覆盖这些参数；生效优先级 MUST 为「Agent 覆盖值 > 条目默认值 > 该模型自身默认值」，且在注册表不变的前提下同一 Agent 的调用参数 MUST 确定可复现。
- **FR-006**: 当 Agent 引用的 Provider 名称未注册时，系统 MUST 在启动/加载期给出显式告警（指出 Agent 与缺失名称），并在该 Agent 发起任何外部调用之前失败；MUST NOT 回退到任意默认 Provider，MUST NOT 因单个 Agent 引用缺失而阻断整个实例启动。
- **FR-007**: 当注册表中存在重复的 Provider 名称、非法接入地址或不受支持的厂商时，系统 MUST 在加载期报错并指出冲突/非法项，拒绝进入可运行状态。
- **FR-008**: 每次调用 MUST 使用被引用条目自身的凭证与接入地址，MUST NOT 复用其它条目的凭证。

**调用契约与响应归一**

- **FR-009**: 单次调用的输入 MUST 包含该 Agent 的运行配置（**Provider 名称** + 采样参数覆盖）与消息序列；模型名与凭证 MUST 由注册表在该次调用中解析得出，不由调用方传入。
- **FR-010**: 单次调用的输出 MUST 归一为三部分：最终文本内容；零条或多条工具调用请求（工具名 + 参数）；token 用量（输入 / 输出 / 合计，厂商不提供时标记为未知）。
- **FR-011**: 本次可用的工具声明 MUST 能随请求下发至模型；不同厂商的工具声明格式差异 MUST 由本能力吸收，上层不感知。
- **FR-012**: 系统 MUST 只做 LLM 调用与格式转换；MUST NOT 自动执行工具、MUST NOT 自行回填工具结果。
- **FR-013**: 单次调用 MUST 以同步阻塞语义返回（并发由运行时并发模型承担），MUST NOT 要求调用方使用异步编程模型。
- **FR-014**: 调用失败 MUST 表达为结构化失败结果，至少包含 Provider 名称、模型名、失败类别与原因摘要；MUST NOT 以空文本或默认文本伪装成功。
- **FR-015**: 核心阶段 MUST NOT 实现 fallback、hedge racing 或熔断；一次调用失败 MUST NOT 触发向其它 Provider 的补偿调用。

**审计与用量**

- **FR-016**: 每一次调用尝试（成功或失败）MUST 写入一条 LLM 调用审计记录。
- **FR-017**: 审计记录 MUST 包含 Provider 名称、模型名、token 用量（未知时显式标记）、耗时、发起时间；失败记录 MUST 含失败类别与错误摘要；记录 MUST 可关联发起它的会话与单轮处理标识。
- **FR-018**: 审计写入失败 MUST NOT 导致调用结果丢失，但 MUST 产生显式告警，MUST NOT 静默忽略。

**可扩展性**

- **FR-019**: 在既有协议形态已被支持的前提下，新增一个 Provider MUST 仅通过配置与凭证完成，无需改动调用契约、审计逻辑或上层调用方。

**弱依赖与态势感知**

- **FR-020**: Provider MUST 被视为**弱依赖**：任何条目的不可达、模型不可用、限流或凭证未就绪 MUST NOT 阻断应用启动，MUST NOT 连带影响其它条目的调用，MUST NOT 使系统进入不可服务状态。凭证就绪性 MUST NOT 在启动期强制要求（支持零凭证启动）。
- **FR-021**: 系统 MUST 维护每个 Provider 条目的运行态势数据，至少包含：最近成功时间、最近失败时间与失败类别、连续失败次数。该数据 MUST 在每次调用返回后即时更新，且 MUST 可在不重新发起调用的前提下被读取。
- **FR-022**: 态势数据 MUST 基于**被动感知**（真实调用结果）产生；核心阶段 MUST NOT 以主动探测（心跳、定期探测请求）作为启动前置、选路依据或态势来源。

### Key Entities

- **Provider 注册表**：全局唯一的一份 Provider 条目集合，是"名称 → 模型连接"映射的唯一真相源。关键属性：条目集合、名称唯一性约束、加载与校验结果；生命周期为"启动加载、运行期只读"。
- **Provider 条目（Provider 实例）**：注册表中的一个具名模型接入点，一个名称对应唯一一个「厂商 + 模型」组合。关键属性：唯一名称、所属厂商、模型名、凭证引用（环境变量占位）、可选自定义接入地址、默认采样参数。
- **Provider 运行态势**：每个条目随真实调用被动累积的健康画像。关键属性：最近成功时间、最近失败时间、最近失败类别、连续失败次数。它是可读状态，不是主动探测结果；展示出口不属本能力。
- **调用请求**：一次模型调用的输入。关键属性：Provider 名称、采样参数覆盖（可选）、消息序列、本次可用工具声明；模型名与凭证不在此列，由注册表解析。
- **调用响应**：一次模型调用的归一结果。关键属性：最终文本、工具调用请求列表、token 用量（输入/输出/合计，可为未知）、耗时、成功/失败状态、实际解析出的 Provider 名称与模型名。
- **工具调用请求**：模型要求上层执行的一次动作。关键属性：工具名、参数、可选的调用标识。与"已执行"无关——执行归上层。
- **LLM 调用审计记录**：一次调用尝试的留痕。关键属性：Provider、模型、token 用量、耗时、发起时间、结果状态与错误摘要、会话标识、单轮处理标识。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 多 Provider 并存时路由正确率 100%——同时注册不少于 3 个 Provider、交叉发起不少于 10 次调用，投递到非声明 Provider 的次数为 0。
- **SC-002**: 新增一个 Provider 的接入成本可度量——在协议形态已支持的前提下，仅改配置与凭证即可完成首次成功调用，全过程不超过 15 分钟，且核心调用链路代码改动为 0 行。
- **SC-003**: 审计覆盖率 100%——任何一次调用尝试（含失败、含超时）都在审计存储中恰好留下一条记录，成功与失败记录均含必需字段。
- **SC-004**: 故障可诊断率 100%——所有失败调用都返回 Provider 名称、模型名与可定位的原因摘要；静默切换 Provider 或伪装成功的次数为 0。
- **SC-005**: 契约归一——同一段结果解析逻辑可覆盖全部已接入 Provider（文本、工具调用请求、token 用量三类结果均不需要厂商分支）。
- **SC-006**: 并发无串扰——不少于 20 个 Agent 并发调用（含相同 Provider 与不同 Provider 混合）时，响应错配次数为 0，凭证混用次数为 0。
- **SC-007**: 凭证零泄漏——配置、日志、错误信息与审计记录中，完整密钥明文出现次数为 0（抽样检查）。
- **SC-008**: 故障判定的及时性——在配置的超时上限内返回失败结果，不出现超过该上限的等待。
- **SC-009**: 弱依赖不扩散——注册表中至少 1 个条目不可达或凭证未就绪时，应用仍能成功启动，且引用其它条目的调用成功率与全部健康时一致（连带失败 0 次）。
- **SC-010**: 态势时效——一次调用失败在本次调用返回时即反映到该条目的运行态势（失败类别 + 连续失败次数），无需等待额外探测周期；连续失败次数与审计中的失败记录数一致。

## Out of Scope (Core Phase)

以下内容明确不属于本能力，留待扩展阶段（架构上预留但不实现）：

- **Fallback / hedge racing / 熔断 / 自动重试**：故障直接失败给上层（FR-015）。
- **用量查询界面与成本看板**：本能力只负责写入审计数据，查询与聚合界面属治理阶段。
- **模型侧的高级路由**（按成本/延迟/负载自动选择 Provider、灰度分流）：核心阶段选路完全由 Agent 定义显式决定。
- **注册表的运行期管理**（通过命令/接口新增、修改、停用条目，热生效与并发一致性）：核心阶段注册表是启动加载的静态只读配置，改动后重启生效。
- **主动健康探测与健康状态机**（心跳、定期探测请求、healthy/degraded/unhealthy 状态迁移与状态变更告警）：核心阶段只做基于真实调用的被动感知（FR-022）。
- **态势数据的对外展示界面与告警通道**：本能力只维护态势数据，展示与告警出口属能力五与治理阶段。
- **流式输出与异步调用**：核心阶段单次调用同步返回。
- **多模态输入**（图片、音频、文件内容）与提示词模板管理。
- **认证、限流、多租户隔离**：与整体方案一致，核心阶段假设内网单租户。
- **工具的实际执行与结果回填**：归上层推理循环（能力二）与工具体系（能力四）。

## Assumptions

- **配置归属**：Provider 的厂商、模型、凭证与接入地址一律集中在全局 Provider 注册表；Agent 定义只保留 Provider 名称这一个引用字段（见 Clarifications 2026-10-07）。本决策以 `CLAUDE.md` 运行时指南与用户明确指令为准，取代 `TechnicalSolution.md` §3.1 中"Profile 内联 Provider 配置"的表述。
- **Provider 是弱依赖**：工程上无法保证所有 Provider 永远健康，因此正确目标不是"保证健康"而是"不健康不扩散 + 态势及时可见"。启动与选路 MUST NOT 以外部可达性或凭证就绪为前提（支持零凭证启动）。
- **配置校验分层**：注册表自身的静态一致性错误（重名、地址非法、厂商不受支持）启动即拒；Agent 引用缺失与凭证未就绪属运行前提缺失，启动告警、调用时失败。
- **Token 用量以厂商返回为准**：厂商不返回时记"未知"，不做估算填充。
- **上层负责工具执行**：本能力只把工具定义下发、把模型返回的工具调用请求解析出来；是否执行、执行几次、结果如何回填由上层决定。
- **失败呈现给最终用户**：核心阶段由上层把结构化失败渲染成用户可读信息；本能力不负责面向最终用户的文案。
- **同步调用与并发模型**：单次调用同步返回，高并发依赖运行时并发模型而非异步编程模型。
- **协议适配由底层管道承担**：各家厂商的协议差异由既有 LLM 管道吸收，本能力不重复实现厂商协议。
- **验证方式**：本能力的验收可完全使用固定响应端点/桩 Provider 完成，不依赖真实厂商账号与网络。
- **范围边界**：内网单租户部署假设；核心阶段不做认证、限流与配额。
